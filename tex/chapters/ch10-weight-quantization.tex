\chapter{Quantizing Weights: INT8, INT4, GPTQ, AWQ and K-Quants}\label{ch:weight-quantization}

\begin{ChapterIntent}
A quantized weight is a code interpreted using a scale and possibly other metadata. We
will connect the small encoding from Part I to real packed formats, then measure whether
reduced storage saves time after conversion work and accuracy changes are included.
\end{ChapterIntent}

\section*{Store fewer bytes per weight}
Begin with the scale, code and reconstructed value for one block. Count metadata before
converting a four-bit label into bytes per parameter. Only then compare quantization
methods and kernels. A smaller file need not run faster if the chosen hardware cannot
consume its representation efficiently. Keep storage reduction, numerical error and
measured speed as three separate outcomes.

\OpeningSection{Fewer bits, more tokens}

Take one model, Llama~3.2~3B, and store it six ways, from llama.cpp's 8-bit
format down to its 2-bit K-quant. On the M1 of \Chref{roofline}, the files
range from 3.41~GB to 1.36~GB, and decode speed runs the other way: from
\textbf{15.0 to 28.8 tokens per second} as the file shrinks
(measured; record \texttt{2026-09-23-m1-part2};
Figure~\ref{fig:ch10-quant-sweep}). Multiply each file's size by its tokens
per second and the product --- the bandwidth it effectively reads at --- stays
between 39 and 51~GB/s. Decode speed is, to first order, the inverse of the
bytes in the file. (A first run of the same sweep, while the machine was busy
with other work, measured every format about 20 to 30 percent slower; the
record keeps both runs, and the numbers here are from the second.)

\EngineFigure{ch10-quant-sweep}{Decode speed against file size for six
llama.cpp formats of Llama~3.2~3B on the M1 (measured, second run). Each curve
is a constant effective bandwidth: points on one curve read their bytes equally
fast. The 8-bit file sits on the 51~GB/s curve, the 3- and 2-bit files on the
39~GB/s curve.}{fig:ch10-quant-sweep}

Prefill does not care. The same six files process a 512-token prompt at
246--281 tokens per second, with no trend in size: prefill is compute-bound
(\Chref{prefill-decode}), and fewer bytes per weight do not reduce the
arithmetic.

Two caveats frame the rest of the chapter. First, these files were made by
re-quantizing the 4-bit file, so they measure speed only; their accuracy is
not representative of the formats. llama.cpp's own quantizer publishes the
accuracy side: on Llama-3-8B its table lists perplexity increases of 0.02 for
6-bit, 0.06 for 5-bit, 0.66 for 3-bit and 3.52 for 2-bit K-quants (the
quantizer's built-in help, build \texttt{d00685831}; the maintainers'
measurement, not reproduced here). Second, the smallest formats are not
proportionally faster. The 8-bit file is read at 51~GB/s, about what a plain
streaming kernel reached in \Chref{roofline}; the 4- to 6-bit K-quants at
46--48; the 3- and 2-bit files at 39. Q3\_K\_M is 17\% smaller than Q4\_K\_M
and only 3\% faster. Unpacking the weights has started to cost arithmetic that
the bandwidth no longer hides. That trade --- bytes saved against work added
and accuracy lost --- is this chapter's subject.

\Foundations{A stored code is not the weight}{
Quantization replaces a real-valued weight with a finite code and a reconstruction
rule. The code may be an integer, but its meaning depends on a scale, sometimes a zero
point, and a grouping convention. Counting only code bits understates the storage when
scales and padding are present. Weight-only quantization does not imply that
activations or accumulators have the same precision. Nor does small weight error
guarantee small output error: the input determines which errors matter.
Chapter~\ref{app:numerics} works through rounding and scale overhead;
Chapter~\ref{app:formats} explains why the file's type is part of the contract.
}

\NapkinSection{Napkin math: bits per weight to tokens per second}

A weight-quantized model reads $P\,q_w/8$ bytes per decode step, where $q_w$
is the average bits per weight \emph{including} scales. So
\begin{equation}
r_{\max} = \frac{8\beta}{P\,q_w}\quad[\text{tokens/s}],
\label{eq:quant-ceiling}
\end{equation}
and halving $q_w$ doubles the ceiling. Here $q_w=8b_w$: $q_w$ counts bits
per weight, while the book's canonical $b_w$ counts bytes per weight.
The averages are larger than format
names suggest. llama.cpp's ``Q4\_K\_M'' Llama~3.2~3B file averages
\textbf{5.0 bits per parameter}: its K-quant blocks cost 4.5 bits per weight
including scales \cite{kawrakow2023kquants}, and the mix keeps the vocabulary
table and, in half the layers, the value and FFN-down projections in the
6.56-bit Q6\_K format (read from the file; record
\texttt{2026-09-23-gguf-tensor-bytes}). For a 70-billion-parameter model on an
H100, equation~\eqref{eq:quant-ceiling} gives 24 tokens per second at 16 bits,
48 at 8 and about 85 at a real 4.5-bit average --- if it fits: only the last
two do, in 80~GB. The first worked problem takes the 3B file apart tensor type
by tensor type.

\section{What a quantized weight is}

A quantized weight is an integer code $q$ with $b$ bits and a rule for turning
it back into a number. The usual rule is affine:
\begin{equation}
w \approx s\,(q - z),\qquad q\in\{0,\dots,2^{b}-1\},
\label{eq:affine-quant}
\end{equation}
with a scale $s$ and a zero point $z$ shared by a group of weights. Quantizing
chooses $s$, $z$ and each $q$; dequantizing computes $s(q-z)$ inside the
kernel, just before the multiply. A symmetric scheme fixes $z$ at the middle of
the range and stores only $s$.

\emph{A worked example.} Take eight weights --- 0.90, $-0.35$, 0.12, 0.05,
$-0.61$, 0.28, $-0.02$ and 0.44 --- and quantize them to 4 bits with one
symmetric scale. Seven levels on each side of zero must reach the largest
magnitude, so $s = 0.90/7 = 0.1286$. Dividing by $s$ and rounding gives the
codes 7, $-3$, 1, 0, $-5$, 2, 0, 3, and multiplying back gives 0.900, $-0.386$,
0.129, 0, $-0.643$, 0.257, 0 and 0.386. Every error lies within half a step,
$\pm 0.064$: the largest is $-0.054$, on 0.44, and the two small weights 0.05
and $-0.02$ are rounded away altogether. Storage is eight 4-bit codes and one
16-bit scale, 48 bits: 6 bits per weight for this tiny group, 4.5 for a group of
32, 4.06 for a group of 256. (The lab's first test checks these numbers.) Two
consequences follow at once. The step, and so every error, is set by the
group's single largest weight; and the scale's cost is spread over the group.
A format is a choice of group size between those two pressures.

\section{Scales, zero points and groups}

One scale for a whole matrix wastes the grid on its few largest values. One
scale per group of $g$ consecutive weights adapts to local ranges at a cost of
$(b_s+b_z)/g$ extra bits per weight --- 0.25 bits for a 16-bit scale and a
16-bit zero shared by 128 weights. llama.cpp's K-quants go a level further:
super-blocks of 256 weights, split into sub-blocks with their own scales, which
are themselves quantized to 6 bits against a super-block scale
\cite{kawrakow2023kquants}. Q4\_K spends 4.5 bits per weight this way; Q6\_K,
6.5625; Q2\_K, 2.5625. The simplest formats keep one 16-bit scale per 32
weights: Q8\_0 stores 32 signed bytes beside it (34 bytes, 8.5 bits per weight),
and Q4\_0 32 four-bit codes read as $q - 8$ (18 bytes, 4.5 bits)
(\texttt{ggml/src/ggml-common.h} at \texttt{d006858}).

\section{A real block, byte by byte}

The lab reads the Llama~3.2~3B file itself and decodes its blocks with ggml's
layouts. A Q4\_K super-block is 144 bytes: a 16-bit scale $d$, a 16-bit scale of
minimums $d_{\min}$, 12 bytes packing eight 6-bit sub-block scales and eight
6-bit minimums, and 128 bytes of 4-bit codes. Each 32-weight sub-block $j$
decodes as
\begin{equation}
w = d\,\sigma_j\,q - d_{\min}\,\mu_j ,
\label{eq:q4k}
\end{equation}
an affine rule whose scale $d\sigma_j$ and offset $d_{\min}\mu_j$ are themselves
quantized. The first super-block of layer 0's query projection holds
$d = 3.600 \times 10^{-4}$ and $d_{\min} = 3.845 \times 10^{-3}$; its first
sub-block's 6-bit scale and minimum are 43 and 22; and its first code is 3. So
the model's first query weight is
$3.600\times10^{-4} \times 43 \times 3 - 3.845\times10^{-3} \times 22 = -0.03815$,
and the next codes, 7, 10 and 9, give $+0.0238$, $+0.0702$ and $+0.0547$
(measured by reading the file, record \texttt{2026-09-26-m1-pass3}). Every weight
of that sub-block lies on a grid of sixteen points spaced $0.0155$ apart, from
$-0.0846$ up. A Q6\_K super-block is 210 bytes: 128 bytes of the codes' low four
bits, 64 of their high two, sixteen 8-bit sub-block scales and one 16-bit $d$,
and a weight is $d\,\sigma_j\,(q - 32)$ over sixteen 16-weight sub-blocks. The
lab's decoders are twenty lines each. To check them, the lab's oracle script
called the \texttt{dequantize\_row\_q4\_K} and \texttt{dequantize\_row\_q6\_K}
functions of the very ggml library this book's llama.cpp build links against,
on the same bytes: all 24,576 values of four rows of each tensor agreed \emph{bit
for bit}. A format is only a byte layout and an arithmetic rule; transcribe
both exactly and a decoder can be rebuilt from scratch.

\section{Round-to-nearest and why it fails}

The obvious quantizer rounds each weight to its nearest grid point. It is fast
and needs no data, and at 8 bits it is nearly lossless. At 4 bits and below it
fails, for a reason that is not about weights at all: the error that matters is
in the layer's \emph{output}, $\mathbf{W}\mathbf{x}$, and a few input channels
of $\mathbf{x}$ carry much larger values than the rest. Small rounding errors
in the weights that multiply those channels are amplified; large errors
elsewhere barely matter. Every method below uses data about the activations to
decide where the error goes.

The lab measures it on real data. It takes layer 0's value projection of
Llama~3.2~3B, a $1{,}024 \times 3{,}072$ matrix stored in the file as Q6\_K,
and feeds it exactly what layer 0 sees: the token embeddings of a real text,
RMS-normalized and multiplied by the layer's own normalization weights. The
text is this book's \texttt{AUTHORING.md}, 3,217 tokens; the first 1,024
calibrate the methods that need data, and the other 2,193, of which 1,081 are
tokens the calibration never saw, evaluate them. Errors are relative,
$\lVert(\mathbf{W} - \hat{\mathbf{W}})\mathbf{X}\rVert / \lVert\mathbf{W}\mathbf{X}\rVert$
over the evaluation tokens (measured, record \texttt{2026-09-26-m1-pass3}):

\section{GPTQ: second-order error correction}

GPTQ quantizes a weight matrix one column at a time and, after each column,
adjusts the columns not yet quantized to compensate for the error just made
\cite{frantar2023gptq}. It is one-shot --- no retraining --- and its authors
quantized 175-billion-parameter models to 3 or 4 bits in about four GPU hours,
with negligible loss on the tasks they measured, and ran them end to end about
3.25 times faster than 16-bit on an A100 and 4.5 times on the less expensive
A6000. The idea is exact least
squares. For a layer with calibration inputs $\mathbf{X}$ it seeks
\begin{equation}
\hat{\mathbf{W}} = \arg\min_{\hat{\mathbf{W}}}
\lVert \mathbf{W}\mathbf{X} - \hat{\mathbf{W}}\mathbf{X} \rVert_2^2 ,
\label{eq:gptq-objective}
\end{equation}
which splits into one quadratic problem per row, all with the same Hessian
$\mathbf{H} = 2\mathbf{X}\mathbf{X}^{\top}$. Quantizing weight $q$ of a row moves
it by $w_q - \operatorname{quant}(w_q)$, and the best compensating change of
every weight not yet quantized is
\begin{equation}
\boldsymbol{\delta} = -\frac{w_q - \operatorname{quant}(w_q)}{[\mathbf{H}^{-1}]_{qq}}\,
(\mathbf{H}^{-1})_{:,q},
\label{eq:obq-update}
\end{equation}
the update of Optimal Brain Quantization, on which GPTQ builds. Its
contributions are about making that affordable. It quantizes every row in the
same column order, so that one sequence of inverse Hessians serves all rows;
it applies the updates lazily, 128 columns at a time, to raise arithmetic
intensity on a GPU; and it reads everything it needs from the Cholesky factor
of $\mathbf{H}^{-1}$, computed once, after adding 1\% of the average diagonal to
$\mathbf{H}$ for numerical stability \cite{frantar2023gptq}. The lab implements
the same algorithm without the lazy batches, in about forty lines: it forms
$\mathbf{H}$ from the calibration tokens, obtains the upper-triangular factor
$\mathbf{U}$ with $\mathbf{H}^{-1} = \mathbf{U}^{\top}\mathbf{U}$ from one Cholesky
factorization and one triangular inverse, and runs the rows in parallel; on
the M1's four performance cores it quantizes the 3.1 million weights of the lab's
projection in about ten seconds.

On the calibration tokens GPTQ is spectacular: 4.0\% output error at 4 bits,
against 15.0\% for round-to-nearest with the same groups, and 9.9\% at 3 bits
against 32.2\%. On the tokens it was not calibrated on, it gives back most of
the gain: 12.2\% and 27.8\%. The weight error tells why. GPTQ moved the weights
far from the original --- 16.8\%, the largest of any 4.5-bit method --- in the
directions the calibration inputs could see, and the calibration could not
see much. Layer 0's input depends only on the token, so 1,024 calibration
tokens are 501 distinct vectors in a 3,072-dimensional space: $\mathbf{H}$ has
rank at most 501, and GPTQ is free to push error into the directions it never
observes, held back only by the damping. The obvious cure is a wider
calibration set, and the lab tried it: 4,096 embeddings spread evenly over the
vocabulary, enough for $\mathbf{H}$ to have full rank. The overfitting
vanished --- 17.5\% on both sets of text tokens --- and so did the benefit:
GPTQ now did \emph{worse} than plain rounding, whose 15.1\% used no data at all.
Rows spread evenly over the vocabulary are mostly rare tokens, and they do not
look like this text; GPTQ minimized the error for the inputs it was shown,
faithfully, and paid for it on the inputs it was not. Both failures teach one
lesson. Second-order correction fits its calibration set, so the calibration
set must be large enough to span the inputs \emph{and} drawn from the traffic
the model will actually serve.

\section{AWQ: protect the salient channels}

AWQ observes that protecting about 1\% of weights --- those that multiply the
largest-magnitude activation channels --- removes most of the error, and that
it can protect them without storing them separately: scale those input
channels up in the weights and down in the activations, an equivalent
transformation, before quantizing \cite{lin2024awq}. With $s_{X,j}$ the average
magnitude of input channel $j$, the scale is
\begin{equation}
s_j = s_{X,j}^{\,\alpha},\qquad
\hat{\mathbf{W}} = \operatorname{quant}(\mathbf{W}\operatorname{diag}(\mathbf{s}))\,
\operatorname{diag}(\mathbf{s})^{-1},
\label{eq:awq}
\end{equation}
with $\alpha$ found by a grid search over $[0, 1]$ --- twenty points in the
paper, eleven in the lab --- that minimizes the output error on the calibration
data. A weight in a loud channel is multiplied by a large $s_j$ before rounding,
so it occupies more of its group's grid and loses less relative precision;
dividing by $s_j$ afterwards restores the product. It needs no gradients and no
reconstruction, only activation statistics, and its authors argue that this
is why it does not overfit its calibration set.

The lab bears that out. At 4 bits the search picked $\alpha = 0.6$, and the
output error fell from round-to-nearest's 15.1\% to 8.6\% on new tokens --- the
best of the methods here, better than llama.cpp's own Q4\_K at the same 4.5
bits --- while the \emph{weight} error rose, from 10.5\% to 12.5\%. AWQ spends
precision where the inputs are loud and saves it where they are quiet, and it
does so with one number per input channel, which a handful of tokens estimates
as well as a thousand: its calibration and evaluation errors agree to a tenth
of a point (8.55\% and 8.62\%). At 3 bits, with $\alpha = 0.7$, it cut the error
from 32.3\% to 20.2\%. Its authors ran the resulting 4-bit models, up to
Llama-2-70B, on desktop and mobile GPUs with their own runtime.

\section{One error, four answers}

The methods look different; they answer one question. For one output row with
weight error $\mathbf{e}$, the squared error over a set of inputs
$\mathbf{x}_t$ is
\begin{equation}
\sum_t (\mathbf{e}^{\top}\mathbf{x}_t)^2 = \mathbf{e}^{\top}\mathbf{G}\,\mathbf{e},
\qquad \mathbf{G} = \sum_t \mathbf{x}_t\mathbf{x}_t^{\top},
\label{eq:gram-error}
\end{equation}
a quadratic form in the Gram matrix of the inputs --- half of GPTQ's Hessian.
Every method is a different approximation of $\mathbf{G}$. Round-to-nearest
pretends it is the identity and minimizes $\lVert\mathbf{e}\rVert^2$, the weight
error. An importance matrix keeps only its diagonal: llama.cpp's
\texttt{llama-imatrix} accumulates, for every input column of every matrix, the
sum of the squared activations that pass through it, and the K-quant quantizer
then fits each sub-block's scale and minimum by weighted least squares, each
weight's error weighted by its column's entry (\texttt{tools/imatrix/imatrix.cpp}
and \texttt{quantize\_row\_q4\_K\_impl} in \texttt{ggml-quants.c} at
\texttt{d006858}). AWQ also uses per-column statistics, but spends them before
the rounding, by rescaling columns so that plain rounding lands where the
diagonal is large. GPTQ uses all of $\mathbf{G}$, including the correlations
between columns, and moves the unrounded weights to cancel errors along them.
The more of $\mathbf{G}$ a method uses, the better it can do on the inputs
$\mathbf{G}$ was built from, and the more it depends on $\mathbf{G}$ being
right: a diagonal is estimated well from a few hundred tokens, a
$3{,}072 \times 3{,}072$ matrix of correlations is not. The lab's table is that
trade in numbers: plain rounding the same on every input, AWQ nearly as good on
new tokens as on its calibration, GPTQ superb on its calibration set and
ordinary elsewhere.

\section{Weights and activations: SmoothQuant and W8A8}

Quantizing activations too lets the matrix product itself run in low-precision
integer arithmetic rather than dequantizing to 16 bits first --- a compute
saving for prefill, where compute binds. Activations are harder to quantize
than weights because of those outlier channels: in OPT-13B, SmoothQuant's authors
found a few activation channels with magnitudes above 70, in a layer whose
weights were flat. SmoothQuant migrates the difficulty into the weights with the
same kind of equivalent scaling as AWQ, $\mathbf{Y} =
(\mathbf{X}\operatorname{diag}(\mathbf{s})^{-1})(\operatorname{diag}(\mathbf{s})\mathbf{W})$,
but chooses the scale to balance the two operands rather than to protect one:
\begin{equation}
s_j = \frac{\max\lvert \mathbf{X}_j\rvert^{\alpha}}{\max\lvert \mathbf{W}_j\rvert^{1-\alpha}},
\label{eq:smoothquant}
\end{equation}
so that with $\alpha = 0.5$, the value that suited most models, channel $j$'s
largest activation and largest weight come out equal after scaling. The division
of the activations folds into the preceding layer's parameters offline, so it
costs nothing at run time, and both operands then fit an 8-bit grid; the
authors report up to 1.56 times the speed of 16-bit inference with half the
memory \cite{xiao2023smoothquant}. At 4 bits,
rotation-based methods multiply activations and weights by orthogonal matrices
that spread outliers evenly across channels without changing the layer's
output: QuaRot uses Hadamard rotations and quantizes weights, activations and
KV cache all to 4 bits \cite{ashkboos2024quarot}; SpinQuant learns the
rotations \cite{liu2025spinquant}.

\section{K-quants and mixed-precision files}

A quantized checkpoint need not use one format. llama.cpp's mixes assign
formats per tensor type and layer, spending bits where the model is most
sensitive: in the Q4\_K\_M file above, 6-bit K-quants for the vocabulary table
and for value and FFN-down projections in half of the layers, 4.5-bit K-quants
for everything else, and 32-bit floats for norms. The name describes the
majority format, not the average.

How good is the format itself? The lab's oracle quantized the same value
projection with ggml's reference Q4\_K quantizer --- the path
\texttt{llama-quantize} takes when it is given no importance matrix --- and
measured 11.2\% output error on the new tokens, at the same 4.5 bits per weight
as round-to-nearest in groups of 32 (15.1\%). Q4\_K's asymmetric sub-blocks and
refined scales buy a quarter of the error without any data; AWQ's activation
statistics bought 43\%. llama.cpp can bring data in too, through the importance
matrix described above, which \texttt{llama-quantize --imatrix} takes as an input
(both tools ship in the build this book uses; the importance-weighted quantizer
was not measured here).

\section{Dequantization inside the kernel}

A weight-only quantized matrix product loads packed codes, unpacks them,
applies scales, and multiplies in 16- or 32-bit arithmetic --- extra work per
weight that the bandwidth saving must pay for. At batch one there is spare
arithmetic, and the kernel stays bandwidth-bound; the opening measurement's
46--51~GB/s for the 4- to 8-bit files is that regime, and the fall to
39~GB/s at 2 and 3 bits is the unpacking beginning to show. As the batch
grows, the unpacking is repeated work per weight that batching does not
amortize the same way, and a quantized kernel can become compute-bound before
a 16-bit one would. Specialized kernels push that point out: Marlin, an
FP16$\times$INT4 kernel, stays close to the ideal 4$\times$ speedup up to
batches of 16--32 \cite{frantar2024marlin}, and vLLM's Machete kernel does the
same job with Hopper's asynchronous copies and warpgroup MMA (vLLM pull request
7174). The fastest CPU kernels avoid floating point altogether and compute dot
products directly on the integer codes, applying scales once at the end.

The lab's third part measures all of that on the M1's CPU. A
$4{,}096 \times 4{,}096$ matrix times 1, 4 and 16 vectors, on four threads, with
the weights in 32-bit floats (67~MB), in Q8\_0 (17.8~MB) and in Q4\_0 (9.4~MB)
dequantized inside the kernel, and in Q4\_0 multiplied against activations
quantized to Q8\_0 with integer dot products, every product checked against
float64 (measured, record \texttt{2026-09-26-m1-pass3}, two runs):

\noindent Four findings. \emph{Reductions cost.} Converting a block of codes to
floats and reducing it on its own, the obvious way, is the slowest kernel at one
vector; folding each block's scale into its unpacked weights and keeping sixteen
running sums in registers for the whole row, reduced once at the end, is 1.4
times faster --- the fix in the case study at the end of this chapter.
\emph{Unpacking costs about what the bandwidth saves.} Even the better float
kernel only draws level with 32-bit floats at one vector, although it reads an
eighth of the bytes: four cores stream the 32-bit weights at 40--57~GB/s, close
to their roof, while unpacking and converting 16.8 million codes takes as long.
\emph{Batches expose the unpacking.} At 4 and 16 vectors the float kernels fall
three to four times behind, because 32-bit weights are reused by every vector
for free while codes must be unpacked --- once per vector here, or reduced once
per block per vector. \emph{Integers win everywhere.} Quantizing the activations
to 8 bits once per product and multiplying codes by codes, as llama.cpp's CPU
kernels do, is 2.2 times faster than 32-bit floats at one vector and 2.2--2.7
times at sixteen, for an error of 0.3--0.5\% of the largest output where the
float kernels stay within $4\times10^{-7}$ of float64 --- the price of rounding
the activations. The third worked problem accounts for the times.


\section{Measuring what you lost}

Quantization's cost is a change in the model's output distribution, and the
honest way to measure it is to compare distributions. Perplexity on a text
corpus is a coarse average; the Kullback--Leibler divergence between the
quantized and unquantized models' next-token distributions, token by token,
shows where and how often they disagree; task evaluations show whether the
disagreements matter. \Chref{fast-wrong-answers} builds the harness, and one of
its measurements belongs here. Against Llama~3.2~3B in Q4\_K\_M, over 2,040
scored tokens, the same model requantized to Q2\_K chose the same top token only
65.8\% of the time, with a mean KL divergence of 0.58 and perplexity 1.63 times
higher; the same machinery scores an 8-bit KV cache at 99.5\% agreement and a
mean divergence of 0.00009 (record \texttt{2026-09-26-m1-part8}; the Q2\_K file
was made from the 4-bit one, so it overstates a proper Q2\_K's loss). A
quantized model whose perplexity barely moves can still change the answers to
the questions a particular application asks; a divergence measured token by
token shows how often it does.

\HappenedSection{a SIMD matrix--vector kernel slower than scalar}

Hermon's expert-streaming work needed a matrix--vector product over K-quant
weights, and its first version was scalar. The obvious vectorization ---
unpack each 16- or 32-weight sub-block to floats and call an already
vectorized dot product --- made it \textbf{slower}: 0.62 tokens per second
against the scalar 0.72 on the same trace. Every short dot product ended in a
horizontal reduction across the vector lanes, and on 16 elements the reduction
cost more than the multiply--adds it summed. Folding each sub-block's scale into
the unpacking let a whole 256-weight super-block be reduced once, eight times
fewer reductions, and the result was about \textbf{1.3$\times$} faster than
scalar on an x86 machine with AVX2 --- far from the 8--19$\times$ the same
team had measured vectorizing other kernels (Hermon
\texttt{docs/STORAGE\_ARCHITECTURE.md}, section 5.8, commit \texttt{a7c0597}).
Its authors located the remaining multiple precisely: the fast implementations
never convert the codes to floating point, computing integer dot products and
scaling once at the end --- the lab's fourth kernel. Correctness held
throughout: the vectorized path reproduced a NumPy reference on real Qwen3
weights exactly. The kernel is callable through the kernel crate's public
interface, but no request path calls it at commit \texttt{2a3fd52}, so LIBRARY.

\FrontierSection{2026-09-27}

Post-training weight quantization is becoming one option among several.
Models increasingly arrive already quantized or trained for a format
(\Chref{low-precision-float}); rotation-based methods push weights,
activations and cache together to 4 bits \cite{ashkboos2024quarot,liu2025spinquant};
and serving engines carry specialized mixed-precision kernels per GPU
generation \cite{frantar2024marlin}. At the low end, llama.cpp's i-quants
replace uniform grids with fixed code books: an index selects a pattern of
eight (IQ2) or four (IQ3) weight magnitudes from a 256-entry table, and the IQ4
formats use sixteen non-uniform levels. Scales included, they run from 1.5625
bits per weight (IQ1\_S) through 2.0625 (IQ2\_XXS) and 3.0625 (IQ3\_XXS) to
4.25 (IQ4\_XS) (block definitions in \texttt{ggml/src/ggml-common.h} at
\texttt{d006858}).
