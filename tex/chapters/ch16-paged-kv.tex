\chapter{Paged KV Memory}\label{ch:paged-kv}

\begin{ChapterIntent}
When every request reserves contiguous KV memory for its maximum length,
most of the reservation is never used and capacity --- and with it batch size
and throughput --- collapses. Paged KV memory borrows virtual memory's answer:
fixed-size blocks, a per-request block table and a pool that allocates on
demand. This chapter builds a block pool with reference counts and
copy-on-write, rewrites attention to read through a block table, prices the
indirection, and discusses block size, fragmentation and eviction.
\end{ChapterIntent}

\OpeningSection{Most of the reservation, never used}

Give llama.cpp's server 8,192 cells of KV cache and ask for four request
slots, and by default it cuts the cache into four private regions of 2,048
cells, one per slot (the unified pool is the default only when the server
chooses the slot count itself). On the M1, with Llama~3.2~3B and nothing else running, a request with a
3,001-token prompt was refused with HTTP 400: \emph{request (3001 tokens)
exceeds the available context size (2048 tokens)}. All 8,192 cells were
allocated --- 896~MiB at 112~KiB per token --- and all of them were empty.
Restarted with one unified pool that every slot can draw from, the same server
accepted the same request and processed its prompt in 11.4 seconds (measured;
record \texttt{2026-09-24-m1-part3}). Nothing about the memory changed. Only
the rule for who may use which cell did.

The per-slot rule is contiguous reservation, and it is the rule every early
serving system used: decide in advance how long a sequence may grow and set that
much memory aside. The reservation must cover the worst case, because a
sequence that outgrows its region cannot simply continue elsewhere. When the
vLLM team measured the systems of 2022, only 20.4\% to 38.2\% of their KV-cache
memory held actual token states; the rest was reservation and fragmentation
\cite{kwon2023pagedattention}. Since the batch size is bounded by the cache
(\Chref{kv-cache}), a cache two-thirds wasted is a batch a third of its
possible size --- and, on the roofline, a third of the throughput.

\Foundations{Logical order need not be physical order}{
Attention needs keys in the correct logical positions; it does not require all their
bytes to occupy one contiguous allocation. A block table maps a request's logical
block number to a physical block. The offset within that block then selects a token.
Sharing a full immutable block is different from allowing two requests to append into
the same mutable tail. This distinction motivates reference counts and copy-on-write.
Chapter~\ref{ch:kv-cache} supplies the append-only history model;
Chapter~\ref{app:notation} gives the quotient-and-remainder arithmetic used by an
address translation.
}

\NapkinSection{Napkin math: fragmentation under real length distributions}

Suppose each request reserves room for $S_{\max}$ tokens but uses $S_i$, its
prompt plus its output. The fraction of reserved memory that holds tokens is
\begin{equation}
u_{\text{reserve}} = \frac{\bar{S}}{S_{\max}}.
\label{eq:reserve-utilization}
\end{equation}
An API that allows 32,768-token contexts but sees a mean of 2,000 tokens per
request (illustrative) has $u = 0.06$: 94\% of the cache is reserved and empty.
Now allocate in blocks of $b$ tokens on demand. A sequence wastes only the
unused tail of its last block, about $b/2$ tokens on average, so
\begin{equation}
u_{\text{paged}} \approx \frac{\bar{S}}{\bar{S} + b/2},
\label{eq:paged-utilization}
\end{equation}
which for $b = 16$ and $\bar{S} = 2{,}000$ is 0.996. The batch that fits in a
fixed cache grows by $u_{\text{paged}}/u_{\text{reserve}}$ --- sixteenfold in
this example --- until something else binds: compute, or the latency each
sequence can tolerate (\Chref{continuous-batching}).

\section{Reservation and fragmentation}

Contiguous allocation wastes memory three ways. \emph{Reservation} holds space
for tokens a sequence may never produce. \emph{Internal fragmentation} is the
unused end of a region once the sequence stops. \emph{External fragmentation}
is free memory broken into pieces too small for the next request's region, even
when their sum would suffice. The opening measurement is the purest case of the
first: the cache was free, and the request still did not fit, because the free
memory belonged to other slots.

\section{Blocks and block tables}

PagedAttention applied the operating system's answer to the KV cache
\cite{kwon2023pagedattention}. The cache becomes a pool of fixed-size blocks,
each holding the keys and values of $b$ consecutive tokens for every layer and
KV head. A sequence owns a \emph{block table}: the list of physical blocks that
hold its first $b$ tokens, its next $b$, and so on. Logical position $p$ lives
in block $\lfloor p/b\rfloor$ of the table at offset $p \bmod b$. Blocks are
allocated when a sequence crosses a block boundary, so no memory is reserved
for tokens not yet generated and no sequence needs contiguous space. vLLM's
default block size was 16 tokens.

Trace logical position four through each table. The offset within its block is zero for both requests, but A reaches physical block two and B reaches block nine. Sharing the prefix is safe because neither continuation writes into the other's tail.

\section{The block pool and its allocator}

With every block the same size, allocation needs no search: the pool keeps a
free list and hands out its head. Freeing a finished sequence returns its
blocks in constant time per block. The allocator's real decisions are
elsewhere: how many blocks to hold back so running sequences can grow, and
which cached blocks to evict first when the free list is empty. vLLM's V1 pool
keeps freed blocks that still hold reusable content in a queue ordered by
recency, so the same list serves allocation and least-recently-used eviction
\cite{vllm2026prefixcaching} --- the bridge to \Chref{prefix-caching}.

\section{Sharing: reference counts and copy-on-write}

Once sequences reach their memory through tables, two tables can point at the
same block. Parallel sampling --- several completions of one prompt --- needs
the prompt's blocks once, not once per completion; beam search shares every
prefix the beams have in common. Each block carries a reference count. A
sequence that must write into a shared block --- the partly filled last block
of a common prompt --- first copies it and points its own table at the copy.
This is copy-on-write, borrowed from \texttt{fork}, and it is what makes sharing
safe: no sequence can see another's tokens.

\section{Attention through a block table}

The price of paging is paid inside the attention kernel. Instead of reading a
contiguous $S\times d_h$ key matrix, the kernel walks the block table, reading
$b$ tokens at a time from wherever each block lives (\Chref{decode-attention}).
The table is small and the lookups are cheap next to the bytes they locate,
provided blocks are large enough to be read in efficient bursts. The larger
cost is engineering: every attention kernel, and every kernel that touches the
cache, must be written or rewritten for the paged layout. vAttention's authors
argue that this burden is avoidable: they keep each sequence's cache
contiguous in \emph{virtual} memory and map physical pages on demand through
the GPU's virtual-memory interface, so unmodified kernels work, and they report
up to 1.23 times the throughput of paged kernels in FlashAttention and
FlashInfer \cite{prabhu2025vattention} (their measurement).

\section{Choosing the block size}

Small blocks waste less --- about $b/2$ tokens per sequence --- but lengthen
block tables, add lookups and make each memory access smaller. Large blocks
read efficiently and share less: two prompts that agree on 1,000 tokens share
only whole blocks, so a 256-token block wastes up to 255 tokens of possible
reuse at the boundary. Kernels also constrain the choice, because a block is
the unit a thread group loads. Hybrid architectures complicate it further:
vLLM's hybrid cache manager groups layers so that full-attention layers keep
blocks for every token while sliding-window layers keep only the most recent
window, with one page size across groups \cite{vllm2026hybridkv}.

\section{Eviction and swapping at block granularity}

When the pool runs dry, the scheduler must free blocks that running sequences
still need. It can \emph{swap} a victim's blocks to host memory and bring them
back later, paying bus bandwidth twice, or \emph{recompute}: drop the blocks,
requeue the sequence, and rebuild its cache later by prefilling its prompt and
the tokens it had generated. Recomputation costs compute instead of transfer
and needs no host memory; vLLM's V1 engine preempts by recomputation by default
\cite{vllm2026optimization}. \Chref{scheduling} takes up which sequence
to evict.

\HappenedSection{the paged path and its release gate}

Hermon's default runtime keeps each sequence in one of a fixed number of
llama.cpp slots (\Chref{continuous-batching}), with the slot limits that
implies. Its developers built a paged alternative as a separate attention path
that reads keys and values from its own block pool and calls llama.cpp only for
the rest of the layer, keeping the vendored library unmodified (Hermon
\texttt{docs/PHASE\_1D\_INTEGRATION.md}). The path is selected with
\texttt{HERMON\_RUNTIME\_MODE=paged} and \texttt{HERMON\_PAGED\_GGUF=1}, and
it refuses to run with a temperature above zero; the default remains the
slot-based runtime (\texttt{crates/hermon-runtime/src/dispatch.rs} at commit
\texttt{2a3fd52}; PREVIEW).

What keeps it a preview is a gate written before the code: the paged path
becomes the default only when it produces bit-identical output to the
slot-based path over a corpus of a thousand prompts at temperature zero. At
that commit the path matched llama.cpp on a three-token greedy decode of the
reference Llama~3.2 model and on a chat case; the thousand-prompt corpus had
not been run.
Paging changes where every token's keys live and how every attention kernel
finds them, so its bugs are silent --- a wrong block entry produces fluent,
wrong text. A gate stated in advance, and checked by bits rather than by
reading outputs, is how such a change earns the default.

\FrontierSection{2026-09-24}

Paging is the industry standard for GPU serving; the questions now are how far
the abstraction stretches. vAttention revisits the trade between a paged layout
and unmodified kernels \cite{prabhu2025vattention}. Hybrid models mix layers
whose caches grow at different rates, and vLLM's hybrid manager allocates each
group differently under one page size \cite{vllm2026hybridkv}. And blocks have
become the unit of transfer between machines and storage tiers: prefix caches
(\Chref{prefix-caching}), disaggregated prefill (\Chref{disaggregated-serving})
and KV stores (\Chref{kv-storage-tier}) all move KV cache in blocks.

\end{enumerate}
