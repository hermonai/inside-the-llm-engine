\chapter{Offloading Across VRAM, RAM and NVMe}\label{ch:offloading}

\begin{ChapterIntent}
Most people run models on hardware that is too small for them. Offloading
places some layers, experts or cache blocks in host memory or on NVMe and
streams them in when needed, and then the slowest link --- PCIe or the SSD ---
sets the token rate. This chapter prices each tier by bandwidth, covers layer
offloading, CPU--GPU splits, cache and expert offloading and prefetching, and
shows how to predict the result before trying it.
\end{ChapterIntent}

\OpeningSection{From 448 gigabytes per second to 18}

When Hermon's developers brought its paged-attention kernel to CUDA in August
2026, the first question was not about the kernel. It was where the key/value
cache should live. On Apple silicon the cache's arena sat in ordinary host
memory and the GPU read it in place, because CPU and GPU share one memory
(\Chref{unified-memory}). On the development desktop's RTX~5060~Ti the same
choice was available --- the driver will map host memory into the GPU's address
space --- and the developers measured what it would cost. The card's memory was
recorded at 448~GB/s; pinned host memory copied across PCIe arrived at
17.8~GB/s, 25 times less (Hermon \texttt{docs/KERNEL\_DESIGN.md} section K5,
commit \texttt{79c1485}; the developers' measurement)
\todo{measure: host-to-device and device-to-host copy bandwidth on the RTX 5060
Ti host, with the PCIe generation and link width recorded}.

A decode step of Llama~3 8B at a 4,096-token context reads about 537~MB of
cache: 32 layers, 8 key/value heads of width 128, keys and values, two bytes
each (derived). From the card's memory that takes 1.2~ms. Across the link it
takes 30~ms --- a ceiling of 33 tokens per second set by the interconnect alone,
before one weight has been read. The arena moved to the card. Host-mapped
access worked, the developers wrote, and was exactly the wrong thing to use.

Every offloading decision is that calculation with different bytes: what a
token must read, from which tier, over which link. The same desktop spans two
orders of magnitude --- 448~GB/s in the card's memory, 17.8~GB/s across PCIe,
about 2.3~GB/s from its NVMe drive with the page cache bypassed
(\Chref{expert-streaming}) --- and a byte placed on the wrong tier costs as much
as dozens placed on the right one.

\NapkinSection{Napkin math: the slowest link sets the rate}

Let a decode step read $W_i$ bytes from tier $i$, each at the bandwidth
$\beta_i$ with which the processor doing the arithmetic can read that tier. If
the reads do not overlap,
\begin{equation}
t_{\mathrm{tok}} \approx \sum_i \frac{W_i}{\beta_i},
\qquad
\frac{t_{\mathrm{tok}}}{t_{\mathrm{fast}}} = 1 + f\,(\rho - 1),
\label{eq:offload-time}
\end{equation}
where the second form puts a fraction $f$ of the bytes on a tier $\rho$ times
slower than the fast one. The tiers add like resistors in series: at
$\rho = 25$, placing 4\% of the bytes across the link doubles the time per
token, and placing a quarter of them there multiplies it by seven.

Take a model of the Qwen3-8B architecture in llama.cpp's Q4\_K\_M format: a
decode step reads about 4.9~GB of weights (the 5.2~GB file less its token-embedding
table, from which a step reads one row; derived). From the card's
448~GB/s that is 10.9~ms, a ceiling of 92 tokens per second. Put a quarter of
the layers in host memory and the result depends on how those bytes are used:
\begin{itemize}
\item computed by the CPU from its own memory, at an illustrative 40~GB/s
  (dual-channel DDR4-3200 is specified at 51.2~GB/s), the step takes
  $8.2 + 30.4 = 39$~ms, 26 tokens per second;
\item copied across the link every step at 17.8~GB/s, it takes $8.2 + 68 =
  77$~ms, 13 tokens per second;
\item read from the NVMe drive at 2.3~GB/s, it takes about 0.54~s, under 2 tokens
  per second (all derived with Equation~\ref{eq:offload-time}).
\end{itemize}

The ordering is the chapter in miniature
(Figure~\ref{fig:ch35-slowest-link}). For decoding one sequence, weights
that must live off the card are better computed where they live than moved to
where the fast processor is. Moving them pays only when one transfer is
amortized over many tokens: a streamed layer costs $W/(\beta\,B)$ per token for
a batch of $B$, so the 77~ms above falls to 0.15~ms per token in a 512-token
prefill chunk. Offloading systems built for throughput exploit exactly this
\cite{sheng2023flexgen}.

\section{When the model does not fit}

An 8~GB card holds the weights of an 8B model at 4 bits with room for a
modest cache, and not much more. A 14B model at 4 bits, a 30B mixture-of-experts
model, or a long context on either does not fit, and there are four ways out:
a smaller format (\Chref{weight-quantization}), a smaller cache
(\Chref{kv-quantization}), a smaller model, or placing some bytes elsewhere.
Offloading is the fourth, and Equation~\ref{eq:offload-time} says which bytes
to place elsewhere first: those a token reads least often per byte stored. A
dense layer's weights are read by every token. A mixture-of-experts layer's
experts are each read by a small fraction of tokens --- 8 of 128 in Qwen3-30B-A3B,
6\% at batch one. The cache of a conversation that is waiting for its user is
read by nobody until the user returns. Offload in that order: idle cache first
(\Chref{kv-storage-tier}), experts next, dense layers last.

\section{Layer offloading}

The oldest form of offloading keeps whole layers in host memory. In llama.cpp,
\texttt{-ngl}~$N$ places the last $N$ layers on the GPU, counting the output
layer as one of them; the rest stay in host memory and, during decode, the CPU
computes them there, so their weights never cross the link. For batches of 32
tokens or more, the scheduler may instead copy a host-resident weight to the GPU
for one matrix multiplication, because a large enough batch amortizes the
transfer (\texttt{ggml/src/ggml-cuda/ggml-cuda.cu} and
\texttt{ggml-metal.cpp} at \texttt{d006858}; DEFAULT, disabled by
\texttt{--no-op-offload}). vLLM offers both halves as configuration: its UVA
backend keeps chosen weights in pinned host memory and lets the GPU read them in
place on every forward pass, which its documentation says requires a fast
CPU--GPU interconnect; its prefetch backend offloads the last layers of every
group and copies each one to the GPU on a separate stream a configurable number
of layers ahead (\texttt{vllm/model\_executor/offloader/} at \texttt{bcdacfc};
PREVIEW, off by default).

On the M1 used for this book's measurements the experiment has a twist:
there is no link, because CPU and GPU share one memory, so moving layers
between them changes which processor reads the bytes, not where the bytes are.
With all 37 offloadable layers of the Qwen3-8B-architecture model on the GPU,
llama.cpp decoded 10.0 to 10.7 tokens per second; with none, on four CPU
threads, 5.9 to 8.0 --- the CPU reading the same memory at about two thirds of
the GPU's rate. With 27 layers on the GPU decoding ran at 6.6 to 9.8, between
the two as Equation~\ref{eq:offload-time} predicts. With 18 it ran at 1.7 to 7.9,
and with 9 at 0.4 to 2.4 --- slower than no GPU at all (measured, four runs of
each on a loaded machine; record \texttt{2026-09-24-m1-part7}).

The cause was memory, not arithmetic. For layers that stay on the CPU,
llama.cpp repacks the weights into an interleaved layout its Arm kernels read
faster --- a second copy of those layers, 2.9~GiB when 28 of them stay behind ---
while the Metal backend maps the whole model file for the GPU. On a 16~GB
machine already deep in swap, the copy tipped the system into paging. In one
43-second run with 9 layers on the GPU, 6.0~GiB were swapped out and decoding
ran at 1.4 tokens per second; with repacking turned off (\texttt{--no-repack}),
the CPU layers read the same mapped pages the GPU used, nothing was swapped out,
and decoding ran at 9.1. Two days later the same pair measured 0.42 and 5.7,
with 22.7 and 4.1~GiB swapped out (measured; the second pair started cold).
Prefill, which is compute-bound, degraded smoothly in the same sweep: 113 to
120 tokens per second on the GPU, 56 to 58 with 27 layers there, 35 to 36 with
18, 20 to 21 with 9, and 25 to 27 on the CPU alone. A layout optimization that is free on a machine
with memory to spare made the split unusable on one without it --- which is
the argument of \Chref{unified-memory}: on one memory, a second copy is the
expensive part of offloading.

\section{Splitting work between CPU and GPU}

Layer offloading splits a model once per step. Finer splits place individual
tensors: llama.cpp's \texttt{-ot} option assigns tensors matching a pattern to
a buffer type, so attention can stay on the GPU while the feed-forward weights
of every layer live in host memory. The step then crosses between processors
twice per layer; llama.cpp's scheduler reported 74 graph splits per decoded
token for this placement, against 2 with the whole model on the GPU, and every
split is a synchronization --- one processor must finish before the other reads
its output. On the M1 this split decoded at 0.09 to 2.5 tokens per second in
six runs with llama.cpp's default repacking --- the slowest while 130~GiB were
swapped out in six minutes --- because it paid for the same second copy as the
layer splits above. Without the copy it decoded at 6.8 tokens per second
(measured, one run), inside the 6.8 to 8.7 that
Equation~\ref{eq:offload-time} predicts for 3.3~GB of feed-forward weights read
by the CPU and 1.6~GB by the GPU at the rates each reached alone (derived). On
this machine, 74 crossings per token cost little; memory cost a great deal.

On a discrete GPU the crossings are not cheap, because each one is a
transfer across the link and a round of kernel launches. KTransformers, which
runs DeepSeek-V3's routed experts on CPUs and everything else on a GPU, reports
that a straightforward CPU--GPU orchestration of that
model decoded at 4.68 tokens per second with the GPU below 30\% utilization, and
that such systems issue thousands of GPU kernel launches per decoded token ---
over 7,000 for Fiddler, about 3,000 for llama.cpp
\cite{chen2025ktransformers}. Splitting is worth doing only where the bytes
saved exceed the crossings added: Fiddler's observation was that for a small
batch an expert's input is kilobytes while its weights are hundreds of
megabytes, so it computes experts that are not on the GPU on the CPU instead of
copying them \cite{kamahori2025fiddler}. PowerInfer applies the same test to
neurons, keeping the frequently activated ones on the GPU and computing the
rest on the CPU, and reports up to 11.69 times llama.cpp's speed on an RTX~4090
\cite{song2024powerinfer}.

\section{Offloading the cache}

The cache is the worst candidate for offloading while its sequence is active,
because decode reads all of it at every step --- the arithmetic that moved
Hermon's arena to the card. llama.cpp's \texttt{--no-kv-offload} keeps the
cache in host memory and computes attention on the CPU. On the M1 that cost
little with an empty context and a lot with a long one: decoding fell from
8.9 to 10.9 tokens per second to 7.5 to 8.1 at no prior context, and from 8.5 to
8.9 to 4.7 after 4,096 tokens (measured, two passes). There were no bytes to
move; the CPU was slower at attention over 4,096 positions than the GPU. On a
discrete card the options are worse still: attention on the CPU, or the GPU
reading the cache across PCIe at every step. What offloading the cache is good
for is caches that are not being read --- a paused conversation, a prefix
waiting for its next request --- which is the storage tier of
\Chref{kv-storage-tier}, moved back in whole blocks before they are needed.

\section{Offloading experts}

Experts are the best candidates: at batch one a token reads 6\% of Qwen3-30B-A3B's
experts, and which 6\% changes from token to token. llama.cpp's
\texttt{--cpu-moe} keeps every expert tensor in host memory, and
\texttt{--n-cpu-moe}~$N$ does so for the first $N$ layers, so the GPU holds
attention, the router and the shared weights while the CPU computes the
experts where they live (\texttt{common/arg.cpp} at \texttt{d006858}; explicit
options). By Equation~\ref{eq:offload-time} a
token's 1.1~GB of Qwen3-30B-A3B experts cost about 27~ms computed from host
memory at 40~GB/s, 62~ms copied across the link at 17.8~GB/s, and 0.48~s read
from the NVMe drive (derived).

On the M1 the same options can be measured with a small mixture-of-experts
model, IBM's Granite 3.1 3B-A800M, and there is no link to cross: CPU and GPU
read the same pages of the file, and \texttt{--no-repack} keeps it that way.
Keeping every expert on the CPU cut single-sequence decode from 49--58 tokens
per second to 31--32 and prefill from 573 to 160--181; keeping the experts of
half the layers there gave 39--43 and 253--323; four sequences decoding
together lost less, 88--90 tokens per second against 64--67 (measured,
\texttt{llama-batched-bench}, two interleaved rounds; record
\texttt{2026-09-26-m1-part8}). With nothing to copy, the option only moves
arithmetic from the faster processor to the slower one, and prefill, which is
compute-bound, pays most. On a discrete GPU the same option replaces a copy
across the link, and by the arithmetic above that is where it wins.
KTransformers takes the placement to server CPUs, with Intel AMX kernels for
prefill and lighter AVX-512 kernels for decode; on a dual-socket Xeon with an
A100 or an RTX~4080 it reports 4.62 to 19.74 times the prefill speed and 1.25
to 4.09 times the decode speed of existing hybrid systems, and a further
1.45 times from deferring some experts' results to the next layer, at an
average accuracy cost of no more than 0.5\% \cite{chen2025ktransformers}. When
even host memory is too small, the experts go to the drive, and the hit rate of
an expert cache decides everything (\Chref{expert-streaming}).

\section{Prefetch and overlap}

Overlapping a transfer with computation turns the sum in
Equation~\ref{eq:offload-time} into a maximum. It cannot do better: prefetching
hides a slow link only behind work that takes at least as long. The techniques
differ in how they know what to fetch. Layer offloading knows exactly ---
the next layer is always the next layer --- which is why vLLM's prefetch
backend can issue copies several layers ahead. FlexGen searches for a schedule
over weights, cache and activations across GPU, CPU and disk, and with a large
effective batch generated from OPT-175B at 1 token per second on a single 16~GB
GPU \cite{sheng2023flexgen}. Expert offloading must guess: applying the next
layer's gate to the current hidden state predicts its experts well enough to
start reading early \cite{eliseev2023moeoffload}, and a model can be trained to
route one layer ahead \cite{hwang2023pregated}. On flash storage the unit of
transfer matters as much as its timing: Apple's LLM in a Flash reads larger
contiguous chunks and reuses recently loaded neurons, running models up to
twice the size of DRAM with 4 to 5 times the speed of naive loading on a CPU
and 20 to 25 times on a GPU \cite{alizadeh2024llmflash}.

\LedgerSection

Placing layers, experts or cache blocks in host memory or on an SSD:

\begin{ConstraintLedger}
Memory capacity & buys & Models and contexts larger than the accelerator's memory run at all. \\
Memory bandwidth & spends & Every byte placed on a slower tier costs its bandwidth ratio; at 25$\times$ a few percent of the bytes doubles the step. \\
Latency & spends & Per-token time rises with the fraction off the card, and each CPU--GPU crossing adds a synchronization. \\
Compute & moves & The host CPU takes arithmetic the GPU would have done faster; the GPU idles while it waits. \\
\end{ConstraintLedger}

\HappenedSection{hybrid inference hits the CPU}

Running DeepSeek-V3 --- 671 billion parameters --- outside a data center means
keeping its routed experts in the DRAM of a server with one or two CPUs and
everything else on a single GPU. The KTransformers team measured where that
approach, as implemented by an existing CPU--GPU orchestration system, spent its
time: 70.02 tokens per second of prefill and 4.68 of decode, with the GPU below
30\% utilization. The CPU was the bottleneck in two ways. Its matrix kernels used
generic vector instructions rather than the processor's matrix extensions ---
and even a library path that did use them reached 7\% of their theoretical
peak in the authors' measurement. And the orchestration issued thousands of GPU
kernel launches per token and synchronized CPU and GPU twice in every MoE
layer.
The fixes were each aimed at one term: AMX kernels with a memory layout built
for them, a schedule that lets CPU and GPU submit and wait asynchronously so
that the whole step can be captured as one CUDA graph, and deferring some
experts' contribution to the next layer so that CPU and GPU work overlap ---
the one change that alters the computation, and the one whose accuracy the
authors measured \cite{chen2025ktransformers}. Offloading moves the bottleneck;
it does not remove it. The engineering is in finding where it moved.

\FrontierSection{2026-09-24}

Offloading is becoming a configuration of mainstream engines rather than a
separate system: vLLM ships zero-copy and prefetching weight offload behind
options, llama.cpp exposes tensor-level placement and expert placement, and
the KTransformers and SGLang projects have announced SGLang integration of
KTransformers' CPU kernels for hybrid serving \cite{lmsys2025ktransformers}. Two hardware trends change the
equation's inputs. CPUs gain matrix engines (AMX, and SME on Arm), raising what
the host can compute where the bytes live; and coherent CPU--GPU links such as
NVLink-C2C carry seven times the bandwidth of PCIe Gen~5 by NVIDIA's
comparison, which turns some of this chapter's offloading into the
single-memory design of \Chref{unified-memory}.

\item \emph{Derivation.} Extend Equation~\ref{eq:offload-time} to a batch of
  $B$ sequences with weights streamed across the link once per step, and find
  the batch at which streaming a quarter of the Qwen3-8B-architecture model's layers costs
  less per token than computing them on a 40~GB/s CPU.
\item \emph{Prediction.} On an 8~GB card at 448~GB/s with a 17.8~GB/s link,
  predict decode tokens per second for a 14B dense model at 4 bits with
  (a) layers split to fit, computed by the CPU at 40~GB/s, and (b) the same
  layers streamed across the link every step.
\item \emph{Implementation.} Run the lab's sweep over \texttt{-ngl} on your
  machine and fit $\beta_{\mathrm{cpu}}$ and $\beta_{\mathrm{gpu}}$ to the
  measurements. Where does the fit break?
\item \emph{Falsification.} On the M1 the repacked copy turned a split that
  should have interpolated into one slower than either processor alone. Using
  your machine's free memory, predict for which values of \texttt{-ngl}
  repacking is a net loss, and design a measurement that could prove the
  prediction wrong --- including the swap counters that would.
\end{enumerate}
