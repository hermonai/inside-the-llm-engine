\chapter{One Server, Many Models: LoRA, Adapters and Routing}\label{ch:multi-model-serving}

\begin{ChapterIntent}
A fine-tuned model need not be another full copy of a base model. Low-rank adapters
make the difference small enough to load, cache and batch dynamically---but only if
the inference engine treats adapter identity as part of model identity. This chapter
derives LoRA execution, follows one mixed-adapter batch through segmented kernels,
builds a two-tier adapter cache, and connects routing decisions to KV correctness,
continuous batching, scheduling and cold starts. The goal is not merely to ``support
LoRA.'' It is to share every byte and operation that is genuinely common without ever
sharing state whose semantics differ.
\end{ChapterIntent}

\OpeningSection{The weights are small; the scheduling boundary is not}

For the Llama~3.2~3B configuration used by this edition's M1 experiments, adapting all
seven major projections in each transformer layer at rank 16 produces about
24.3 million LoRA parameters, or 48.6 MB in 16-bit storage (derived from the stated
layer dimensions). That is less than one percent of the roughly 3.2-billion-parameter
base. A thousand such adapters occupy about 48.6 GB rather than thousands of full base
models.

The measurement record then exposes the systems problem. Three synthetic adapters
were loaded into llama.cpp: two rank-16 and one rank-64. Their $B$ factors were zero,
so mathematically every adapter update was zero. Outputs matched the base token for
token, while the engine still executed the adapter path. A single stream decoded at
roughly 41--42 ms/token without an adapter, 45--51 ms/token at rank 16, and
49--51 ms/token at rank 64 (measured, two runs each;
\texttt{research/measurements/2026-09-24-m1-part3.md}).

More revealingly, two simultaneous users selecting \emph{different} rank-16 adapters
did not share the measured decode step. One 128-token response completed around
6.7 seconds and the second around 13.1 seconds. When both selected the same adapter,
they shared steps and both completed around 11.8 seconds. The pinned server path at
llama.cpp commit \texttt{d006858} required compatible adapter settings for slots to
batch together.

The base weights were shared in memory. The execution policy still serialized
different effective models. Multi-adapter serving exists to remove that boundary
without corrupting which model each request asked for.

\Foundations{A model is more than a base checkpoint}{
Let a request select base checkpoint $m$, adapter set $a$, adapter version $v$, and
scales/composition $c$. The effective model is a function
$F_{m,a,v,c}$, not merely ``model $m$.'' Any state computed by model weights---KV,
prefix-cache entries, speculative state and sometimes compiled execution plans---must
be namespaced by the effective-model identity required for correctness. A router may
choose that identity, but once chosen it is request state. An adapter miss is not
permission to run the base model. Recall the linear projections in
Chapter~\ref{app:qkv}: changing a projection changes the hidden state from
which later keys and values are computed. Even an adapter applied outside
the first attention projection can therefore invalidate later-layer KV.
The namespace must describe the computation that created the state,
not merely the name printed in an API response.
}

\NapkinSection{Napkin math: low rank is cheap until diversity multiplies bytes}

For a linear map with
$W\in\mathbb{R}^{d_{\rm out}\times d_{\rm in}}$, LoRA applies
\begin{equation}
W' = W + sBA,\qquad
A\in\mathbb{R}^{r\times d_{\rm in}},\quad
B\in\mathbb{R}^{d_{\rm out}\times r},
\label{eq:lora-update}
\end{equation}
where $s$ commonly contains $\alpha/r$ \cite{hu2022lora}. One adapted matrix adds
\[
P_{\rm LoRA}=r(d_{\rm in}+d_{\rm out})
\]
parameters. Across matrices/layers, sum the dimensions before multiplying by rank.

For row-vector $x$, evaluation can be written
\[
y=xW^\top+s(xA^\top)B^\top.
\]
The update costs approximately
\[
2r(d_{\rm in}+d_{\rm out})
\]
floating-point operations/token for multiply-add counting, plus launch/indexing costs.

Now consider a decode iteration containing $K$ distinct resident adapters. The base
weights are read once according to the base kernel's reuse pattern, but each distinct
adapter needed by the batch contributes adapter traffic. A first-order byte model is
\[
M_{\rm step}\approx M_{\rm base}+ \sum_{a\in\mathcal A_{\rm step}}M_a.
\]
Thus adapter overhead scales with \emph{distinct adapter diversity}, not simply batch
size. Sixty-four rows using one adapter are a different memory problem from sixty-four
rows using sixty-four adapters.

\section{Derive the update before optimizing it}

Take $d_{\rm in}=4$, $d_{\rm out}=3$, rank $r=2$:
\[
A=\begin{bmatrix}1&0&1&0\\0&1&0&1\end{bmatrix},\quad
B=\begin{bmatrix}1&0\\0&2\\1&-1\end{bmatrix}.
\]
For $x=[1,2,3,4]$, the low-dimensional activation is
\[
h=xA^\top=[4,6].
\]
Then
\[
hB^\top=[4,12,-2].
\]
With $s=1/2$, the adapter contributes $[2,6,-1]$ to the shared base result $xW^\top$.
The important intermediate has width $r$, not model width. Every multi-LoRA kernel is
an optimized way of performing these thin projections for rows that select different
$(A,B,s)$.

\section{Merged weights are the single-adapter baseline}

If every request uses the same immutable adapter, compute
\[
W_a=W+sB_aA_a
\]
once and run the ordinary dense kernel. This removes per-token LoRA operations and is
an important baseline.

But materializing $W_a$ for every tenant duplicates the base-sized matrix and destroys
the memory advantage. It also creates a model-switching problem when demand moves
between adapters. Dynamic serving therefore keeps $W$ shared and evaluates the update
at runtime.

A correct benchmark compares dynamic multi-LoRA not only with ``base model'' but with
merged single-adapter execution, split-by-adapter batches, and the realistic cost of
maintaining many merged copies.

\section{Mixed-adapter batching}

For batch row $i$ with adapter identity $a_i$,
\begin{equation}
y_i=x_iW^\top+s_{a_i}(x_iA_{a_i}^\top)B_{a_i}^\top.
\label{eq:mixed-lora}
\end{equation}
The first term is shared across the entire batch. The second must select the factors
belonging to that row.

The naive implementation partitions rows by adapter, launches one LoRA computation
per group, and scatters results back. It is numerically sound but launch-heavy and
inefficient when many adapters have only one or two rows.

Punica introduced segmented gather matrix-vector multiplication (SGMV): row segments
carry adapter indices so one specialized kernel can gather the corresponding LoRA
weights and evaluate heterogeneous updates. Its authors reported 12$\times$ higher
multi-LoRA throughput than their compared serving systems while adding about 2 ms/token
in their evaluated setting. \cite{chen2024punica}

S-LoRA extends the serving problem to thousands of adapters, heterogeneous ranks,
custom kernels and unified paging. Its authors report up to 4$\times$ throughput over
their compared baselines and orders-of-magnitude more served adapters. These are
authors' system measurements, not generic LoRA speedups. \cite{sheng2024slora}

\section{Metadata is part of the kernel interface}

A mixed kernel needs more than tensors. For each row/token it needs an adapter slot or
index, rank/offset metadata, scale, and the locations of $A$ and $B$. Variable-rank
adapters need either padding to a maximum rank or rank-aware offsets/groups.

The scheduler and model runner therefore share a contract:
\[
\text{row}\rightarrow
(\text{request},\text{adapter slot},r,s,A\text{ offset},B\text{ offset}).
\]
If compaction changes batch-row order, this mapping must be compacted identically.
An off-by-one adapter index produces a plausible tensor with the wrong effective
model---a correctness failure more dangerous than a crash.

\section{Adapter identity is a versioned content identity}

Names such as \texttt{customer-42} are not enough. An adapter can be updated while
requests using its previous version remain active. Define an immutable identity such
as
\[
I_a=H(\text{base fingerprint},\text{adapter content/version},
      \text{composition},\text{scale},\text{target modules}).
\]
The exact hash format is implementation-specific; the invariant is that two identities
compare equal only when their model semantics are safe to share.

A runtime update publishes a new identity. Existing requests keep leases on the old
resident object until retirement. Reusing the same slot number for new bytes requires
a generation/version check, just like paged KV physical blocks.

\section{KV caches inherit effective-model identity}

Attention KV at layer $\ell$ is produced by projections whose weights may be adapted.
Even when only non-attention modules are adapted, later hidden states can differ and
therefore future KV differs. The conservative correctness rule is simple:
\[
K_{\rm prefix}=
H(I_{\rm effective\ model},\text{token prefix},\text{position/config namespace}).
\]

Two requests with identical prompt tokens but different LoRA identities must not share
KV unless an engine proves that the particular adapter composition cannot affect the
cached values. General-purpose serving should namespace first and specialize only with
a proof.

This extends Chapter~\ref{ch:prefix-caching}: adapter identity belongs in the prefix
cache key. It also extends Chapter~\ref{ch:paged-kv}: shared physical blocks retain
their effective-model namespace until every reference retires.

\section{The adapter residency hierarchy}

A practical server has at least three adapter states:
\[
\textsc{Catalogued}\rightarrow\textsc{HostResident}\rightarrow\textsc{DeviceResident}.
\]
The catalog records immutable identity and storage location. Host residency avoids
disk/object-store fetch. Device residency is required by the execution kernel.

If adapter size is $M_a$ and effective host-to-device bandwidth is $\beta$, a simple
load lower bound is
\[
T_{\rm load}\gtrsim M_a/\beta+T_{\rm setup}.
\]
The transfer can overlap other work, but a request whose adapter is absent cannot
execute correctly until residency is established.

S-LoRA explicitly stores many adapters in main memory and fetches currently needed
ones to GPU memory. Its unified paging design manages adapter weights and KV state
within a common memory-management framework to reduce fragmentation. \cite{sheng2024slora}

\section{A residency slot needs a lease}

Suppose device slot 7 contains adapter A. Request $r$ is admitted and records
``slot 7.'' While it waits, the residency manager evicts A and loads B into slot 7.
If execution trusts only the integer slot, $r$ silently runs the wrong model.

Use a handle
\[
h=(\text{slot},\text{generation},I_a).
\]
Execution validates the generation/identity, and active/in-flight kernels pin the
resident object. Eviction may choose only unpinned entries. This is the same ABA
problem already encountered in KV allocation.

\section{LRU is a baseline, not a complete policy}

Least-recently-used adapter eviction is simple, but adapter demand has burst structure.
A large adapter used by one low-priority request can evict several small hot adapters.
A router may know that twenty queued requests need an adapter that is currently cold.
An SLO-aware residency score can consider:
\[
R_a=f(\text{queued demand},\text{recent demand},M_a,T_{\rm reload},
      \text{priority},\text{pin count}).
\]
Do not overfit an opaque score before measuring workload reuse. The durable requirement
is to expose load bytes, miss latency, queue demand and eviction reason.

\section{Admission now has two resources}

Chapter~\ref{ch:scheduling} admitted against KV and latency budgets. Multi-adapter
serving adds adapter residency. A request can fit KV but require an adapter load that
would violate TTFT, or it can force eviction of adapters needed by incumbents.

Admission can therefore estimate:
\[
M_{\rm KV}+M_{\rm adapter}\le M_{\rm device\ budget}
\]
and
\[
\widehat{\mathrm{TTFT}}=
T_{\rm queue}+T_{\rm adapter\ miss}+T_{\rm prefill}.
\]
Batching policy may also cap the number of distinct adapters in one step because
adapter bandwidth and kernel metadata grow with diversity.

\section{Fairness across hot and cold adapters}

A locality-only scheduler repeatedly chooses requests whose adapters are resident.
That improves throughput but can starve a tenant with a cold adapter. Conversely,
strict FIFO can thrash residency by alternating adapters every request.

Compose objectives: choose an eligible tenant/priority class using fairness and SLO
rules, then use adapter locality as a bounded tie-breaker. Charge adapter-load cost to
the request or tenant that causes it if that matches the service model. Keep queue age
monotone across residency waits.

This mirrors prefix-cache-aware scheduling: locality is valuable but should not become
an unbounded starvation mechanism.

\section{Routing is a decision before execution identity freezes}

A model router chooses among base models/adapters based on quality, latency, cost,
capability, policy or user selection. RouteLLM demonstrated learned routing between
stronger and weaker models using preference data, reporting substantial cost savings
at comparable quality in evaluated settings. \cite{ong2024routellm}

At the engine boundary, routing should produce an immutable execution plan:
\[
P_r=(I_{\rm base},I_{\rm adapter},\text{backend},\text{sampling/policy namespace}).
\]
Changing that plan after prefill invalidates model-derived state unless the runtime
explicitly restarts/recomputes it. A router is not allowed to ``fall back'' to another
model mid-stream merely because an adapter was evicted.

\section{Routing has locality and quality externalities}

Assume replicas A and B both serve the same base model, but only A holds the requested
adapter and a warm prompt prefix. Sending the request to B may balance queue length
while paying both adapter load and prefill. A good fleet router estimates total
completion cost:
\[
C_j=w_q Q_j+w_a A_j+w_p P_j+w_n N_j,
\]
where $Q_j$ is queue delay, $A_j$ adapter-miss cost, $P_j$ prefix-miss cost and $N_j$
network/transfer cost. This equation is illustrative; coefficients are workload/SLO
policy.

The router should consume cache/residency summaries with bounded staleness. Perfect
global state is expensive, and stale ``adapter present'' metadata can route a request
to a replica that has already evicted it.

\section{Whole-base-model multiplexing}

Adapters are the favorable case because the differing state is small. When requests
select different base checkpoints, sharing disappears for the base weights.

The edition's M1 Ollama measurement answered a warm eight-token request in about
0.28 seconds. Alternating between two roughly 3B models caused approximately
1.6--2.3 seconds of model loading and 2.2--3.0 seconds total/request in the recorded
runs. These are local measurements with likely OS page-cache effects, not storage
hardware limits.

ServerlessLLM attacks the same cold-start problem at data-center scale with checkpoint
layout/loading, live migration and locality-aware scheduling; its authors report
10--200$\times$ lower latency than their compared serverless baselines. \cite{fu2024serverlessllm}
The common principle is to place requests where their expensive immutable state is
already resident, unless queue/SLO pressure outweighs locality.

\section{Adapter composition complicates identity}

Some applications combine multiple adapters:
\[
W'=W+\sum_{j=1}^{k}s_jB_jA_j.
\]
The effective identity must include the ordered/canonicalized composition and scales.
Kernel cost now depends on the total active ranks and whether factors can be fused or
compressed. Cache reuse between composition $\{A,B\}$ and $\{A,C\}$ is not generally
safe merely because one component matches.

Joint-compression research explores shared bases across large adapter collections.
Compress-then-Serve, for example, learns shared structure among adapters and reports
maintaining about 80\% of single-LoRA throughput in experiments with more than a
thousand adapters. \cite{bruelgabrielsson2024compress}
This is a different trade: additional approximation/training complexity buys residency
and bandwidth reduction.

\section{Tensor parallelism changes where LoRA runs}

When $W$ is tensor-parallel sharded, $A$ and $B$ must align with the base projection's
partition or introduce communication. Depending on whether the input or output
dimension is sharded, one LoRA factor can be replicated while another is partitioned.

S-LoRA includes a tensor-parallel strategy for heterogeneous LoRA serving. Production
engines similarly expose choices about fully sharding LoRA computation. Exact
collective patterns depend on the base layer partition and kernel implementation;
there is no universal ``LoRA adds no communication'' rule.

\section{Quantized bases do not make LoRA free}

A quantized base can be far smaller than BF16 while adapters remain FP16/BF16. Then
the adapter/base byte ratio rises. The low-rank arithmetic may also require conversion
or different kernels. A rank that was negligible beside a 16-bit base can become a
visible bandwidth fraction beside a 4-bit base.

Therefore report adapter overhead against the actual deployed base representation,
not parameter count alone. The opening's roughly 2.01-GB quantized base makes this
especially relevant.

\section{Hot loading is a publication protocol}

Runtime adapter loading has a security and correctness boundary:
\begin{enumerate}
\item fetch bytes into non-visible staging storage;
\item authenticate/authorize source and request;
\item validate format, shapes, target modules and base compatibility;
\item compute immutable content identity;
\item transfer/prepare device representation;
\item atomically publish the new catalog/residency entry;
\item only then admit requests that reference it.
\end{enumerate}
A partially loaded adapter must never become selectable. Unload marks the identity
unavailable for new leases but waits for active pins before physical destruction.

\section{Observability must name the effective model}

At minimum record base identity, adapter identity/version, adapter rank, residency
hit/miss, load latency, distinct adapters per batch, LoRA kernel time, bytes loaded,
eviction reason, KV/prefix namespace and route decision.

Aggregating metrics only by base model hides the entire phenomenon. A server can show
healthy base-model throughput while one tenant's cold adapter repeatedly misses and
violates TTFT.

Cardinality is a concern: thousands of adapter IDs should not automatically become
unbounded metrics labels. Keep detailed IDs in traces/logs and aggregate metrics into
bounded dimensions such as rank bucket, residency status or tenant class.

\section{Failure tests}

Test two identical prompts under different zero/nonzero adapters and prove their KV
namespaces differ. Test an adapter slot evicted and reused before an old request
executes; generation validation must reject the stale handle. Test two adapter versions
with the same display name. Test a missing adapter and prove the engine errors/queues
rather than serving base output. Test cancellation while an adapter transfer is in
flight and ensure publication/pins retire correctly.

For mixed kernels, compare every row with an independent merged-weight oracle. Include
different ranks, repeated adapter IDs, base-only rows, permuted row order and an
adapter whose update is exactly zero. Numerical parity should be defined with a
tolerance appropriate to the accumulation precision.

\LedgerSection
\begin{ConstraintLedger}
Memory capacity & buys & One shared base plus small adapters replaces many full fine-tuned checkpoints; host/device residency extends the working set.\\
Memory bandwidth & spends & Each distinct adapter used by a step contributes factor traffic; quantized bases make the relative adapter traffic larger.\\
Compute & spends & Two thin projections and accumulation per adapted matrix, plus segmentation/indexing/launch overhead.\\
Latency & trades & Resident mixed-adapter kernels preserve batching; misses add transfer/cold-start delay and poor locality can thrash.\\
Correctness & risks & Wrong adapter row mapping, stale residency slots, unsafe KV reuse, version aliasing and silent base fallback change model semantics.\\
Cost & buys & High tenant density shares expensive base weights and GPUs; routing can trade quality against inference cost.\\
\end{ConstraintLedger}

\LabSection{mixed LoRA execution plus residency correctness}

The Rust lab in \texttt{code/labs/ch21-multi-lora/} uses small deterministic matrices.
It computes each row three ways: (1) explicitly merged $W+sBA$, (2) shared base plus a
per-row adapter update, and (3) a segmented mixed-adapter path. A separately written
dense oracle materializes merged weights and checks numerical parity.

A second fixture models two device adapter slots with generation-checked handles.
Loading a new adapter into a reclaimed slot increments its generation; an old request
holding the previous handle is rejected rather than silently executing the replacement.

The lab is a correctness/representation lesson, not a performance claim about Punica,
S-LoRA, vLLM or SGLang.

\HappenedSection{multi-LoRA became a first-class serving mode}

Punica showed that heterogeneous adapters need a heterogeneous kernel rather than
separate base-model replicas. S-LoRA added a large adapter working set, unified paging,
heterogeneous ranks and distributed execution. Modern engines expose LoRA capacity,
rank and runtime-loading controls.

Source inspection for this edition found vLLM LoRA configuration at commit
\texttt{155488d853a0bc42df227dbfc74005b3fd488e94}, including explicit limits around
resident LoRAs and rank. SGLang commit
\texttt{7a719e9a65e7f52b012ab37211b5f174e5d3d38d} has a dedicated LoRA argument and
runtime subsystem. These are source-pinned implementation observations, not claims that
all deployments use identical defaults.

The architectural shift is larger than a feature flag: adapter identity now crosses
API routing, scheduler metadata, model kernels, memory residency and cache keys.

\FrontierSection{2026-10-05}

Punica and S-LoRA remain foundational designs for heterogeneous multi-adapter kernels
and residency. Current engine source shows multi-LoRA as a normal serving concern
rather than a research-only wrapper. Research is pushing beyond independent adapters:
joint compression can share structure among many LoRAs; routing research treats model
choice as a quality/cost allocation problem; and fleet schedulers increasingly need to
co-optimize queue locality, prefix locality and adapter locality.

The unresolved systems question is composability. An industrial runtime should support
adapter versions, compositions, quantized bases, tensor parallelism and hot loading
without multiplying bespoke cache/scheduler paths. The strongest design is an explicit
effective-model identity plus generic leases, namespaces and cost signals reused by
the rest of the engine.

\ExercisesSection
\begin{enumerate}
\item \emph{Derivation.} For $d_{\rm in}=4096$, $d_{\rm out}=4096$, rank 16 and FP16
factors, compute LoRA parameters, bytes and multiply-add FLOPs/token for one matrix.
\item \emph{Trace.} A two-slot device cache contains A@gen4 and B@gen9. Request $r$
holds A@gen4. A retires, C loads into the same physical slot at gen5, then $r$ reaches
execution. State the required result and why checking only slot number is unsafe.
\item \emph{Batching.} Compare adapter bytes for 64 rows using one 48.6-MB adapter
versus 64 distinct adapters, assuming each distinct adapter's factors must be streamed
once. What assumption makes this an upper-level bandwidth model rather than a kernel
measurement?
\item \emph{Implementation.} Extend the lab to heterogeneous ranks. Acceptance:
merged-oracle parity for every row; no padding assumption leaks into semantics; stale
slot handles fail; base-only rows remain unchanged.
\item \emph{Caching.} Explain why identical tokens under two different adapters should
normally produce different prefix-cache keys even if both adapters leave the first
layer's K/V projections untouched.
\item \emph{Falsification.} Construct a workload where splitting by adapter is faster
than a heterogeneous gather kernel. Include group size, adapter diversity and launch/
memory assumptions that make the result plausible.
\end{enumerate}
