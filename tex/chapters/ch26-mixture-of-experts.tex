\chapter{Mixture of Experts}\label{ch:mixture-of-experts}

\begin{ChapterIntent}
A mixture-of-experts (MoE) layer stores many feed-forward networks but routes each token
through only a few. That separates three quantities a dense model largely couples:
total parameters determine capacity, active parameters determine arithmetic per token,
and the union of experts selected by a serving batch determines much of decode weight
traffic. This chapter derives that split, follows token--expert pairs through
route--dispatch--grouped GEMM--combine, explains load imbalance and dropless execution,
and connects local grouped kernels to distributed expert parallelism.
\end{ChapterIntent}

\OpeningSection{Sparse arithmetic, dense residency}

The book's Apple M1 measurement isolates the expert matrix product at the shape used by
Qwen3-30B-A3B: 128 experts, 8 selected per token, with one projection shaped
$2048\times768$. With Q4\_K weights, one token took about 102.6 microseconds per
benchmark call. Eight tokens took about 919.6 microseconds. At 32 tokens the call took
about 6.25 milliseconds; at 64 about 7.06 milliseconds; at 256 about 7.32 milliseconds.
Per-token time therefore first worsened and then collapsed to about 28.6 microseconds
at 256 tokens (\texttt{research/measurements/2026-09-24-m1-part5.md}).

The curve is not mysterious. Under the benchmark's uniformly random routing, one token
selects 8 experts, eight tokens select about 52 distinct experts in expectation, 32
select about 112, and 64 about 126 of 128. At small batch the Metal backend performs
matrix--vector-like work per selected pair. At larger batch it groups rows by expert,
turning repeated reads into matrix--matrix reuse.

This is the systems problem of MoE in one experiment:
\[
\boxed{\text{sparse per token}\neq\text{sparse per batch}\neq\text{small model}.}
\]

\Foundations{Three parameter counts, not one}{
Let $P$ be all parameters, $P_{\rm act}$ the parameters executed for one token, and
$P_{\rm union}(B)$ the expert parameters whose weights a batch of $B$ tokens must touch.
Memory capacity pays approximately for $P$. Arithmetic pays for $P_{\rm act}$ per token.
Decode weight traffic depends on $P_{\rm union}(B)$ and on how effectively the engine
reuses each expert's weights across its assigned tokens. The feed-forward
lesson in Chapter~\ref{ch:matmul-hardware} explains how more rows can amortize a
matrix's weight reads. A routed layer splits those rows among several
matrices: the batch size seen by one expert can be tiny even when the
server's total batch is large. Distinguish model storage, executed
arithmetic and observed memory traffic before applying a roofline estimate.
}

\NapkinSection{Napkin math: how quickly a batch activates the model}

Suppose a layer has $E$ routed experts and each token chooses $k$ distinct experts.
Under an illustrative independent/uniform approximation, a particular expert is not
chosen by one token with probability $1-k/E$. It escapes all $B$ tokens with
probability
\[
\left(1-\frac{k}{E}\right)^B.
\]
By linearity of expectation, the expected number of distinct experts used is
\begin{equation}
\mathbb{E}[U(B)]
=E\left[1-\left(1-\frac{k}{E}\right)^B\right].
\label{eq:ch43-union}
\end{equation}

For $E=128,k=8$:
\[
U(1)=8,\quad U(8)\approx51.6,\quad U(32)\approx111.8,\quad
U(64)\approx125.9.
\]
The last number means a 64-token step can execute only 8/128 experts per token while
collectively touching almost every expert.

If one expert projection occupies $M_e$ bytes and grouping lets its weights be loaded
approximately once per step, an idealized expert-weight traffic bound is
\[
D_{\rm expert}(B)\approx U(B)M_e.
\]
Per token,
\[
\frac{D_{\rm expert}(B)}{B}\approx\frac{U(B)}{B}M_e.
\]
This is why batching eventually amortizes MoE weight traffic even though the union
itself becomes dense.

\section{The sparse feed-forward layer}

A dense transformer FFN computes a fixed function for every token. An MoE layer instead
has experts $f_0,\ldots,f_{E-1}$ and a router. For hidden vector
$h\in\mathbb{R}^{d}$, a simple router produces
\[
r=W_rh\in\mathbb{R}^{E}.
\]
Let $\mathcal{T}(h)$ be the top-$k$ expert indices and $g_i(h)$ their normalized gate
weights. The layer output is
\begin{equation}
y(h)=\sum_{i\in\mathcal{T}(h)}g_i(h)f_i(h).
\label{eq:ch43-moe}
\end{equation}

The router therefore produces both \emph{control}---which experts execute---and
\emph{data}---the weights used to combine their outputs. Losing either changes the
model.

\section{One token becomes several execution rows}

With top-$k>1$, a logical token is copied into $k$ expert work items:
\[
(t,h_t)\longrightarrow
\{(t,e_1,g_1,h_t),\ldots,(t,e_k,g_k,h_t)\}.
\]
These are not new sequence tokens. They are temporary rows carrying the same token
identity.

A production execution pipeline is therefore:

\begin{enumerate}
\item compute router scores;
\item select top-$k$ experts and gate weights;
\item materialize token--expert assignments;
\item group assignments by expert;
\item execute each expert over its group;
\item scatter results back to token identity;
\item multiply by gates and reduce the $k$ contributions.
\end{enumerate}

The inverse mapping from grouped row to original token is a correctness object, not
bookkeeping.

\section{Total parameters and active parameters answer different questions}

Let the non-expert portion contain $P_s$ shared parameters. Let every routed expert
contain $P_e$ parameters. Then
\[
P=P_s+EP_e,
\qquad
P_{\rm act}=P_s+kP_e.
\]
The active fraction is
\[
\rho=\frac{P_{\rm act}}{P}.
\]

The arithmetic of one token can resemble a much smaller dense model when $\rho\ll1$,
but all $EP_e$ expert parameters must be resident somewhere or fetched from another
tier. ``30B total, 3B active'' therefore means neither ``a 3B model'' nor ``30B of
compute per token.''

\section{The union is the missing third quantity}

For a batch, define
\[
P_{\rm union}(B)=P_s+U(B)P_e.
\]
This is the first-order amount of parameter state that can participate in the step.
At batch one, $U=k$. As $B$ grows, $U\to E$.

Thus:
\[
P_{\rm act}\le P_{\rm union}(B)\le P.
\]
The left quantity drives arithmetic per token; the middle drives batch weight locality;
the right drives storage.

This three-number model is more useful for inference than quoting only total/active
parameters.

\subsection{Why the compute knee can arrive late}

Suppose the expert union has saturated, each parameter is read once per
step in a format costing $b_w$ bytes, and matrix arithmetic dominates the
FLOPs. The approximate arithmetic intensity is
$I(B)=2BP_{\rm act}/(Pb_w)$. Solving $I(B^*)=I^*$ for a machine's
ridge intensity gives
\begin{equation}
B^*\approx\frac{I^*b_w}{2}\frac{P}{P_{\rm act}}.
\label{eq:moe-ridge-batch}
\end{equation}
The dense-model term is multiplied by the total-to-active parameter ratio.
Illustratively, a ridge of 600 FLOP/byte, one-byte weights and a ratio of
nine imply a knee near 2,700 token rows, not 300. These are derived inputs,
not a device benchmark. The estimate assumes saturated expert coverage and
efficient grouped products; before saturation use $P_{\rm union}(B)$
instead of $P$. KV traffic, routing, quantization metadata, dispatch and
interconnect costs can move the actual bottleneck. A model need not reach
this knee to serve requests usefully. The equation explains why larger
expert-parallel groups seek more rows per expert, not why every deployment
should maximize batch size.

\section{Uniform routing is an oracle, not a deployment assumption}

Equation~\eqref{eq:ch43-union} assumes independent uniform selections. Real routers are
correlated with token content, layers, languages, domains and training-induced expert
specialization. Some experts become hot.

That can \emph{reduce} the union and improve cache locality, but it creates load
imbalance. A skewed router can therefore improve bytes while worsening the critical
path. Systems work must measure both:
\[
\text{expert diversity}
\quad\text{and}\quad
\text{maximum expert load}.
\]

\section{A second napkin model: expert occupancy}

Let $n_e$ be the number of token--expert rows assigned to expert $e$ in a step. Then
\[
\sum_{e=0}^{E-1}n_e=Bk.
\]
Average occupancy among active experts is
\[
\bar n=\frac{Bk}{U}.
\]
For $B=64,k=8,U\approx126$, only about 4.1 rows land on each active expert on average.
That is a tiny GEMM.

MoE therefore creates an awkward kernel regime: the batch is large globally while each
expert sees a small local matrix.

\section{Why the naive loop wastes batching}

The simplest implementation is:

\begin{verbatim}
for token:
    for selected expert:
        expert(token)
\end{verbatim}

This creates $Bk$ matrix--vector operations. If two tokens select the same expert, its
weights may be streamed twice instead of reused.

A grouped implementation instead sorts or bins assignments by expert:
\[
[e_7,e_2,e_7,e_2,e_2]
\longrightarrow
[e_2,e_2,e_2,e_7,e_7].
\]
Expert 2 then processes three rows together and expert 7 two. The mathematical output
is unchanged; the physical execution layout is transformed.

\section{Grouped GEMM is a sparse-model batching primitive}

A conventional dense GEMM has one matrix shape. MoE needs a family of GEMMs:
\[
Y_e=X_eW_e,\qquad e\in\mathcal{U},
\]
where $X_e$ can have a different row count $n_e$ for every expert.

A grouped-GEMM kernel launches these heterogeneous products efficiently. Implementations
may pad row counts to tile boundaries, maintain offsets into packed rows, or use masked
layouts under graph capture.

The optimization target is not merely FLOPs. It is:
\[
\text{useful rows per expert tile}
\times
\text{weight reuse}
\times
\text{launch/dispatch efficiency}.
\]

\section{The M1 measurement crosses execution regimes}

The historical llama.cpp benchmark is valuable because it exposes a backend transition.
Below the larger-batch path, time roughly scales with token--expert work. From 32 rows,
the Metal implementation groups tokens by expert and uses matrix--matrix execution.

For F16 experts, the grouped path approached the bandwidth implied by reading the
expert union once. Q4\_K behaved differently: at high batch, dequantization and
matrix-matrix arithmetic made the 4-bit path cease to look like a simple
``quarter the bytes, therefore quarter the time'' optimization.

Quantization can move a kernel from bandwidth-bound toward compute-bound.

\section{Router cost is small; router consequences are not}

A router matrix is often tiny compared with expert matrices. Its direct FLOPs are
usually not the serving bottleneck.

But its output determines:
\begin{itemize}
\item which weights must be read;
\item how many rows each expert receives;
\item which device receives each token under expert parallelism;
\item whether one expert becomes a straggler;
\item which experts are worth caching or replicating.
\end{itemize}

The router is therefore a low-cost computation with high-cost scheduling consequences.

\section{Top-$k$ selection and numerical determinism}

Routing is sensitive to close scores. If experts near the $k$th boundary exchange order
because of numerical differences, a token executes different parameters. This can
amplify into different generated tokens.

A reproducibility contract must specify, where relevant:
\[
\text{router precision}+
\text{top-$k$ tie behavior}+
\text{gate normalization}+
\text{expert implementation}.
\]
A deterministic dense GEMM does not guarantee deterministic MoE routing.

\section{Capacity factors and token dropping}

Training systems historically bounded expert work with a capacity such as
\[
C=\left\lceil
\gamma\frac{Bk}{E}
\right\rceil,
\]
where $\gamma$ is a capacity factor. If expert $e$ receives more than $C$ rows, some
system must pad, reroute, or drop overflow.

Dropping is particularly dangerous at serving time: then one request's output can
depend on unrelated batch-mates because they consumed expert capacity first.

A dropless inference engine instead executes all selected assignments. The price of
imbalance becomes latency or communication, not silent semantic change.

\section{Load imbalance turns into a straggler}

If expert computations execute in parallel, step time is controlled by something close
to
\[
T_{\rm experts}\approx
\max_e T_e(n_e)
+\text{dispatch/combine overhead},
\]
not the average $T_e$.

Two batches with the same $U$ and $Bk$ can therefore have very different latency. One
may distribute four rows to each active expert; another may send hundreds to one hot
expert.

Useful observability needs a histogram, maximum, coefficient of variation or similar
load statistic---not merely ``128 experts active.''

\section{Shared experts change the arithmetic}

Some architectures add experts that every token executes. Let $P_{\rm shared}$ denote
their parameters. Then
\[
P_{\rm act}=P_{\rm nonexpert}+P_{\rm shared}+kP_e.
\]
Shared experts behave like a dense sublayer: they batch naturally, are always hot and
are natural replication candidates in distributed deployments.

Do not include shared experts in the routed-union equation as if they were sampled.
They are always in the union.

\section{Fine-grained experts improve specialization but shrink GEMMs}

Splitting one large expert into many smaller experts can increase combinatorial
specialization. For the engine, however, smaller experts and larger $E$ mean more
routing metadata, more groups and often less work per GEMM.

There is therefore an architecture--kernel co-design trade:
\[
\text{finer specialization}
\leftrightarrow
\text{smaller, more fragmented execution groups}.
\]

This is one reason modern MoE serving invests heavily in specialized grouped kernels
rather than treating experts as ordinary dense FFNs in a loop.

\section{Weight quantization changes both capacity and kernel balance}

Suppose expert weights use $b_w$ bytes/parameter. Total expert residency is
approximately
\[
M_{\rm experts}=EP_eb_w.
\]
Reducing $b_w$ makes very large MoE models deployable on fewer devices.

But packed low-bit weights must be decoded or consumed by specialized tensor-core
formats. At batch one the saved bytes can dominate. At higher occupancy, dequantization
and matrix arithmetic can dominate. The M1 Q4\_K/F16 crossover in the historical
kernel experiment is a concrete warning against predicting latency from file size
alone.

\section{Expert locality is a cache problem}

If all experts cannot remain in fast memory, the engine may maintain a hot set. Let
$p_e$ be the probability that a future assignment needs expert $e$. An ideal cache
would retain high-value experts, but real routing is sequence-, layer- and
domain-dependent.

The serving problem resembles a weighted object cache with unusually expensive misses:
an expert can be megabytes or more, and the miss lies directly on token latency unless
prefetched.

This leads to expert streaming and offloading later in the book.

\section{Prefetching needs prediction before the layer}

Ordinary paging discovers a missing object when it is referenced. Expert paging is more
interesting because the router reveals the next objects just before expert execution.

An engine can overlap:
\[
\text{router at layer }\ell
\rightarrow
\text{fetch experts for }\ell
\]
with other work only if there is sufficient lookahead or predictive routing. Otherwise
storage latency sits on the critical path.

Pre-gating and predictive schemes are therefore algorithm--systems co-design, not
merely I/O optimization.

\section{From grouped GEMM to expert parallelism}

On one device, dispatch means rearranging rows in memory. Across devices, the same
logical operation becomes communication.

If device $d(e)$ owns expert $e$, a token routed to $e$ must send its hidden row to
$d(e)$, execute there, then return the expert result for combine. Conceptually:
\[
\text{route}
\rightarrow
\text{all-to-all dispatch}
\rightarrow
\text{local grouped GEMM}
\rightarrow
\text{all-to-all return}
\rightarrow
\text{combine}.
\]

The local chapter therefore supplies the semantics for the later distributed chapter.
The network does not change what dispatch means; it makes the permutation expensive.

\section{Communication volume}

If hidden width is $d$ and activation elements occupy $b_a$ bytes, sending one copy of
every top-$k$ assignment naively costs on the order of
\[
Bk d b_a
\]
bytes in each dispatch direction, before protocol/alignment overhead.

Whether implementations can avoid duplicate sends when several experts for one token
share a destination depends on placement and kernel design. The formula is therefore a
conservative conceptual budget, not a universal wire count.

At scale, MoE shifts pressure from HBM bandwidth to fabric bandwidth and topology.

\section{Placement is part of scheduling}

Expert placement answers which device stores each $W_e$. Static round-robin placement
is simple but ignores routing skew. Replicating hot experts can reduce network traffic
and stragglers at the cost of capacity.

A placement controller therefore trades:
\[
\text{memory replication}
\quad\text{for}\quad
\text{communication and load balance}.
\]

Because routing statistics change with workload, dynamic placement can be useful, but
moving a large expert is itself expensive. Control loops must operate at a slower
timescale than token scheduling.

\section{Continuous batching changes the router population}

A continuous-batching engine forms each step from requests at different sequence
positions and possibly different domains. That changes the distribution of router
inputs compared with a static batch.

Consequently, expert union and imbalance are properties of the \emph{scheduler's
cohort}, not only the model. A scheduler that groups similar requests may improve
prefix locality yet worsen expert hotspots; a diverse cohort may activate more experts
but balance rows better.

MoE introduces another coupling between request scheduling and kernel efficiency.

\section{Chunked prefill versus decode}

Prefill supplies many token rows and can produce healthy expert GEMMs, but it may
activate a broad expert union. Decode supplies few rows per sequence and often tiny
per-expert groups.

When chunked prefill and decode share a step, their assignments can be grouped together.
This can improve expert occupancy, but only if latency-sensitive decode rows are not
delayed behind a huge prefill expert group.

The scheduler's token budget is therefore also an MoE kernel-shape budget.

\section{Speculative decoding can improve expert occupancy---or waste it}

Verification of several draft tokens gives the target model multiple token rows per
sequence. For MoE, that can enlarge per-step expert groups and improve weight reuse.

But rejected speculative tokens still paid router and expert work. A useful cost model
must count:
\[
\text{accepted target tokens}
\quad\text{per}\quad
\text{expert bytes/FLOPs executed}.
\]
Acceptance rate and expert-union overlap jointly determine the benefit.

\section{Correctness invariants for dispatch and combine}

For every logical token $t$:
\begin{enumerate}
\item exactly its selected experts execute;
\item each selected expert sees the correct hidden vector;
\item its gate remains paired with that expert;
\item every expert result returns to the correct token;
\item the combine reduction contains every selected contribution exactly once;
\item temporary row ordering cannot leak into sequence ordering.
\end{enumerate}

These invariants should be tested with distinct, adversarial expert outputs so a
permutation bug cannot accidentally cancel.

\section{A tiny worked trace}

Take three tokens, four experts and top-2 routing:
\[
t_0:(e_2,.7),(e_0,.3)
\]
\[
t_1:(e_1,.6),(e_2,.4)
\]
\[
t_2:(e_2,.8),(e_3,.2).
\]
The logical assignment order is
\[
[(t_0,e_2),(t_0,e_0),(t_1,e_1),(t_1,e_2),(t_2,e_2),(t_2,e_3)].
\]
Grouped by expert:
\[
e_0:[t_0],\quad
e_1:[t_1],\quad
e_2:[t_0,t_1,t_2],\quad
e_3:[t_2].
\]
The engine must retain enough inverse metadata to reconstruct
\[
y_0=.7f_2(h_0)+.3f_0(h_0)
\]
and similarly for $t_1,t_2$. Sorting rows is legal; forgetting the inverse permutation
is not.

\section{What to measure}

A production MoE dashboard should expose at least:
\begin{itemize}
\item routed assignments per step $Bk$;
\item distinct expert union $U$ per layer;
\item occupancy distribution $n_e$ and maximum load;
\item grouped-GEMM padding/wasted rows;
\item router/top-$k$ time;
\item dispatch and combine time;
\item expert GEMM time by dtype/kernel;
\item expert cache hit/miss and bytes fetched, if offloaded;
\item cross-device bytes and all-to-all time, if distributed;
\item per-layer straggler expert/device.
\end{itemize}

``Active parameters'' alone cannot explain any of these bottlenecks.

\section{Failure tests}

A robust implementation should deliberately test:
\begin{enumerate}
\item two tokens selecting the same experts in opposite order;
\item repeated equal router scores at the top-$k$ boundary;
\item one expert receiving every token;
\item every expert receiving at least one token;
\item an expert receiving zero rows;
\item non-contiguous token IDs after continuous-batch compaction;
\item top-$k$ gates accidentally sorted independently of expert IDs;
\item capacity overflow in a mode that promises dropless inference;
\item expert hot-swap/version change while rows are in flight;
\item distributed return rows arriving in a different order than dispatch.
\end{enumerate}

\LedgerSection
\begin{ConstraintLedger}
Compute & buys & Each token executes only $k$ routed experts rather than all $E$; arithmetic follows active parameters.\\
Memory capacity & spends & All experts must be resident somewhere or supplied from slower tiers; capacity follows total parameters.\\
Memory bandwidth & trades & Batch-one reads only selected experts, but the expert union rapidly approaches all experts; grouped GEMM is required to amortize those reads.\\
Latency & risks & Router skew, tiny per-expert groups, expert misses and distributed stragglers lengthen the critical path.\\
Correctness & requires & Dispatch must preserve token/expert/gate identity and combine every selected contribution exactly once; serving should not silently drop overflow tokens.\\
Cost & trades & Sparse compute enables much larger parameter capacity at a given FLOP/token budget, while demanding more HBM capacity, specialized kernels and often more devices/network.\\
\end{ConstraintLedger}

\LabSection{route, group, execute, combine}

The Rust lab in \texttt{code/labs/ch26-mixture-of-experts/} implements a deterministic
tiny MoE layer in two independent ways. The reference path loops token-by-token through
its assignments. The grouped path packs assignments by expert, executes each expert
over its group, and combines through explicit token IDs.

It also computes the uniform-routing union expectation, reports expert occupancy and
contains adversarial tests for a wrong inverse permutation and a gate/expert mismatch.
The lab intentionally uses scalar affine experts so the routing machinery is visible;
it is not a performance benchmark.

\HappenedSection{the expert union predicts the kernel's opportunity}

The M1 measurement provides a useful causal chain rather than a leaderboard number.
As batch grows, the expected expert union approaches all 128 experts. The backend then
switches from repeated small products to grouped execution, after which more tokens
reuse already-touched expert weights.

The experiment also falsifies a simplistic quantization prediction: Q4\_K does not
remain proportionally faster than F16 at large grouped batches. Once reuse increases,
dequantization/arithmetic become more important than raw packed bytes.

That is exactly why an inference-engine book needs both model sparsity and kernel
mechanics.

\FrontierSection{2026-10-05}

MoE inference is increasingly an end-to-end systems problem: fine-grained experts make
the matrices smaller; grouped kernels recover local efficiency; expert parallelism
turns dispatch into all-to-all communication; hot-expert replication trades memory for
balance; low-bit expert formats trade bandwidth for decode arithmetic; and expert
streaming introduces another memory hierarchy.

The durable abstraction is not ``call expert FFNs.'' It is:
\[
\boxed{\begin{gathered}
\text{route}\rightarrow\text{materialize assignments}\rightarrow\text{place/dispatch}\\
\rightarrow\text{grouped execution}\rightarrow\text{return/combine}.
\end{gathered}}
\]
The next chapters can optimize individual arrows without changing this logical
contract.
