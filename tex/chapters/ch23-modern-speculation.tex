\chapter{Modern Speculation: The EAGLE Family, Medusa and Multi-Token Prediction}\label{ch:modern-speculation}

\begin{ChapterIntent}
Chapter~\ref{ch:speculative-decoding} established the invariant: proposals are tentative,
the target is authoritative, and only a verified contiguous history commits. Modern
speculation changes the proposal engine. EAGLE predicts from target features, EAGLE-2
allocates a dynamic tree, EAGLE-3 predicts tokens from fused target features, Medusa
adds future-token heads, and multi-token-prediction modules train future prediction
into the model. This chapter follows those mechanisms into the serving engine: tree
layout, ancestry masks, logical positions, target verification, KV ownership, dynamic
tree budgets and the point where drafting becomes a scheduling problem.
\end{ChapterIntent}

\OpeningSection{A smaller model can be both expensive and wrong}

The book's M1 record paired an 8B target with a 3B drafter. On two measured tasks the
target accepted only 98/208 and 106/231 proposed tokens, roughly 46--47 percent. A
drafter step cost about 0.38 of a target step, and the models used different
vocabularies, requiring token/text translation
(\texttt{research/measurements/2026-09-24-m1-part4.md}). The combination decoded more
slowly than the target alone.

This is the modern speculation problem in one experiment. A useful drafter needs
\emph{correlation with the target} and \emph{low marginal cost}. A separately trained
small model may have neither. Modern methods move proposal generation closer to the
target's own representation or train future prediction into the model itself.

\Foundations{Proposal architecture and verification semantics are orthogonal}{
A better drafter raises useful accepted work; it does not become the authority.
Linear, multi-head and tree proposals all feed the target-verification/commit protocol
of Chapter~\ref{ch:speculative-decoding}. A tree additionally contains incompatible
histories. Flattening nodes into one tensor does not make them a sequence: attention
must follow ancestry, logical positions must follow depth, and only one accepted path
may survive as autoregressive history.
}

\NapkinSection{Napkin math: optimize accepted work per wall time}

For one speculative iteration define $N$ proposed/verified tree nodes, $A$ newly
committed draft tokens, $t_d(N)$ draft time, $t_v(N)$ target verification time and
$t_o$ controller overhead. Compare with ordinary target decode time $t_1$ per token:
\begin{equation}
S_{\rm iter}\approx\frac{(A+1)t_1}{t_d(N)+t_v(N)+t_o}.
\label{eq:modern-speed}
\end{equation}
The $+1$ represents the correction/bonus opportunity from the target contract. This
form is more useful for trees than ``acceptance rate'': ten accepted nodes scattered
across incompatible branches do not equal ten committed tokens.

Define verification efficiency
\begin{equation}
\eta_{\rm tree}=\frac{A+1}{N}.
\end{equation}
A wider tree can increase the probability of finding a long accepted path while
decreasing $\eta_{\rm tree}$. Modern drafting is therefore a constrained search:
spend verification slots where their expected contribution to accepted path length is
largest.

\section{The proposal engine is now part of model architecture}

Classical speculative decoding uses another autoregressive model. Modern methods exploit
information already produced by the target or add lightweight predictive structure.
This changes four costs:
\begin{enumerate}
\item how many sequential draft steps occur before verification;
\item how much target state must be exported to the drafter;
\item how many candidate nodes target verification must evaluate;
\item how tightly a drafter checkpoint is coupled to one target checkpoint.
\end{enumerate}
The last point is operationally important. A prompt lookup table is model-agnostic. An
EAGLE-style drafter is trained for a particular target representation. Updating the
target can invalidate the drafter even when tokenizer and public API remain unchanged.

\section{EAGLE: autoregress in feature space}

EAGLE's central move is to predict a target-model feature rather than ask an unrelated
small LM to reproduce the target's token distribution. A lightweight autoregressive
draft module consumes target-derived features together with sampled-token information,
predicts a future feature, and uses the target's language-model head to obtain proposal
tokens \cite{li2024eagle}.

Conceptually, if target layer features are $h_t$ and emitted token embedding is
$e(x_t)$, the drafter implements a learned transition
\[
\widehat h_{t+1}=D_\phi(h_t,e(x_t),\text{draft state}),
\qquad
q_{t+1}=\operatorname{softmax}(W_{\rm lm}\widehat h_{t+1}).
\]
This is schematic, not a universal EAGLE equation. The important systems fact is that
$D_\phi$ is much cheaper than a full target forward step while its predictions are
conditioned on target-native representations.

The target still verifies proposals. Feature prediction improves proposal quality; it
does not grant predicted features authority over committed target KV.

\section{Why a draft chain leaves probability on the table}

Suppose the drafter assigns next-token probabilities $(0.45,0.40,0.15)$. A chain must
choose one token. If the target follows the second candidate, speculation stops at
depth one even though the drafter knew that alternative was almost as plausible.

A tree retains several futures. At depth $d$, node $u$ has a path score such as
\[
s(u)=\prod_{v\in\operatorname{path}(u)}q(v\mid\operatorname{ancestors}(v)),
\]
or, numerically, a sum of log probabilities. Under a node budget $N_{\max}$, the tree
builder chooses which frontier nodes deserve expansion.

The score is a proposal heuristic, not target acceptance probability unless calibration
has been established. A production engine should distinguish draft confidence from
measured target acceptance.

\section{EAGLE-2: spend the tree budget dynamically}

EAGLE-2 develops the draft tree according to context-dependent confidence rather than
using one fixed shape \cite{li2024eagle2}. Predictable continuations can grow deep;
ambiguous positions can branch. This reframes tree construction as best-first resource
allocation.

A teaching version is:
\begin{enumerate}
\item initialize the frontier with candidates from the current committed state;
\item score frontier nodes with draft probabilities/path scores;
\item pop the most promising expandable node;
\item generate children and insert them into the frontier;
\item stop when node/depth/time budgets are exhausted.
\end{enumerate}
The real algorithm and engine optimizations are more specific, but this abstraction
exposes the systems contract: tree construction must produce parent links, token IDs,
depth/logical positions and a deterministic flattened order for verification.

\section{A proposal tree is a graph stored in an array}

Consider committed prefix $P$ and this tree:
\[
P\rightarrow A,\quad
A\rightarrow B,\ A\rightarrow C,\quad
B\rightarrow D,\ C\rightarrow E.
\]
Flatten the draft nodes as $[A,B,C,D,E]$. Array index 2 ($C$) is after $B$ in memory,
but $C$ must not attend to $B$. Node $E$ is after $D$, but $E$ must not attend to
$B$ or $D$.

For draft nodes $i,j$, define
\begin{equation}
M_{ij}=
\begin{cases}
0,&j\in\operatorname{Ancestors}(i)\cup\{i\},\\
-\infty,&\text{otherwise}.
\end{cases}
\label{eq:tree-mask}
\end{equation}
Every draft node may additionally attend to the entire committed prefix. Logical
position is
\[
\operatorname{pos}(i)=C+\operatorname{depth}(i),
\]
not $C+i$. Siblings at the same depth share a logical position while occupying
different packed rows.

\section{Why an ordinary triangular mask is wrong}

A causal triangular mask means row $i$ sees every earlier packed row. That is correct
only when packed order is one causal sequence. In a tree it leaks sibling history.

With flattened $[A,B,C,D,E]$, triangular attention lets $C$ see $B$ and $E$ see
$A,B,C,D$. The resulting hidden states correspond to no legal root-to-node sequence.
The target may then ``verify'' logits for a history it could never autoregressively
produce.

This is an excellent differential test. Evaluate each root-to-node path independently
with ordinary causal attention. Its final result must equal the corresponding row of
the flattened tree evaluation under the ancestry mask, modulo the numerical tolerance
of the implementation.

\section{Tree packing needs three coordinate systems}

For every packed node retain:
\[
(\text{packed row},\ \text{parent row},\ \text{logical position}).
\]
Packed row addresses tensors. Parent row reconstructs ancestry. Logical position drives
RoPE/positional semantics.

Do not derive parentage from position: siblings have equal logical position. Do not
derive position from packed row: breadth-first and depth-first layouts assign different
rows to the same logical tree.

For paged KV, tentative tree nodes additionally need physical storage ownership. A
useful descriptor is
\[
(\text{request generation},\text{tree generation},\text{node id},
\text{KV handle},\text{parent}).
\]
Only nodes on the accepted path are candidates for retention.

\section{Verification is a short irregular prefill}

Target verification over $N$ nodes resembles a short prefill with a non-triangular
mask. It can exploit matrix parallelism unavailable to single-token decode, but tree
geometry changes attention.

The engine prepares packed token IDs, logical positions, ancestry metadata/mask and KV
write destinations; executes the target; then walks candidate paths according to the
acceptance algorithm. The result is a selected path length $A$, not ``all nodes whose
token matched somewhere.''

The verification kernel should not materialize a dense $N\times N$ mask if topology can
be encoded more compactly. But any optimized representation must be equivalent to
equation~\eqref{eq:tree-mask}.

\section{Rollback becomes branch retirement}

Chapter~\ref{ch:speculative-decoding} rolled back a linear rejected suffix. A tree has
many losing branches. After target verification:
\begin{enumerate}
\item identify the accepted root-to-node path;
\item reconcile the correction/bonus token;
\item retain or materialize target KV for committed history;
\item retire every unchosen branch's tentative KV/state;
\item reset draft state to the new committed history.
\end{enumerate}
A losing branch must never enter the shared prefix cache merely because target KV was
computed for it.

Reference counts matter when physical pages contain shared committed prefix plus private
tree tails. Branch retirement decrements only the private ownership it acquired.

\section{EAGLE-3: direct token prediction from fused target features}

EAGLE-3 changes the drafting representation: its authors describe direct token
prediction using fused features from multiple target layers and a training procedure
designed to expose the drafter to its own rollout conditions \cite{li2025eagle3}.
The motivation is practical: draft quality must remain strong several speculative
steps away from the verified target frontier.

For the serving engine, this means target execution must expose the feature set expected
by the drafter, with exact layer identity, dtype, shape and model revision. Treat that
interface like an ABI:
\[
I_{\rm draft}=
H(\text{target checkpoint},\text{layers},\text{feature transform},
\text{tokenizer},\text{drafter checkpoint}).
\]
Loading a superficially compatible drafter against the wrong target features is a
correctness/quality configuration error, not merely a performance miss.

At vLLM source snapshot
\texttt{155488d853a0bc42df227dbfc74005b3fd488e94}, documentation and model executor
paths explicitly include EAGLE/EAGLE-3 support, including
\texttt{vllm/model\_executor/models/deepseek\_eagle3.py}. This is a pinned source fact,
not a statement that every model/backend combination is supported.

\section{Medusa: multiple futures from one hidden state}

Medusa attaches multiple decoding heads to predict future offsets from target hidden
state \cite{cai2024medusa}. Head $k$ proposes candidates for a token roughly $k$ steps
ahead. Combining top candidates across heads produces a tree that target verification
checks.

This trades an autoregressive draft loop for parallel head computation. But independent
future heads do not automatically define mutually consistent paths: a token predicted
for offset 3 was not necessarily conditioned on the particular offset-1 and offset-2
candidates paired with it. Tree verification is what restores target authority.

Medusa also illustrates a crucial taxonomy: \emph{exact verification} and looser
``typical'' acceptance are different semantic products. If an acceptance heuristic
permits tokens the exact target sampler would not emit under the same random process,
label the mode approximate rather than hiding the distinction inside a speed feature.

\section{Multi-token prediction: train speculation into the checkpoint}

Multi-token prediction (MTP) asks the model to predict several future positions during
training. Future-token modules can improve representations and can also serve as
drafters at inference \cite{gloeckle2024mtp,deepseek2024v3}.

Architecturally, MTP moves compatibility management upstream. Instead of pairing an
arbitrary external drafter with a target, the checkpoint/model family declares the
future-prediction module it was trained with. That can reduce deployment mismatch.

It does not remove verification. An MTP head predicts possible futures; the ordinary
target path remains authoritative unless the model defines a different decoding
semantics.

\section{Parallel drafting attacks draft latency itself}

Even a tiny autoregressive drafter has a serial dependency:
\[
d_1\rightarrow d_2\rightarrow\cdots\rightarrow d_\gamma.
\]
Once target verification is highly optimized, this small serial chain can dominate the
iteration.

Parallel-draft approaches predict multiple speculative positions with fewer sequential
draft passes. The systems question becomes whether the parallel proposal computation
raises accepted path length enough to justify its larger one-shot work.

At vLLM snapshot \texttt{155488d853a0bc42df227dbfc74005b3fd488e94},
\texttt{vllm/config/speculative.py} and
\texttt{docs/features/speculative\_decoding/parallel\_draft\_model.md} expose
parallel-drafting integration. Treat exact performance as model/hardware/load-specific.

\section{The tree builder is a scheduler}

A dynamic tree consumes a finite verification budget. Let frontier node $u$ have
estimated probability $\hat p_u$ of extending the accepted path and expansion cost
$c_u$ verification nodes. A simple priority is
\[
\rho(u)=\frac{\hat p_u\Delta L_u}{c_u},
\]
where $\Delta L_u$ estimates accepted-length contribution. Real policies can include
depth penalties, diversity, verification shape and calibrated acceptance.

This looks like scheduling because it is scheduling: choose speculative work under
compute, latency and memory budgets. Under high server load, the same verification
slots may be more valuable serving other requests.

\section{Tree shape changes GPU work}

A chain of eight drafts has eight nodes and maximum accepted draft length eight. A full
binary tree of depth three has
\[
2+4+8=14
\]
nodes but can commit at most three draft tokens along one path before the target's
correction/bonus. Width hedges uncertainty; depth creates potential accepted length.

The right tree is therefore neither ``widest'' nor ``deepest.'' It depends on proposal
entropy, target agreement, verification-kernel efficiency, KV capacity and concurrent
load.

\section{Continuous batching with speculative trees}

For request $i$, let $N_i$ be verification nodes. A scheduler can impose
\[
\sum_i N_i + N_{\rm ordinary}\le T_{\rm iter}.
\]
But equal node counts need not cost equally: attention context lengths differ, tree
metadata differs, and model/drafter families may invoke different kernels.

A practical scheduler needs at least draft method, requested tree budget, estimated
verification tokens, tentative KV requirement, recent accepted length and queue/SLO
state. It may shrink trees under load rather than disable speculation globally.

This creates a feedback loop:
\[
\text{load}\rightarrow\text{tree budget}\rightarrow
\text{acceptance/work}\rightarrow\text{iteration time}\rightarrow\text{load}.
\]
Stable control matters more than maximizing an isolated benchmark.

\section{Structured output prunes the proposal tree}

If grammar state permits only a subset of tokens at a node, illegal children should
not consume tree budget. Each branch has its own grammar state because branches encode
different token histories.

A tree node therefore may carry a grammar-state handle alongside parent/depth. Sibling
grammar states must not alias mutable state. After verification, retain only the
accepted branch's state and retire the rest.

This is an opportunity as well as a constraint: schemas can make future tokens highly
predictable, increasing useful speculative depth.

\section{Distributed targets complicate feature reuse}

With tensor parallelism, the feature consumed by an EAGLE-style drafter may be sharded.
Running the drafter on one rank can require an all-gather; replicating it can require
replicated inputs and synchronized proposal decisions.

With pipeline parallelism, required target features may live on a stage different from
the language-model head. A drafter that is cheap in FLOPs can become expensive in
communication.

Always account:
\[
t_d=t_{\rm draft\ compute}+t_{\rm feature\ movement}+t_{\rm synchronization}.
\]
The method name alone does not determine draft cost.

\section{Quantization and drafter compatibility}

Quantizing the target can change feature values and target logits. A drafter trained
against one numerical target may experience lower acceptance against another
quantization, even when model semantics appear close.

Similarly, quantizing the drafter reduces its cost but can lower proposal quality.
Evaluate the pair, not each component independently. Record target format, drafter
format, tokenizer, feature dtype and backend.

\section{Failure boundaries}

Modern speculation adds new failure classes:
\begin{enumerate}
\item triangular attention accidentally leaks sibling branches;
\item packed-row index is used as logical position;
\item a child points to a stale parent/tree generation;
\item losing-branch KV is retained or prefix-cached;
\item target upgrade is paired with an incompatible feature drafter;
\item grammar state is shared mutably between siblings;
\item acceptance statistics count matching nodes rather than committed path tokens.
\end{enumerate}
Most can survive superficial text tests. Structural differential tests are mandatory.

\section{Observability: count paths, not just nodes}

Record draft method/version, tree nodes, maximum depth, branch factor distribution,
draft time, target verification time, controller time, accepted path length, rejected
nodes, bonus/correction events, tentative KV bytes and rollback.

Two useful metrics are
\[
\eta_{\rm tree}=\frac{A+1}{N},
\qquad
G_{\rm spec}=\frac{\text{committed tokens}}
{t_d+t_v+t_o}.
\]
Neither replaces end-to-end TTFT/ITL/goodput. At high concurrency, per-request
$G_{\rm spec}$ can improve while fleet goodput falls.

\LedgerSection
\begin{ConstraintLedger}
Memory bandwidth & trades & Target-feature reuse can avoid a separate full drafter; verification still reads target weights and KV for many nodes.\\
Compute & spends & Draft heads/modules plus target evaluation of losing branches; width can grow work exponentially with depth.\\
Memory capacity & spends & Drafter parameters/features and tentative KV/state for every live tree node.\\
Latency & trades & Longer accepted paths reduce target iterations; serial drafting, feature movement or oversized trees can erase the gain.\\
Correctness & risks & Sibling leakage, wrong positions, stale branch state and approximate acceptance can change semantics.\\
Cost & trades & Fewer target iterations can improve economics, but training/serving model-specific drafters and reduced batch capacity add cost.\\
\end{ConstraintLedger}

\LabSection{flatten a tree without inventing a sequence}

The Rust lab in \texttt{code/labs/ch23-draft-tree/} builds a parent-indexed proposal
tree, assigns logical depth/position, constructs the exact ancestry visibility matrix,
and compares every flattened row's visible token path against an independently walked
parent-chain oracle. A deliberately wrong triangular mask fails on siblings.

The lab also performs deterministic best-first selection over a prebuilt tree,
considering only roots and children whose parents have already been selected.
This preserves ancestor closure under a node budget, making
the difference between fixed branching and budgeted dynamic trees inspectable. It is a
structural oracle, not a neural-model speed benchmark.

\HappenedSection{modern drafters entered serving engines}

The EAGLE family, Medusa and MTP moved speculative proposal generation from ``run a
second generic LM'' toward target-coupled components
\cite{li2024eagle,li2024eagle2,li2025eagle3,cai2024medusa,gloeckle2024mtp}.
Their reported speedups should be read with model, GPU, batch and acceptance settings,
not as universal constants.

Current source inspection reinforces the architectural trend. vLLM commit
\texttt{155488d853a0bc42df227dbfc74005b3fd488e94} contains EAGLE documentation,
EAGLE-3 model-executor code and parallel-draft configuration/documentation. SGLang
commit \texttt{7a719e9a65e7f52b012ab37211b5f174e5d3d38d} contains speculative tree metadata
and EAGLE-related integration. These are pinned source observations, not claims about
all current backends.

\FrontierSection{2026-10-05}

The frontier is shifting from ``can speculative decoding work?'' to co-design among
model training, draft architecture, tree construction, verification kernels and
serving schedulers. EAGLE-3-style feature fusion, model-native MTP and parallel drafting
reduce proposal cost or increase proposal quality; tree kernels and dynamic budgets try
to convert that quality into accepted target work.

The durable evaluation question is:
\Callout{Evaluation question}{How many correct committed target tokens are
delivered per unit of end-to-end serving resource?}
Chapter~\ref{ch:when-speculation-loses} now asks the complementary question: when does
all this extra machinery reduce, rather than improve, real serving performance?

\item \emph{Tree arithmetic.} Compute node count and maximum accepted draft length for

\item \emph{Mask construction.} For parent array $[-1,0,0,1,2]$, write the five-by-five

\item \emph{Differential test.} Explain the smallest tree that distinguishes ancestry

\item \emph{Budgeting.} Given frontier scores/costs $(.8,2),(.5,1),(.9,3),(.3,1)$,

\item \emph{Falsification.} Construct a tree whose flattened triangular evaluation
contains a token dependency absent from every legal root-to-node history.
\end{enumerate}
