\chapter{The KV Cache: Inference's Central Data Structure}\label{ch:kv-cache}

\begin{ChapterIntent}
Every token a model generates attends to every token before it. Recomputing
their keys and values at each step would make generation quadratic; caching
them makes it linear, and turns the engine into a memory manager. This chapter
derives what is cached and when, checks the formula for its size against the
allocations a real engine makes --- from half a megabyte to a few tens of
kilobytes per token, depending on the architecture --- proves on a small engine
that a cache reproduces recomputation bit for bit, and measures what one wrong
entry does. It then shows how the cache, not the weights, comes to dominate
memory capacity at long context and large batch, and the bytes read per step at
long context. Nearly every chapter in Part~\ref{part:serving} manages this one
data structure.
\end{ChapterIntent}

\OpeningSection{At 32K tokens the cache outweighs the model}

When llama.cpp loaded Llama~3.2~3B on the M1 of \Chref{roofline} with room for
8,192 tokens of context, it reported the memory it had set aside for the KV
cache: \textbf{896~MiB} --- 448~MiB of keys and 448~MiB of values, in 16-bit
floats (measured; the allocation is in the record). That is 112~KiB for every
token of context, and it matches the model's shape exactly: 2 tensors (keys and
values) $\times$ 28 layers $\times$ 8 key/value heads $\times$ 128 numbers per
head $\times$ 2 bytes.

The weights of the same model occupy 2.01~GB. At 32,768 tokens of context ---
the length of a long document, or a few hours of agent conversation --- one
sequence's cache is 3.5~GiB (derived from the measured 112~KiB per token):
\textbf{nearly twice the size of the model}. Serve eight such conversations
and the cache is fifteen times the model.

A language model's weights are fixed and shared by every request. Its KV cache
is per request, grows with every token, is written once and read at every
later step, and must be released when the request ends. Managing it is most of
what distinguishes an inference engine from a model runner.

\Foundations{Memoization with a moving frontier}{
Memoization saves a result when a later computation needs the same result again. In
causal attention, an earlier position's key and value remain usable after more tokens
arrive, provided the weights, position convention and preceding history remain
unchanged. The new query is different, so the old attention output is not the item to
reuse. The cache boundary separates positions already evaluated from tokens that exist
in the history but have not yet been processed. Drawing that boundary prevents
off-by-one errors after sampling. Appendix A.7 distinguishes query, key and value;
Chapter~\ref{ch:prefill-decode} explains when each is computed.
}

\NapkinSection{Napkin math: bytes per token, sequences per GPU}

For a model with $L$ attention layers, $H_{kv}$ key/value heads of width $d_h$,
and a cache element of $b_{kv}$ bytes, each token of context costs
\begin{equation}
m_{kv} = 2\,L\,H_{kv}\,d_h\,b_{kv}\quad[\text{bytes/token}].
\label{eq:kv-per-token}
\end{equation}
The factor 2 counts keys and values. The number of \emph{query} heads does not
appear: grouped-query attention lets several query heads share one key/value
head, and that sharing is the main reason 2026's models cache far less per
token than 2022's (\Chref{shrinking-kv}).

The formula is worth checking against an engine rather than trusting. Asked
for 8,192 tokens of context, llama.cpp reported these allocations on the M1
(measured, record \texttt{2026-09-26-m1-pass3}):

Capacity follows by division. An H100 has 80~GB. Qwen3-8B in BF16 takes
16.4~GB; set aside about 4~GB for activations and workspace (illustrative),
leaving about 60~GB for caches. At 144~KiB per token, that is about 400,000
tokens of context in total (derived) --- 49 sequences of 8,192 tokens, or
twelve of 32,768. Every one of those sequences must be resident for
the engine to decode it. At long context, \textbf{memory capacity decides the
batch size}, and \Chref{roofline} showed that batch size decides throughput.

A larger model makes it worse. Llama~3~70B has 80 layers, so 320~KiB per
token. Stored in FP8 it needs about 71~GB for weights, leaving an 80~GB H100,
with the same 4~GB set aside, room for roughly 16,000 tokens of cache in
total: one long conversation, or a handful of short ones. On an H200's
141~GB, the same model has room for about 200,000 tokens (derived).

Bandwidth follows too. A decode step for $B$ sequences with contexts $S_i$
reads
\begin{equation}
W_{\text{step}} = W_{\text{weights}} + m_{kv}\sum_{i=1}^{B} S_i
\quad[\text{bytes}],
\label{eq:decode-bytes}
\end{equation}
and only the first term is shared across the batch. \Chref{prefill-decode}
found the crossover for Qwen3-8B: with 32 sequences, the cache term overtakes
the weights at about 3,200 tokens each.

\section{Why recomputation is quadratic}

Attention at position $t$ compares the query of token $t$ with the keys of
tokens $1$ to $t$ and mixes their values. Those keys and values are
projections of each earlier token's hidden state, layer by layer. A model
without a cache would recompute them at every step: generating $n$ tokens
would project $1+2+\dots+n \approx n^{2}/2$ token positions through every
layer, instead of $n$.

The keys and values of earlier tokens do not change when a later token
arrives: causal attention means token $j$'s state depends only on tokens
$\le j$. So they can be computed once and kept. This is the entire idea of
the \Term{KV cache}, and it changes the cost of generation from quadratic in
projections to linear. What remains quadratic --- each step attending over all
previous tokens --- is now a memory read rather than a recomputation.

Put numbers on it. A 32-token prompt followed by 128 generated tokens needs
$32 + 127 = 159$ token positions projected through the model with a cache. Without
one, the step that generates the token at position $t$ must process all $t$
earlier positions again: $32 + 33 + \dots + 159 = 12{,}224$ positions, 77 times
as many. The chapter's lab runs exactly this on the capstone engine's code with
a small four-layer model, and Figure~\ref{fig:ch05-recompute} shows the result:
with the cache each generated token costs about 0.4~ms whatever its position;
without it the cost climbs in a straight line, from 10~ms at position 33 to 55~ms
at position 159 (measured). The whole generation took 0.05--0.08~s with the
cache and 4.1--4.2~s without: 50 to 79 times as long, the ratio still growing
with every token.

\EngineFigure{ch05-recompute}{The chapter's lab on the M1's CPU: time to
generate each token of a 128-token reply, with a KV cache and by recomputing the
whole sequence (measured; logarithmic scale). The two paths pick the same
tokens and produce bit-identical logits at every step; only the cost
differs.}{fig:ch05-recompute}

The recomputation is not a straw man. It is the capstone engine's
\emph{oracle}: a function that computes the logits for a sequence from nothing,
with no cache, no paging and no batching, sharing only the arithmetic kernels.
Because those kernels fix their summation order, the cached engine must match
it to the last bit, and the lab checks that it does at every one of the 128
steps before it reports a single time. A cache is an optimization that must be
invisible, and the only way to know it is invisible is to compare it with the
thing it replaced.

\section{What is cached, and when}

For each layer and each token, the cache holds that token's key vector for
every key/value head --- after rotary position embedding has been applied
(Appendix~\ref{app:rope}) --- and its value vector. Queries are not cached; each is
used once, in the step that computes it.

It is worth seeing why keys and values are \emph{enough}. Look back at the layer
of \Chref{forward-pass}: a later token interacts with an earlier one in exactly
one place, attention, and there it uses only the earlier token's key (to score
it) and value (to mix it). The earlier token's residual stream, its normalized
hidden state, its FFN activations and its query never enter a later token's
computation at all. So an engine can discard everything about a token except its
keys and values the moment its step is done: for each layer of Llama~3.2~3B, a
12~KB residual stream and 32~KB of FFN activations (in 32-bit floats) are thrown
away, and 4~KiB of keys and values is kept. A
cache of keys and values is therefore not an approximation of the model's state:
for a causal transformer it \emph{is} the state, which is why the lab can demand
bit-for-bit agreement with recomputation.

Prefill writes the cache for every prompt token at once. Each decode step
writes one new entry per layer and reads all previous entries. A
multi-head-latent-attention model such as DeepSeek-V3 caches a compressed
latent of 512 numbers plus a 64-number rotary key per layer instead of full
keys and values --- 576 numbers where multi-head attention with the same heads
would store 40,960 (derived from its configuration; \Chref{shrinking-kv}).

Two consequences of that definition matter every day. First, because keys are
stored \emph{after} rotation, an entry is tied to the position it was computed
at: the same token at another position has a different cached key. A cache can
be reused only for the exact same prefix at the exact same positions --- the
rule prefix caching is built on (\Chref{prefix-caching}). Second, an entry
depends on every token before it, through the lower layers' attention. Change
one token and every later entry in every layer above the first is wrong.

How wrong? The lab has a switch that zeroes the cached keys and values of one
prompt position in every layer, just after the prefill, and then keeps
generating. With position 5 of the 32-token prompt erased, the very next step's
logits differ from the oracle's by up to 3.4 --- large for logits of this size
--- yet the greedy choice survives for nine steps and changes at the tenth.
Erasing position 30 changes the second generated token; erasing position 0
changes nothing visible until the 45th (measured, record
\texttt{2026-09-26-m1-pass3}). A damaged cache does not crash: it produces
plausible output that is wrong from some point on, sooner or later depending on
what was lost. That is why the cache's correctness is tested against an oracle
rather than by reading the output (\Chref{fast-wrong-answers}).

\section{State that grows, per request}

The cache has an awkward lifecycle for a memory allocator. Its size is not
known in advance, because the number of output tokens is not. It grows one
token per step. It belongs to one request --- unless requests share a prefix,
when its first blocks could be shared (\Chref{prefix-caching}). It must be freed
the moment its request finishes, fails or is cancelled
(\Chref{request-lifecycle}). An engine that reserves memory for each request's
maximum length wastes most of it; an engine that grows allocations in place
fragments its memory. \Chref{paged-kv} applies the operating system's answer:
fixed-size pages and a table per request.

The waste of reservation is easy to underestimate. A server configured for
8,192-token conversations that reserves the maximum for each request, serving
requests whose prompt and reply together average 1,000 tokens, uses one eighth
of what it reserves: seven eighths of its cache memory holds nothing. llama.cpp
allocates its cache as one pool of cells at start-up and, for each batch of new
tokens, finds free cells for them wherever they are (\texttt{find\_slot} in
\texttt{src/llama-kv-cache.cpp}); vLLM and SGLang page it (\Chref{paged-kv},
\Chref{real-engines}).

\section{The cache's own interface}

Because the cache is state, an engine needs operations on it beyond ``write a
token'' and ``read a sequence''. llama.cpp exposes them as a small public
interface over its memory (\texttt{include/llama.h}, checked at commit
\texttt{d006858}), and reading where its server calls each one is a compact
tour of what the rest of this book does to a cache:

\begin{itemize}
\item \texttt{llama\_memory\_seq\_rm(seq, p0, p1)} removes a sequence's tokens
with positions in $[p_0, p_1)$. The server calls it to free a finished or
cancelled request (\Chref{request-lifecycle}); to throw away the draft tokens
that speculative decoding proposed and the model rejected, keeping the cache
exactly at the last accepted token (\Chref{speculative-decoding}); and to keep
the part of a cached prompt that a new request shares and truncate the rest
--- its per-slot prompt cache (\Chref{prefix-caching}).
\item \texttt{llama\_memory\_seq\_cp(src, dst, p0, p1)} makes a range of one
sequence's cells belong to another as well. The server uses it to hand a
processed prompt to other slots, so that several samples of one prompt share
its cache instead of each prefilling it.
\item \texttt{llama\_memory\_seq\_add(seq, p0, p1, delta)} moves a range of
tokens to new positions, and \texttt{llama\_memory\_seq\_div} divides their
positions by a factor. Because cached keys are stored rotated, moving a token
means rotating its keys again: the cache applies a ``K-shift'', a rotary
embedding by each token's position change, before its next use
(\texttt{build\_rope\_shift} in \texttt{src/llama-kv-cache.cpp}).
\end{itemize}

\noindent The last operation is how llama.cpp's server can keep a conversation
going past its context window. With context shifting enabled, a sequence that
fills its window keeps its first tokens (the prompt, by default), discards half
of the rest, and shifts the remainder left over the gap with
\texttt{seq\_rm} and \texttt{seq\_add} (\texttt{tools/server/server-context.cpp}).
No token is recomputed, so the shift is fast --- and approximate. The K-shift
makes each surviving key exactly what it would have been at its new position
\emph{from the same hidden state}, but from the second layer up those hidden
states were computed while the discarded tokens were still there to be attended
to. The cache after a shift is not the cache a fresh prefill of the shortened
text would produce, which is the worked problems' insertion case seen from the
other side. The feature is off by default in the measured build
(\texttt{ctx\_shift = false} in \texttt{common/common.h}); without it the
server ends generation with an error when the window is full.

Four operations --- remove a range, share a range, shift a range, and the
implicit ``append'' of every decode step --- are the whole vocabulary that
paging, prefix sharing, speculation and preemption are written in. The paged
caches of \Chref{paged-kv} implement the same operations on blocks instead of
cells, which is what makes sharing cheap: two sequences can point at the same
physical block.

\section{How big should the cache be?}

Someone has to decide how much memory the cache gets, and engines decide in two
ways. llama.cpp takes the answer from its user: the context size given at start
(\texttt{-c}) is allocated as cache cells when the model loads --- the 896~MiB
of the opening, reserved before the first request arrives, used or not.

vLLM measures instead. When it starts, it runs a forward pass on dummy inputs
as large as its largest allowed step to record the peak memory that weights,
activations and workspace need, then gives the cache whatever remains of a
fixed share of the GPU --- by default 92\% of its memory
(\texttt{gpu\_memory\_utilization} in \texttt{vllm/config/cache.py} and
\texttt{determine\_available\_memory} in \texttt{vllm/v1/worker/gpu\_worker.py},
checked at commit \texttt{bcdacfc}). It then reports the result in the units
this chapter uses: a log line giving the cache's capacity in tokens and the
``maximum concurrency'' for a request of the model's maximum length
(\texttt{vllm/v1/core/kv\_cache\_utils.py}). For Qwen3-8B on an 80~GB H100 the
arithmetic is: 92\% of 80~GB is 73.6~GB; less 16.4~GB of weights and, say,
3~GB of profiled activations and workspace (illustrative; the profile run
measures it) leaves about 54~GB, which at 144~KiB per token is about 370,000
tokens --- a maximum concurrency of about 11 for requests of 32,768 tokens, or
45 for requests of 8,192 (derived).

The two policies trade the same things differently. A fixed reservation is
predictable and wastes memory on idle cells; a measured reservation uses the
memory but depends on a profile that must cover the largest step the scheduler
will ever build, which is one reason engines cap the tokens per step
(\Chref{chunked-prefill}). Either way the number that comes out --- tokens of
cache --- is the one the scheduler spends: every admitted request draws on it,
and when it runs out, someone waits or is preempted (\Chref{scheduling}).

\section{Reading the whole cache every step}

Weights are read once per step for the whole batch. The cache is read once per
step \emph{per sequence}: every decoding sequence reads all of its own keys and
values in every layer. At short context the weights dominate the bytes of a
step; at long context and large batch, equation~\eqref{eq:decode-bytes} says
the cache does. Batching amortizes the first term and multiplies the second, so
past the crossover, adding sequences no longer makes decode more efficient per
byte --- it only adds cache reads. This is why long-context serving is
bandwidth-bound even at batch sizes that would make short-context serving
compute-bound, and why shrinking the cache (\Chref{shrinking-kv}) and
quantizing it (\Chref{kv-quantization}) pay off twice: in capacity and in
bandwidth.

\Chref{prefill-decode} measured the first term's rival on the M1: at 8,192 tokens
of context a decode step of Llama~3.2~3B reads 0.94~GB of cache beside its
2.01~GB of weights, and the step took 55~ms with a kernel that streams the cache
at about the machine's bandwidth and 94~ms with one that does not. A single
conversation that long already spends a third of every step on its cache.

\section{Written once, read thousands of times}

The cache's traffic has a shape that decides how every later technique treats
it. Take Llama~3.2~3B with 4,096 tokens already cached. A decode step writes one
token's keys and values --- 112~KiB, 4~KiB per layer --- and reads all 4,096
tokens' --- 448~MiB. Reads outnumber writes 4,096 to one, and the ratio grows
with every token. Over a 1,000-token reply, each prompt token's entry is
written once, during the prefill, and read 1,000 times, once per step.

Three design rules follow from that asymmetry, and each has a chapter.

\emph{Spend at write time to save at read time.} Anything that makes an entry
smaller or cheaper to read --- quantizing it, rotating it first so that it
quantizes better, compressing it into a latent --- costs work once per token and
saves bytes on every one of the thousand reads. llama.cpp's Hadamard rotation of
quantized caches, above, is such a trade; so is storing the cache in 8 or 4
bits (\Chref{kv-quantization}), and so is multi-head latent attention, which
spends extra arithmetic in every step to read 576 numbers instead of tens of
thousands (\Chref{shrinking-kv}).

\emph{Writes come in bursts; reads come in streams.} A prefill writes the whole
prompt's cache at once: 448~MiB for the 4,096-token prompt, produced over the
15.7~s the M1 took to process it, about 30~MB/s --- trivial for the memory, and
on a data-center GPU the same burst lasts a fraction of a second. The reads are
the steady load, the 448~MiB of every decode step. That is why caches can be
moved between machines after a prefill and then read locally, the design of
disaggregated serving (\Chref{disaggregated-serving}). Moving Qwen3-8B's cache
for a 4,096-token prompt, 604~MB, over a 400~Gb/s network link takes about 12~ms,
roughly the time to read it sixty-seven times from an H100's memory (derived):
worth it once per request, never once per step.

\emph{An entry is valuable in proportion to how often it will be read again.}
A prompt shared by thousands of requests --- a system prompt, a long document
many users ask about --- has entries that will be read in thousands of
conversations, not just one, which is the economics of prefix caching
(\Chref{prefix-caching}) and of keeping caches in host memory or on disk
between turns rather than recomputing them (\Chref{kv-storage-tier}). The
worked problems price the other side: an entry that must be recomputed costs a
prefill, and a prefill of thousands of tokens costs seconds on a laptop and a
large fraction of a second on the largest GPUs.

\section{Layout: layers, heads and tokens}

A cache has at least four logical dimensions --- layer, key or value, token
and head, each head a vector of $d_h$ numbers --- and the order in which they
are laid out in memory decides how efficiently attention can read it. Decode
attention for one layer and one head reads all tokens of that head, so tokens
should be adjacent for each head; writing a new token touches every head, so
heads should be adjacent for each token. No layout serves both perfectly, and
engines choose based on which kernel they want to make fast.
Figure~\ref{fig:ch05-cache-layouts} draws the three layouts this book meets.

\EngineFigure{ch05-cache-layouts}{Three layouts of a KV cache (illustrative
sizes). (a) One slab per sequence, reserved for the maximum length: simple
addressing, most of the memory idle. (b) Inside one layer as llama.cpp stores
it: a row per token holding every key/value head, and values stored transposed
when flash attention is off. (c) Paged: fixed-size blocks drawn from one pool,
with a table per sequence mapping its logical positions to physical
blocks.}{fig:ch05-cache-layouts}

llama.cpp's choice is concrete in its source. Each layer gets one key tensor
and one value tensor of shape (width of all key/value heads) $\times$ (cache
cells), so each token's keys for every head sit in one contiguous row --- the
write of a new token is one row --- and a head's keys for successive tokens are
a fixed stride apart. When flash attention is off, the value tensor is stored
transposed, so that the matrix product that mixes values reads each head's
values for all tokens contiguously (\texttt{src/llama-kv-cache.cpp} and
\texttt{src/llama-model.cpp}, where \texttt{attn\_v\_trans} is set to
\texttt{!cparams.flash\_attn}; checked at commit \texttt{d006858}). The same
model therefore has two cache layouts in llama.cpp depending on one flag, and a
cache written in one cannot be read with the other. When the cache is quantized
and the head width is a multiple of 64, llama.cpp also applies an orthonormal
Walsh--Hadamard rotation to keys and values --- the \texttt{attn\_rot} lines of
its start-up log --- the device rotation-based quantization uses to spread large
values across a vector before rounding it (same file; \Chref{kv-quantization}). Paged caches add a
level of indirection: tokens are grouped into fixed-size blocks, and a table
maps each sequence's logical positions to physical blocks (\Chref{paged-kv}).

\section{Where the bytes go on a real accelerator}

An engine's memory budget has four lines: weights, KV cache, activations and
workspace, and fragmentation. Weights are fixed. Activations are small at
decode and large at prefill --- prefill of a long prompt materializes
activations for every prompt token, which is one reason engines limit how many
prompt tokens enter a step (\Chref{chunked-prefill}). Workspace is kernel
scratch: attention's split partials, communication buffers, captured graphs.
Everything left is cache, and the engine converts it into concurrency:
\begin{equation}
B_{\max} \approx \frac{M_{\text{HBM}} - M_{\text{weights}} - M_{\text{act}}}
{m_{kv}\,\bar{S}},
\label{eq:max-batch}
\end{equation}
for an average context $\bar{S}$. Every technique in Part~\ref{part:serving}
that raises the numerator or lowers the denominator raises throughput.

llama.cpp prints the budget at start-up, and on the M1 it reads: 12,123~MiB of
the unified memory usable by the GPU; 1,918~MiB of weights mapped for the GPU
(and the 308~MiB input table mapped for the CPU, because, in the words of the
source, ``there is very little benefit to offloading the input layer''); 896~MiB
of cache for 8,192 tokens; 256.5~MiB of GPU compute buffer and 28~MiB on the CPU
(measured). Equation~\eqref{eq:max-batch} then gives
$(12{,}123 - 1{,}918 - 257) / 112~\text{KiB} \approx 91{,}000$ tokens of cache:
eleven conversations of 8,192 tokens, or forty-four of 2,048 --- if nothing else
on the laptop needed memory, which on a desktop in use it always does.

\HappenedSection{537 megabytes per decode step}

When Hermon's paged-attention kernels were ported from Apple silicon to an
NVIDIA RTX 5060 Ti, the cache had to move. On Apple's unified memory the
kernel could read a cache that lived in ordinary host memory at full speed. On
a discrete GPU, Hermon's developers measured \textbf{448~GB/s} from the card's
own memory against \textbf{17.8~GB/s} across PCIe from pinned host memory ---
a 25-fold gap. A decode step of Llama-3-8B at 4,096 tokens of context reads
about 537~MB of cache (derived: $4{,}096\times128$~KiB), about 1.2~ms from
video memory and about 30~ms across PCIe: a ceiling of 33 tokens per second
from the interconnect alone. The design followed from the arithmetic: the
cache arena lives on the device, and each new token's entry is written through
to it --- cheap, because decode writes one token and reads the whole context
(Hermon \texttt{docs/KERNEL\_DESIGN.md}, section K5, the developers'
measurements on an RTX 5060 Ti; the native kernel path is off unless
\texttt{HERMON\_PAGED\_KERNELS=1}, \texttt{crates/hermon-runtime/src/paged.rs}
at commit \texttt{2a3fd52}, so PREVIEW). \Chref{offloading} returns to what happens when the cache
does not fit on the device at all.

\FrontierSection{2026-09-27}

The cache per token is the architectural number that moved most between 2023
and 2026. Grouped-query attention cut it by the sharing factor; multi-head
latent attention cut it several-fold again \cite{deepseek2024v2,deepseek2024v3},
and GLM-5.3 keeps that design at 576 cached numbers per token per layer
\cite{zai2026glm53}. The 2026 flagships go further by making most layers keep no
growing cache at all: Qwen3.5-397B-A17B has 15 full-attention layers among 60,
each with two key/value heads, for 30~KiB per token plus a fixed recurrent state
\cite{qwen2026qwen35config}; Kimi~K3 pairs 69 Kimi Delta Attention layers
with 24 gated latent-attention layers \cite{moonshot2026kimik3}; Kimi Delta
Attention keeps a fixed-size recurrent state updated by a gated delta rule, a
finer-grained form of Gated DeltaNet \cite{kimi2025linear} (\Chref{hybrid-models}).
Gemma~4's small models let their last layers reuse earlier layers' caches
instead of keeping their own \cite{google2026gemma4}. DeepSeek-V4 compresses
the cache along the sequence and reports 10\% of DeepSeek-V3.2's cache at a
million tokens \cite{deepseek2026v4}. Meanwhile the cache is increasingly
stored in eight bits or fewer (\Chref{kv-quantization}) and in tiers beyond the
GPU (\Chref{kv-storage-tier}).
