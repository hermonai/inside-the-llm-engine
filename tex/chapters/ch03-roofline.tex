\chapter{The Roofline: Why Decode Leaves Your GPU Idle}\label{ch:roofline}

\begin{ChapterIntent}
A matrix product needs both numbers and arithmetic. If memory cannot deliver the numbers
quickly enough, faster multiplication alone will not finish it sooner. We will estimate
these two limits, draw them on a roofline plot and test which one explains the measured
workload.
\end{ChapterIntent}

\section*{Two limits on the same computation}
Imagine a calculation needing 20 ms to obtain its data but only 8 ms to perform its
arithmetic. Even with ideal overlap it cannot finish in less than 20 ms. The roofline is
a graphical form of that comparison. First learn what each axis counts. Then follow the
batch sweep: additional rows can reuse weight bytes and change which limit matters.
Hardware comparisons come after the model is understandable.

\OpeningSection{Nearly all of the memory bus, a twentieth of the arithmetic}

Take an ordinary laptop: a 2020 MacBook Pro with Apple's M1 chip, 16~GB of
unified memory and an 8-core GPU. Load Llama~3.2~3B, quantized to about four
and a half bits per weight, into llama.cpp and ask it to generate. On the day
this chapter was drafted, on a busy desktop with browsers and terminals open,
it produced \textbf{21.0 tokens per second} (measured: 21.02~$\pm$~0.30 over
five runs of 128 tokens; the record is in
\texttt{research/measurements/2026-09-23-m1-llama32-3b.md}).

Now count bytes. The model file holds 2,011,539,712 bytes of tensors, and ---
as \Chref{forward-pass} shows --- generating one token reads essentially all
of them once: this model ties its input and output embeddings, so even the
323-megabyte vocabulary table is read in full by the output projection at
every step. Twenty-one tokens per second times 2.01~GB per token is
\textbf{42~GB/s} of weights streamed out of memory.

How much could the memory deliver? Apple does not publish the M1's memory
bandwidth directly, but it pins it down twice: the M2's 100~GB/s is ``50
percent more than M1'' \cite{apple2022m2}, and the M1~Max's 400~GB/s is nearly
six times the M1's \cite{apple2021m1pro}. That puts the M1 at about 67--68~GB/s;
this book uses 68. No program gets the nominal figure; the useful ceiling is
what a plain streaming kernel achieves on the same GPU at the same moment. We
measured it: 46--50~GB/s for large reads and copies. Decode is running at
\textbf{85--92\% of the bandwidth a streaming kernel can reach}.

Now count arithmetic. A forward pass costs about two floating-point operations
per parameter per token --- one multiply and one add for every weight
(\cite{kaplan2020scaling}, eq.~2.2) --- so each token costs about 6.4~GFLOP,
and 21 tokens per second is 135~GFLOP/s. Apple quotes the M1 GPU at ``2.6
teraflops of throughput'' \cite{apple2020m1}. Decode is using \textbf{about 5\%
of the arithmetic}.

The fast part of the chip is waiting for the slow part. That is not a flaw in
llama.cpp or a quirk of Apple silicon: the napkin math below shows the same
imbalance, larger, on every data-center GPU in this book, and the lab at the
end of the chapter shows it on the laptop's CPU cores as well. It is a property
of the workload. This chapter explains which property, and what changes it.

\Foundations{Work is not a rate}{
FLOPs count arithmetic operations. FLOP/s measures a machine's rate of doing them.
Likewise, bytes describe traffic and bytes/s describes bandwidth. Dividing work by a
rate gives time. Arithmetic intensity $I=F/D$ divides an operation count $F$ by bytes
$D$ crossing a \emph{named} memory boundary. An operand reused in cache still
contributes arithmetic but may avoid another DRAM transfer. Therefore intensity
belongs to an algorithm, shape and memory level, not to a model name alone.
Chapter~\ref{app:notation} shows a complete dimensional calculation;
Chapter~\ref{app:gpu} explains the physical boundaries.
}

\NapkinSection{Napkin math: bytes per token, tokens per second}

If every token must stream $W$ bytes of weights through a memory system of
bandwidth $\beta$, then no implementation can generate faster than
\begin{equation}
r_{\max} = \frac{\beta}{W}\quad[\text{tokens/s}],
\label{eq:decode-ceiling}
\end{equation}
for a single sequence, whatever its arithmetic units do. For the M1 run:
$68/2.01 = 34$ tokens/s against the nominal bandwidth, $49/2.01 = 24$ against
the achieved one, and 21 measured. The model predicts the measurement to
within 15\% from two numbers, before any code is read.

The same arithmetic prices data-center hardware. Qwen3-8B has 8.19~billion
parameters (derived from its published configuration). In BF16, two bytes per
weight, it is 16.4~GB; batch-one decode reads about 15.1~GB of it per token,
because its $151{,}936\times4{,}096$ input embedding table, 1.24~GB, is
gathered one row at a time rather than streamed. An H100 SXM delivers
3.35~TB/s, so $r_{\max}\approx 3.35/15.1 \approx 220$ tokens/s. A B200,
at 8~TB/s, gives about 530. Store the same weights in FP8 and both numbers
double; in four bits they double again. Nothing about the tensor cores ---
989 dense BF16 TFLOP/s on the H100, 2.25~PFLOP/s on the B200 --- appears in
these predictions (all figures from the vendors' datasheets, logged in
\texttt{research/FRONTIER.md}). Decode speed at batch one is a memory
bandwidth question.

The arithmetic tells the other half. One token of an 8-billion-parameter model
is about 16~GFLOP. At 220 tokens/s that is 3.6~TFLOP/s --- \textbf{0.4\%} of
the H100's dense BF16 peak.

The two halves combine into the one inequality this chapter keeps using. A
step that must perform $F$ FLOPs and move $Q$ bytes on a machine with peak
compute $\pi$ and bandwidth $\beta$ takes at least
\begin{equation}
t_{\text{step}} \ge \max\!\left(\frac{Q}{\beta},\; \frac{F}{\pi}\right),
\label{eq:step-bound}
\end{equation}
because neither the bytes nor the arithmetic can go faster than its own
ceiling, and in the best case each hides entirely behind the other. For the
M1 at batch one: $Q/\beta = 2.01~\text{GB} / 49~\text{GB/s} = 41$~ms and
$F/\pi = 6.4~\text{GFLOP} / 2.6~\text{TFLOP/s} = 2.5$~ms. The step is a
memory step by a factor of sixteen, and the measured 49.8~ms is 21\% above the
bound (derived from the same record).

\section{Measuring the two roofs}

Every number above uses two ceilings, and it matters which. A datasheet gives
the ceiling the hardware cannot exceed; a measurement gives the one a program
can reach. The roofline is only useful with the second kind, so the first job
is to measure it, and the chapter's lab does it on the reader's own CPU with
nothing but the Rust standard library.

The bandwidth roof is measured with the simplest kernel that moves bytes and
does almost nothing else: sum a large array. ``Large'' means far larger than
every cache --- the lab uses 256~MiB against the M1's 12~MiB shared
second-level cache --- so that every byte comes from memory. ``Almost
nothing'' has to be engineered: a loop that adds each element to one running
sum waits for each addition to finish before starting the next, and on the M1
that holds one core to 4.2--4.3~GB/s (measured). Sixteen independent running
sums let the additions overlap, and then the loads are the limit. The lab
contains both loops, and runs the second on each thread's share of the array:

\CodeLines{../code/labs/ch03-roofline/src/main.rs}{39}{61}

\noindent Run on the M1's performance cores, one thread reads 43--45~GB/s and
two to four threads 52--61~GB/s (measured over five runs, record
\texttt{2026-09-26-m1-pass3}): one core cannot keep enough requests in flight
to fill the memory system, and two nearly can. The best of each run, 60--61~GB/s,
is about 89\% of the nominal 68 --- a larger fraction than the GPU's streaming
kernel reached through Apple's Metal Performance Shaders (46--50~GB/s), a
reminder that ``the'' bandwidth of a machine depends on who is asking.

The compute roof needs the opposite: arithmetic with no memory traffic at all.
The lab keeps 64 independent running sums in registers and adds a product to
each, over and over; on the M1's four performance cores that reaches
374--377~GFLOP/s (measured), about 94 per core. That is what the arithmetic
units can do. It is not what this book's code does. The capstone engine's
matrix kernel, run on weights small enough to stay in cache, reaches about
160~GFLOP/s when it multiplies four vectors at a time and 112--117 at sixteen
or more (measured, with four threads) --- 30--43\% of the machine's
arithmetic, because it also loads, adds up partial sums and moves data between
cache levels. For predicting what \emph{this} kernel will do, the kernel's own
rate is the roof that matters. Chapter~\ref{ch:matmul-hardware} is about
closing the gap between the two.

\section{Arithmetic intensity}

The ratio that decides which resource binds is the \Term{arithmetic intensity}
of a computation: the floating-point operations it performs per byte it must
move from memory,
\begin{equation}
I = \frac{F}{Q}\quad[\text{FLOP/byte}],
\label{eq:intensity}
\end{equation}
where $F$ counts operations and $Q$ counts bytes crossing the boundary we care
about --- here, between off-chip memory (DRAM, HBM or GDDR) and the chip. $Q$
is the \emph{compulsory} traffic: every byte the computation must read or write
at least once. Real kernels move more; the intensity of a kernel can only be
lower than that of the computation it implements.

For a decode step, the dominant term is a matrix--vector product: each weight
is read once and used once, in one multiply and one add. With $b_w$ bytes per
weight,
\begin{equation}
I_{\text{decode}} \approx \frac{2}{b_w}.
\label{eq:intensity-decode}
\end{equation}
BF16 weights give 1~FLOP/byte; the M1 run's weights average 0.63 bytes per
parameter, giving 3.2~FLOP/byte. Either way the number is small, and it is a
property of the product itself: a vector touches each weight once.
Chapter~\ref{app:matmul} derives the same result for the scalar kernels of the
book's teaching engine.

It pays to work the intensity of every operator in one step by hand, because
they do not all respond to batching. For Llama~3.2~3B in its \texttt{Q4\_K\_M}
file, counting compulsory bytes as the weights plus 32-bit activations in and
out, at batch one and at sixteen sequences:

\noindent (Derived: FLOPs are $2 \times$ weights for the products, $4 \times$

3~FLOP/byte and scale almost linearly with the batch, because the weights are
shared and the activations are small. Attention over the cache stays at
3~FLOP/byte whatever the batch, because each sequence reads its own keys and
values. Normalizations and other elementwise operators stay below 1, because
they do a few operations per element they touch. Only the first kind can be
rescued by batching; the other two must be rescued by other means --- fusion
for the elementwise operators (\Chref{kernel-languages}), smaller caches and
better kernels for attention (\Chref{decode-attention}, \Chref{shrinking-kv}).

\section{Two roofs and a ridge}

A processor offers two rates: peak compute $\pi$ (FLOP/s) and memory bandwidth
$\beta$ (bytes/s). A kernel with intensity $I$ can go no faster than either
allows. This is the \Term{roofline} model of Williams, Waterman and Patterson
\cite{williams2009roofline}:
\begin{equation}
P \le \min\left(\pi,\; \beta I\right)\quad[\text{FLOP/s}].
\label{eq:roofline}
\end{equation}
Plotted on logarithmic axes, the bound is a sloped line --- the bandwidth roof,
$P=\beta I$ --- that meets a flat line --- the compute roof, $P=\pi$ --- at the
\Term{ridge point}
\begin{equation}
I^{*} = \frac{\pi}{\beta}.
\label{eq:ridge}
\end{equation}
Left of the ridge a kernel is memory-bound: faster arithmetic would not help.
Right of it, compute-bound: faster memory would not help.

bandwidth roof is irrelevant to it.

\section{Decode sits on the slope}

Compare the decode intensity with the ridges. At 1--3~FLOP/byte, batch-one
decode is one to three orders of magnitude to the left of every ridge in the
table. The fraction of peak compute it can use is at most $I/I^{*}$: 8\% on the
M1 at 3.2~FLOP/byte, 0.3\% on an H100 running BF16 weights. The measured 5\% on
the M1 is right where the model says it must be.

This is the fact the rest of the book is built on. Shazeer made the same
observation about incremental decoding in 2019 and designed multi-query
attention to reduce the bytes it moves \cite{shazeer2019mqa}; Pope and
colleagues built their analysis of large-model inference on it
\cite{pope2023scaling}. Every technique that follows either raises the
intensity of decode, reduces the bytes it must move, or accepts the bound and
hides it.

\section{Batch size moves the point}

The simplest way to raise intensity is to reuse each weight for more than one
token. If $B$ sequences are decoded together, one pass over the weights serves
all of them: the FLOPs grow by $B$ and the weight bytes do not, so
\begin{equation}
I_{\text{decode}}(B) \approx \frac{2B}{b_w},
\qquad
B^{*} \approx \frac{b_w\, I^{*}}{2}.
\label{eq:batch-ridge}
\end{equation}
Below $B^{*}$, adding a sequence costs almost nothing: the step time is set by
the weight bytes, and throughput grows linearly with $B$. Above $B^{*}$, the
step becomes compute-bound and its time grows with $B$. For BF16 weights on an
H100, $B^{*}\approx 295$; for four-bit weights computed in BF16, about 74; on
the M1 with its 0.63-byte weights, about 12--17.

We measured it. Decoding 1 to 32 sequences of Llama~3.2~3B together on the
M1, the aggregate rate rose from 20 to 176 tokens per second: \textbf{8.8$\times$
the tokens for 3.7$\times$ the step time} (measured, same record). An ideal
kernel would have delivered 32$\times$ the tokens for about twice the step
time (derived: at $B=32$ a step needs 206~GFLOP, 79~ms at the M1's peak,
against 41~ms to stream the weights once at 49~GB/s). The measurement follows
the model in aggregate and departs from it in detail, and the detail is
instructive. Equation~\eqref{eq:step-bound} gives the bound for each batch;
dividing the measured step by it shows where the time went:

\section{Prefill sits under the flat roof}

A prompt of $S$ tokens is processed in one forward pass. Every token needs the
same weights, so one pass over the weights serves all $S$: prefill is a batch
of size $S$ in equation~\eqref{eq:batch-ridge}. For a 512-token prompt on the
M1, the intensity is about $512\times 3.2\approx 1{,}600$~FLOP/byte, forty
times the ridge. Prefill should be compute-bound, and it is: the M1 processed
the prompt at \textbf{248 tokens per second}, about 1.6~TFLOP/s or 61\% of the
GPU's peak --- twelve times the per-token speed of decode on the same weights
(measured). \Chref{prefill-decode} takes this difference apart.

Three trends show up as soon as the table above is drawn to scale, as in
Figure~\ref{fig:ch03-rooflines}.

First, ridges are high. Data-center GPUs need hundreds of FLOPs per byte before
their tensor cores are the constraint, and each new precision doubles the
compute roof without moving the bandwidth roof: the B200's FP4 ridge is about
1,100~FLOP/byte. Low precision raises decode's intensity (fewer bytes per
weight) but raises the ridge in step, so the gap stays.

Second, bandwidth and compute do not grow together. From B200 to B300 NVIDIA's
listed dense FP4 throughput rises by half while per-GPU HBM bandwidth stays at
8~TB/s (NVIDIA HGX and GB300 NVL72 specifications, logged in
\texttt{research/FRONTIER.md}): the ridge moves right. Rubin then more than
doubles the bandwidth, to 19.2~TB/s per GPU \cite{nvidia2026verarubin}, while
its BF16 peak rises less than twofold, so its BF16 ridge falls to about 208 ---
but its dense FP4 figure nearly quadruples, and the FP4 ridge rises to about
1,800. Which way the gap moves depends on the precision an engine uses.

Third, the practical roofs sit below the datasheet. On the M1 the GPU's
streaming kernel reached about 70\% of nominal bandwidth, the CPU's about 89\%,
and the engine 85--92\% of what the GPU's streaming kernel reached. On an
H100, published measurements of batch-one decode on small models range from
at most half of the datasheet bandwidth for general-purpose engines to 78\%
for a hand-built ``megakernel'' that runs the whole forward pass as one kernel
\cite{spector2025megakernel}, and 51--86\% for automatically generated
megakernels across fourteen decode configurations of models from 0.6 to 13
billion parameters \cite{li2026forgemegakernel}. A roofline drawn from the
datasheet is an upper bound on an upper bound.

\section{What the roofline leaves out}

The roofline is a bound, not a prediction. The staircase in
Figure~\ref{fig:ch03-batch-staircase} and the lab below show five things it
does not model, each of which later chapters take up.

\emph{Tile quantization.} A matrix kernel works in fixed tiles; if its tile is
32 batch columns wide, nine sequences pay for thirty-two. \Chref{matmul-hardware}.

\emph{Occupancy.} A kernel must give the processor enough independent work to
hide memory latency. Decode attention, with one query per sequence, often
cannot, and then neither roof binds. \Chref{decode-attention}.

\emph{Fixed per-step costs.} Launching kernels, synchronizing and scheduling
take time that neither FLOPs nor bytes explain; at batch one they can be a
large share of a step. \Chref{kernel-languages}.

\emph{Bytes that do not batch.} Batching amortizes weights, not the KV cache:
every sequence reads its own cache every step, so at long context the
attention part of decode stays on the bandwidth slope however large the batch.
\Chref{kv-cache}.

\emph{The rest of the memory hierarchy.} There is a bandwidth roof for every
level of cache, not just for main memory. The lab's matrix kernel does about
160~GFLOP/s when four activation vectors (64~KB) fit in a core's 128~KiB
first-level data cache with room to spare, and 112--117 once sixteen or more
(256~KB and up) must stream from the shared second-level cache for every
weight row (measured; cache sizes read from the operating system). The kernel
is compute-bound at both batches, but against two different roofs. Tiling for
the cache hierarchy is \Chref{matmul-hardware}'s subject.

Use the roofline as a question to test. Count useful work and traffic at one named memory boundary, then compare measured time with both lower bounds. A large unexplained gap calls for another hypothesis, not a faster peak specification.

\emph{Explain} the table with Figure~\ref{fig:ch03-lab-roofline}. From one to
four vectors the step takes the same 4.5~ms: every step reads 268~MB at
60~GB/s and the extra arithmetic hides inside the wait. The two roofs predicted
the knee at $B^{*} = 2 \times 159/60.4 = 5.3$, and it falls between four and
eight. Every predicted step is within 4\% of the measured one up to $B = 128$
and within 7\% at 256, because the prediction uses the kernel's own rate at that
batch rather than the machine's peak. Getting there took two lessons that
belong in every benchmark. The first two runs, without a warm-up, measured the
first batch 20--25\% slow; repeating the small batches in one process showed
that the first passes over freshly written weights are slower than later ones on
this machine, so the lab now makes five untimed passes before it times anything.
And one run of four had a single point 30\% slow for no reason the lab can see;
the record keeps all of them, and it is why the lab takes the best of five
steps and the book reports ranges (\Chref{benchmarking}).

\emph{Break} it in two ways. Run with \texttt{--threads 1}: one core's kernel
does 22~GFLOP/s at one vector, about what one core's 44~GB/s can feed, so
arithmetic and memory tie at $B = 1$ and two vectors cost twice one --- but four
cost less than two (11.75 against 12.61~ms), because the kernel switches to its
four-vector path: a staircase of the same kind as the GPU's. Run with
\texttt{--mib 8}: the weights now fit in the 12~MiB second-level cache, the
lab's ``bandwidth roof'' becomes the cache's (67--81~GB/s instead of 52--61), and
the steps shrink to a tenth of a millisecond at one vector. The prediction then
misses by up to 70\% between two and sixty-four vectors and holds again only at
128 and 256: short steps expose costs that neither roof contains. Exercise~4
asks you to find them.

\HappenedSection{a kernel below both roofs}

The staircase is not noise; it is a design decision recorded in ggml's source.
In the Metal backend's operator code (\texttt{ggml/src/ggml-metal/ggml-metal-ops.cpp},
read at commit \texttt{389ff61d} and again at the measured build's commit
\texttt{d006858}, where the selection is unchanged), llama.cpp chooses among
three matrix kernels for K-quant weights by the number of batch columns:
\begin{itemize}
\item one to three columns: a matrix--vector kernel that handles one column per
pass over the weights --- so two sequences read the weights twice;
\item four to eight: a small-batch kernel (\texttt{mul\_mv\_ext}) that handles
three, four or five columns per pass, chosen by a \texttt{switch} on the
column count --- four and five in one pass, six to eight in two;
\item more than eight: a tiled matrix--matrix kernel dispatched in tiles of 64
weight rows by 32 batch columns, so any batch from nine to thirty-two costs one
column tile.
\end{itemize}
Each kernel is right for its regime and the thresholds are reasonable; the
source says of its parameters that it is ``not sure how optimal'' they are
``across all different hardware''. The measured steps in the table above follow
the selection exactly: the matrix--vector regime costs about one weight pass per
column, the small-batch regime 68--100~ms per pass, the matrix--matrix regime
150--180~ms whatever the batch. The lesson is general. A roofline says batching
is nearly free until the ridge. Whether it is free on your machine depends on
whether the kernel you are actually running reuses each byte it loads --- and
that is a property of code, not of the workload.

\FrontierSection{2026-09-27}

\emph{Asymmetric scaling.} The FlashAttention-4 authors describe Blackwell as a
machine on which ``tensor core throughput doubles while other functional units
scale more slowly'' and redesign attention around the units that did not
scale \cite{zadouri2026flashattention4}. The roofline's single compute roof is
becoming several: tensor-core math, other arithmetic, special functions,
shared-memory bandwidth.

\emph{Bandwidth is catching up at 16 bits, not at 4.} NVIDIA's Vera Rubin
NVL72 lists 288~GB of HBM4 at 19.2~TB/s per GPU, 4~PFLOP/s in BF16, and 35 dense
and 50 ``sparse'' PFLOP/s in NVFP4 \cite{nvidia2026verarubin}; the company's
January 2026 description of the platform had said ``up to 22~TB/s''
\cite{nvidia2026rubinblog}, so the shipped figure should be checked again
before it is relied on. Against the B200, the BF16 ridge falls from 281 to
about 208~FLOP/byte and the dense FP4 ridge rises from 1,125 to about 1,800.
AMD's MI355X sits between them, with 8~TB/s against 2.52~PFLOP/s in BF16 and
10.07 in MXFP4 \cite{amd2025mi355x}. Unless model architectures cut bytes per
token --- the subject of Parts~\ref{part:one-request}
and~\ref{part:architectures} --- the gap between decode and the ridge stays two
orders of magnitude wide on every one of them.
