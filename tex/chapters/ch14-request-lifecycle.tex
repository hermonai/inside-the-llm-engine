\chapter{The Request Lifecycle: Streaming, Cancellation and Terminal Ownership}\label{ch:request-lifecycle}\label{chapter-1-the-missing-half-of-ai}

\begin{ChapterIntent}
The decoder returns scores. A service must deliver text, react when a client leaves and
release the request's state. We will follow one reply through those events and define
the rule that it ends exactly once, even when completion, cancellation and failure race.
\end{ChapterIntent}

\section*{A reply has an owner and an ending}
Imagine two clients sharing the engine. One keeps reading; the other disconnects. The
departed client must not keep consuming model work indefinitely merely because its
neighbour is active. Start with the single-request event trace, then read the measured
cancellation case. Keep noticing a disconnect, deciding to stop, publishing the terminal
event and safely reclaiming memory as distinct steps.

\OpeningSection{Time to first token, measured}

Ask llama.cpp's server on the M1 for 128 tokens after a 200-token prompt, and
stream the answer. In five runs the first token arrived \textbf{741 to 762
milliseconds} after the request was sent; after that a token arrived every 40
milliseconds or so --- median gaps of 39.1 to 40.5~ms, with the slowest gap of
each run between 53 and 83~ms --- and the whole answer took about six seconds
(measured with Llama~3.2~3B; record \texttt{2026-09-24-m1-part3}). The server's
own accounting says where those first three-quarters of a second went: 738 to
757~ms of processing the prompt. Everything else --- parsing the request, scheduling it, sampling,
detokenizing, framing an event, crossing a socket --- fit in the few
milliseconds left.

Then the clients hung up. A client that closed its streaming connection after
its twentieth token left a server that noticed within 71~ms: the request's slot
was released after 21 tokens, one of them generated after the disconnect. A
client that asked for a long answer \emph{without} streaming and hung up after
three seconds left a server that behaved in two ways. On an otherwise idle
server, the request was cancelled within a second and a half. While another
client was streaming, it was not cancelled at all: the server kept generating
for the absent client for another 37 seconds, some 490 tokens nobody would
read, and stopped only when the other stream ended. The case study at the end
of this chapter explains why.

A request is not a function call. It is a small state machine with a clock
attached, and its contract --- what the client sees, when, what the engine
spends, and when it stops --- decides both the latency users feel and the
capacity the engine wastes. This chapter makes that contract explicit.

\Foundations{Ownership is a correctness property}{
A request is not merely a string passed to a model. It has a history, a cancellation
signal, output buffers and resources that must eventually be released. A state machine
declares which transitions are legal. A terminal state means no later token may be
published for that request; it does not prove all asynchronous device work has already
stopped. A single owner must coordinate publication and reclamation across that
boundary. Chapter~\ref{ch:kv-cache} identifies the largest mutable resource. Keep
transport disconnection, cancellation observation and safe memory release separate
while following the trace below.
}

\NapkinSection{Napkin math: what a stream costs the engine}

A streamed token becomes an event on the wire. In the measured build each
event on llama.cpp's own completion endpoint was about 122 bytes and on its
OpenAI-compatible chat endpoint about 306 bytes, for a token that carries three
or four characters of text (measured). At 25 tokens per second a stream sends
about 7.7~KB/s on the OpenAI-compatible endpoint, and ten thousand concurrent
streams send about 77~MB/s: real, but small next to the machines producing
them (derived). Each event also costs CPU for detokenization and
serialization, which can be moved off the scheduling loop
(\Chref{continuous-batching}).

The larger cost of a stream is its duration. While executing, and until safe
reclamation, a request holds engine resources. Its KV cache can dominate:
for Qwen3-8B at 4,096
tokens of context, 576~MiB (\Chref{kv-cache}). A request that should have been
cancelled but runs to completion wastes both, and the waste is easy to price:
\begin{equation}
W_{\text{orphan}} \approx n_{\text{left}}\;t_{\text{token}}
   \quad\text{slot-seconds},
\label{eq:orphan-waste}
\end{equation}
for $n_{\text{left}}$ abandoned output tokens and an approximately constant
$t_{\text{token}}$ seconds per token. The opening's orphan held a slot for
about 37 seconds. Do not insert its single-stream 40~ms gap here: two active
slots changed the step time. Use the orphan's own trace.

Memory waste also has a duration. If $M(t)$ is the request's resident cache
in bytes at time $t$, its abandoned occupancy is
\begin{equation}
A_{\mathrm{memory}}=\int_{t_{\mathrm{close}}}^{t_{\mathrm{release}}} M(t)\,dt
   \quad\text{byte-seconds}.
\end{equation}
A constant 576~MiB held for 37~s would cost 21,312~MiB\,s, or
20.8125~GiB\,s. This is an illustrative fixed-cache calculation, not a new
Qwen measurement; dense decoding normally grows the cache. If abandoned
requests arrived steadily at 0.5 per second and each held that fixed cache
for 37~s, their mean occupancy would be 18.5 requests and 10.40625~GiB.
This follows by counting the arrivals within one holding interval. A
fraction of arrivals is not a fraction of fleet capacity unless their
resource requirements and holding times also match.

\section{One prediction is not yet a service}
Suppose a model has just produced four numbers. One number is larger than the
others. What must happen before a user can read an answer?

Someone must interpret the index of that number, decide whether it means text
or termination, turn it into bytes, preserve their order, update the input for
the next prediction and release the request's resources. If the user cancels
halfway through, the computation must stop with an honest outcome. If the model
fails after emitting a prefix, that prefix does not become a successful answer
merely because some bytes reached the client.

This is the subject of an \Term{inference engine}: the running system around
the numerical prediction. Our first object will be one request, not an
architecture poster. We will run it, draw its state, change its stopping
condition and identify which component owns the final outcome.

\Callout{The boundary of this chapter}{The companion executable already contains
the four-token numerical fixture derived in \Appref{smallest-model}. Here we treat its
forward calculation as an opaque function and inspect the lifecycle around it.
We do not claim to have built a Transformer, trained a model or implemented a
network server. This keeps the first experiment reproducible on the current
checkout without relying on an obsolete fake-model API.}

\section{Run a request you can account for}
From the repository root, run:
\begin{verbatim}
cd code/mini-engine
cargo run -q -p engine0 -- --trace 'I like'
\end{verbatim}
The fixture vocabulary has four IDs: 0 is end of sequence, 1 is \texttt{I},
2 is \texttt{\textvisiblespace like}, and 3 is
\texttt{\textvisiblespace Rust}. The visible-space symbol makes the leading
byte explicit; it is not part of the spelling typed at the terminal.
These are identities, not quantities. The prompt becomes $[1,2]$.
The first forward pass uses its final ID, 2, and returns the scores
\begin{equation}
z^{(0)}=(-0.7,\;0.1,\;0.4,\;2.2).
\label{eq:first-logits}
\end{equation}
The largest score belongs to ID 3. Greedy selection therefore chooses
\texttt{Rust}. The next forward pass receives the prompt plus that new ID,
and its largest score belongs to ID 0. This time selection means stop.
The generated bytes spell \texttt{\textvisiblespace Rust}; the executable does not echo the
prompt as generated text.

Do not memorize the four numbers yet. \Appref{smallest-model} derives every multiplication.
For now, check three different observations in the trace: a model invocation,
a selected ID and a terminal outcome. They are not interchangeable.
There are two model invocations but only one emitted text token. The selected
EOS control ID ends the request; it is not appended as visible text.

The printed microsecond values will vary. They include instrumentation and
local runtime overhead. They are not benchmark results and should not be copied
into a performance comparison.

Now change only the prompt to \texttt{I}. Its first logits are approximately
$(0.2,0.2,0.2,0.1)$. Greedy selection breaks the leading tie by the smallest ID,

\section{Make the loop explicit}
Let $x$ be the input sequence of token IDs and let $g_t$ be the list of
\emph{visible generated tokens} before iteration $t$. The model $F_\theta$,
with fixed parameters $\theta$, produces a vector of logits:
\begin{equation}
z_t=F_\theta(x\mathbin{\|}g_t),\qquad
a_t=\operatorname*{arg\,max}_{i}z_{t,i}.
\label{eq:lifecycle-choice}
\end{equation}
The symbol $\|$ denotes concatenation. The vector index $i$ ranges over the
model vocabulary. The argmax needs a tie rule; our deterministic rule prefers
the smallest ID. Scores need not be positive, normalized or interpretable as
confidence.

For an ordinary text token, the next state is
\begin{equation}
g_{t+1}=g_t\mathbin{\|}(a_t).
\label{eq:lifecycle-feedback}
\end{equation}
For EOS, there is no next generation state: the loop selects a terminal
outcome. A maximum-token budget can terminate the loop before another model
invocation. Cancellation is checked at declared boundaries. These details
belong to the runtime policy rather than to the matrix calculation.

This recurrence is \Term{autoregression}. It says what feeds the next call;
it does not say that the model actually uses every earlier ID. Our fixture
looks only at the final input token. Part I's attention lessons constructed
genuine dependence on earlier positions. Keeping the history and using that
history are separate claims.

Here is the conceptual algorithm. It is pseudocode, not a second implementation
that silently replaces the tested Rust:
\begin{verbatim}
validate request and initialize request-local state
repeat:
    if cancellation is observed: choose Cancelled; leave loop
    if generated count reaches budget: choose MaxTokens; leave loop
    logits = model.forward(prompt + generated)
    if forward fails: choose Failed; leave loop
    validate logits and apply the request's selection policy
    if selected ID is EOS: choose EndOfSequence; leave loop
    append the selected text ID to request history
    send its token event
    decode its bytes and send any complete text prefix
send exactly one terminal outcome
\end{verbatim}
The implementation also checks cancellation after the model returns and
validates incomplete UTF-8 at completion. Error handling is not an optional
decoration on this loop: it determines which observable traces are legal.

\section{A state machine gives stopping a meaning}
An informal flag named \texttt{done} cannot explain whether a request succeeded,
was cancelled or failed. We need a state machine whose transitions are events.

\EngineFigure{request-states}{UML state-machine view of an admitted request in
the teaching runtime. The filled circle starts the lifecycle; the bullseye
ends it. Transition labels name events, guards in brackets and actions after
a slash. One finalizer resolves the outcome and sends one terminal event.
A failed request may already have emitted a prefix.}{fig:request-states}

Call the terminal outcome $o$. For a completed run with a working, non-panicking
in-process sink, our observable contract is
\begin{equation}
N_{\mathrm{terminal}}=1,\qquad
N_{\mathrm{text}}\geq 0,\qquad
\text{no output event follows the terminal event}.
\label{eq:terminal-contract}
\end{equation}
This is a contract for the teaching runtime's event stream, not a promise of
exactly-once network delivery. A disconnected client, process crash or retried
HTTP request introduces different failure domains.

\begin{proposition}[A single terminal owner simplifies the proof]
If every loop exit returns an outcome to one non-reentrant finalization path,
and that path emits one terminal event and then returns, the runtime cannot
emit two terminal events during an ordinary completed invocation.
\end{proposition}
\begin{proof}
Each loop exit transfers control out of the loop. Only the finalization path
contains the terminal emission. It executes once and returns without re-entering
the loop. Therefore there is one terminal emission, regardless of which exit
condition selected the outcome. This argument assumes ordinary control flow;
it does not claim recovery from process termination or a panicking callback.
\end{proof}

Why prefer this structure? If the sampler, model adapter and stream writer
each send their own final event, every pair of error paths must be checked for
double termination. Returning outcomes to one owner reduces the number of
places in which the invariant can be violated.

\section{Change one boundary at a time}
Keep the prompt fixed and run these experiments:

All three can expose the same generated prefix, a space followed by
\texttt{Rust}, but they have

\section{Follow three objects, not one vague arrow}
The request gives us three different journeys.

First, follow the \emph{token}. The prompt becomes IDs $[1,2]$, a model invocation
produces four scores, selection chooses ID 3, and ID 3 joins the next history.
The EOS ID is interpreted as control. A token is a vocabulary identity even
when its spelling happens to look like an English word.

Second, follow the \emph{byte}. Parameters occupy CPU memory. A forward call
reads them to compute temporary scores. On output, the tokenizer maps a
selected identity to a byte piece. A UTF-8 decoder may have to hold incomplete
bytes before emitting valid text. A token boundary is therefore not necessarily
a text-event boundary. \Appref{tokens} makes that failure concrete.

Third, follow the \emph{owner}. Immutable parameters can be shared conceptually;
generation history, decoder buffer, random state and terminal state belong to
one request. Sharing the weights does not grant permission to share mutable
history. The current engine executes synchronously, but choosing honest
ownership now gives later concurrency a tractable contract.

\EngineFigure{parameter-owners}{Two hypothetical requests read the same immutable
parameters while retaining distinct histories and activations. Dashed edges
are read-only borrows, not copies or implemented concurrent execution.}{fig:parameter-owners}

Training changes model parameters according to a learning rule. Inference
normally reads the fixed parameters while changing request-local state.
\emph{The weights do not change} does not mean \emph{nothing is mutable}. The
history grows, the decoder buffers bytes, counters advance and a sampled
request advances its own pseudorandom state.

\section{Measure a distance between named events}
Suppose an instrumented request records arrival $t_a$, execution start $t_s$,
first emitted token $t_k$, first text $t_b$ and terminal event $t_f$. These
timestamps must share a clock domain before we subtract them. Define
\begin{align}
T_{\mathrm{wait}}&=t_s-t_a,\\
T_{\mathrm{first\ token}}&=t_k-t_a,\\
T_{\mathrm{first\ text}}&=t_b-t_a,\\
T_{\mathrm{request}}&=t_f-t_a.
\end{align}
Waiting, computation and byte assembly now have different observable
boundaries. A request that selects EOS immediately has no first emitted text
token; its first-token and first-text measurements are absent, not zero.

\EngineFigure{request-timeline}{An illustrative clock, not a benchmark.
The first-token and first-text distances begin at arrival but end at different
events. A tokenizer can delay text until a byte sequence is complete.}{fig:request-timeline}

For the synthetic timestamps $(t_a,t_s,t_k,t_b,t_f)=(0,3,11,14,25)$ milliseconds,
the four distances are $3$, $11$, $14$ and $25$ milliseconds. The three
milliseconds between first token and first text do not prove that model
execution slowed down; they may be time spent waiting for another byte piece.

Likewise, aggregate output tokens per second are not the inverse of one
request's first-token latency. A batched service may process many requests
together, improving aggregate work per unit time while increasing an
individual request's wait. We will not call a measured throughput increase a
latency improvement without measuring that latency.

\section{Where the small engine stops being enough}
Our runtime rebuilds a history and calls a tiny CPU model synchronously.
There is no scheduler, persistent KV state, socket, retry protocol or device
transfer. Those omissions establish later problems rather than hiding them.

When many requests arrive, admission must decide which can fit. When prompts
have different lengths, a scheduler must balance prompt work with incremental
decode work. When a model uses attention, history-related state consumes
memory; reusing it requires layout, lifetime and validity rules. When output
crosses a network, a slow receiver creates backpressure and a disconnect
requires cancellation to propagate through the running computation.

The terminology should grow with those mechanisms. A \emph{model artifact}
is persistent data. A \emph{loaded model} is that data interpreted in a runtime.
An \emph{engine} executes and controls requests. A \emph{server} exposes an
interface. An operated \emph{service} adds deployment, resource limits,
observability and failure policy. Packaging the first as a file does not
implement the other four.

Production comparisons in later chapters are source-pinned case studies,
not substitutes for this construction. A repository containing a paged backend
does not prove the default request path uses it. A supported tensor type does
not prove a whole model family works. We will follow actual calls and data
when making those claims.

\section{What we have established}
We can now explain why one request needs both numerical prediction and a
lifecycle. We have observed a real selected token, feedback into another
prediction, an immediate-EOS counterexample and three distinct ways to stop
after the same visible prefix. We have named ownership and timing boundaries.

How text becomes an ID, and how an ID can fail to become readable text
immediately, was constructed in \Appref{tokens}. We now place that byte
buffer inside a service, where other requests and asynchronous work change
what it means to own the next event.

\section{Admission establishes an identity before execution}
Suppose request 7 asks for a 200-token prompt and at most 128 generated
tokens. Before computing its first layer, the service must interpret that
description. It checks that the selected model exists, the token IDs belong
to its vocabulary, the prompt fits its supported context, the output budget
is valid and the caller may use the resources. A malformed request is a
rejection, not a model failure after admission. The chapter's one-terminal
contract applies to admitted engine requests; the frontend must separately
return an honest rejection to callers who never entered that domain.

Admission is not necessarily reservation of the entire future KV cache.
One design reserves a maximum; another reserves initial blocks and grows
them as positions are evaluated. Both need an explicit capacity policy.
Accepting a request into a bounded waiting queue says it may wait. Accepting
it without a limit and hoping memory becomes available says much less.
Scheduling under pressure is developed in \Chref{scheduling}; here we need
only a stable identity and a clear owner while a request is waiting.

Give the request a server-created key. A client-supplied label can help trace
retries, but it is not automatically a unique execution identity. Two
simultaneous requests labelled \texttt{7} must not share history or allow one
client's cancellation to stop the other. In the synchronous lab,
\texttt{Engine::admit} rejects duplicate active identities before adding a
second owner. Its numerical ID is sufficient because the harness never
reuses IDs within a scenario. That is a teaching assumption, not a safe
distributed naming scheme.

A pooled service may identify an execution by a slot and a generation:
$(7,12)$ means the twelfth use of slot seven. When that slot is reused as
$(7,13)$, a delayed cancellation for $(7,12)$ must not affect it. A work
ticket also needs a serial number within the generation; a duplicate reply
from step zero must not retire step one. None of these numbers encode a
token. They identify the computation entitled to mutate the request.
The protocol extension tests both stale generations and stale serials.

\EngineFigure{request-serving-components}{Conceptual component layout.
The owner serializes request decisions; a bounded data queue carries output,
while cancellation bypasses that queue. Shared weights are read-only.
This is a service design, not a claim that the synchronous fixture implements
these components as separate processes.}{fig:request-serving-components}

Read the layout from left to right. Validation establishes the request key.
The owner submits numerical work with that key and receives a matching
completion. Sampling and byte assembly produce a data event. The writer
drains those events toward the connection. Read it from right to left as
well: a failed write reports the loss of the consumer, and that control
message must reach the owner even when no data can move forward.

There is an admission failure before the first model call that a steady-state
decode test misses. A frontend might register an output queue, then await
submission to an engine process. Cancellation during that await leaves a
partially constructed request unless cleanup already knows its identity.
Store the ownership record before the first interruptible operation.
If submission has not occurred, remove the local registration; if it may
have occurred, arrange an abort using that same identity and await the
appropriate acknowledgement. A local exception handler cannot infer that
remote acceptance never happened merely because its await did not return.
This is a design obligation; our one-process lab does not implement remote
admission or prove a distributed rollback protocol.

\section{A notification is not a predicate or a deadline}
A condition variable lets a waiting thread sleep until another thread
announces that shared state may have changed. The announcement does not
identify the result it needs. On waking, the thread must examine a
\Term{predicate}: in this lab, whether the queue contains a result for its
request key. Several handlers can wake for a result belonging to one of
them. A wake without a matching result is not a reason to emit text or stop.

That distinction explains the cancellation failure. Let the timeout slice
be an illustrative 100~ms and let a neighboring request publish at 4, 8,
12~ms and so on through 2,000~ms. The abandoned handler starts its first
wait at zero. At 4~ms it wakes, finds no result for itself, then starts
another full 100~ms wait. The same sequence repeats. The last wake at
2,000~ms moves the timeout to 2,100~ms. A client that left at 350~ms can
therefore remain unobserved for approximately 1,750~ms.

\EngineFigure{request-wait-deadlines}{Deterministic teaching schedule, in
illustrative milliseconds. Restarting an idle slice after unrelated wakes
pushes the check to 2,100~ms. A fixed first deadline remains 100~ms, and a
disconnect event at 350~ms does not depend on either timer.
Thread scheduling can change the measured boundaries.}{fig:request-wait-deadlines}

An \Term{idle timeout} asks whether nothing has happened for an interval.
A \Term{deadline} asks whether the current clock has reached a fixed time.
For a fixed deadline $d_{\mathrm{check}}$, the remaining wait at time $t$
is $\max(0,d_{\mathrm{check}}-t)$. Repeated wakes shorten that remainder
instead of resetting it. When the deadline arrives, check cancellation
and choose the next deadline. Periodic checking then has a configured
observation interval, plus scheduling and engine propagation delays.
It does not make cancellation instantaneous.

The independent integer-time test enumerates every subset of eight possible
wakes. It compares the repeated-slice implementation with the first
interval containing no earlier wake. For this deterministic model, expiry
wins a tie with a notification at the exact deadline. The threaded Rust
condition variable has operating-system scheduling rather than that
chosen tie rule. Separating the two avoids using a nondeterministic race
to establish an exact arithmetic boundary.

Event-driven cancellation removes this dependence on unrelated result
traffic. The disconnect becomes a control event in its own right. The
handler stops waiting for useful output and posts an abort. The engine still
needs to receive that abort before its next cooperative boundary.
In the lab, the worker drains commands before each step, so an event can
arrive just after the drain and wait for the next tick. The experiment
measures this handoff; it does not interrupt the numerical work inside a
real device kernel.

\section{Terminal publication and memory retirement are different clocks}
Now imagine a device step that has already been submitted for $(7,12)$.
Cancellation arrives while that step is running. The owner can prevent
another submission and decide that no further token will be published.
It cannot infer that the device has stopped reading the request's cache.
Freeing or reassigning those bytes immediately can corrupt another request.

Separate a \Term{logical ending}, which fixes the output outcome, from
\Term{physical retirement}, which establishes that no remaining work can
access the resource. A completion fence is evidence about device work;
an HTTP connection close is evidence about a consumer. These events
answer different questions. \Appref{gpu} introduced this
submission-versus-completion distinction for one kernel. Here it becomes
a request-lifetime rule.

\EngineFigure{request-cancel-retirement}{UML sequence for the executable
protocol model. Cancellation fixes one outcome while work is outstanding.
The late reply acknowledges retirement but its text is discarded.
Only then can the device lease be reused. Lifelines are roles, not four
implemented network processes or a measured GPU trace.}{fig:request-cancel-retirement}

Follow the decisive order. The owner issues a work ticket, then selects
Cancelled. Its logical terminal metadata can already be read. When the
matching work reply arrives, the owner acknowledges retirement but refuses
to publish its payload. Only after the outstanding ticket is removed may
the modeled device lease be reused. Output metadata can have a longer host
lifetime than the released cache; the implementation must not destroy that
metadata merely because the device bytes are free.

The small protocol model allows one outstanding ticket per request. For a
real engine with several dependent operations, retirement requires all
relevant references or a fence covering their execution. A cache block
shared by other requests also needs their references accounted for.
The model deliberately omits those mechanisms. Its local reuse predicate is
\begin{equation}
\text{reusable} \iff
  (\text{outcome selected})\land(\text{no outstanding ticket}).
\end{equation}
That predicate is tested after every command in short exhaustive schedules.
It is not a substitute for a production allocator's proof.

Two stopping causes can arrive close together. If EOS has already been
committed as the outcome, a later cancellation does not create a second
ending. If cancellation has been committed first, a later EOS reply must
not change the published status. The owner makes this irreversible decision
at a \Term{linearization point}: one precise state update that competing
operations must observe consistently. In the protocol model,
\texttt{finish} sets an optional outcome only when it is empty.
Its first successful call wins.

The actual single-owner decision in \texttt{ownership.rs} is short enough
to inspect. Returning \texttt{false} leaves the first outcome intact:

This precedence differs from guessing which event happened first according
to clocks on separate machines. The contract is about the order accepted by
the owner. In an asynchronous service, one actor can serialize decisions;
a shared-state design may require locking or an atomic transition.
The lab exercises ordinary single-owner calls, not lock-free correctness.
An implementation should not claim a stronger concurrency guarantee from
those tests.

\section{A slow reader must not block the stop signal}
Suppose a model emits 25 data events per second while a client drains five.
An unbounded queue grows by 20 events each second. If the queue holds at
most 64 events, it fills from empty in approximately
$64/(25-5)=3.2$~s under this illustrative constant-rate model.
At 306 serialized bytes per event, 64 events contain 19,584 payload bytes,
before queue objects, framing buffers and allocator overhead.
An event-count limit is not a byte limit when event sizes differ.

\Term{Backpressure} makes the producer respond when the consumer cannot
keep up. A bounded queue can pause that request, combine deltas, spill to
a deliberately bounded store, or cancel under a documented policy.
There is no universally correct choice. Combining deltas delays when the
reader sees text; pausing retains its KV state; cancelling loses an answer
that may still be valuable. The important first step is to bound what can
grow and identify who pays for the wait.

\EngineFigure{request-backpressure-flow}{Activity diagram for the protocol
extension. A full data queue prevents new submission, not cancellation.
Natural completion drains queued text before one terminal delivery.
Cancellation or failure discards unsent text; already delivered prefixes
cannot be recalled. The teaching queue bounds events, not encoded bytes.}
{fig:request-backpressure-flow}

A common failure is to put cancellation behind data in the same full queue.
The producer waits for space; the consumer has left; the abort cannot enter.
Use a control path that is not blocked by output capacity. Similarly, if
the only terminal indication is another data item, a full queue can prevent
the owner from recording the outcome. The protocol lab stores terminal
metadata separately from its bounded data deque. A responsive receiver can
drain natural output and then receive one terminal event without requiring
another data slot.

Cancellation chooses a different policy in that model: queued but unsent
text is discarded. Any outstanding work still retires, and its late payload
is suppressed. This does not erase a prefix already read by the client.
For a natural budget or EOS ending, the existing deque drains before the
terminal is delivered. Both policies are explicit, tested and intentionally
small. The earlier synchronous engine sends callbacks directly and does not
have this output queue.

Do not block an entire batch behind one request's slow writer. A per-request
queue and scheduling eligibility can separate the stalled consumer from
its neighbors, though retained KV still consumes shared capacity. Nor can
we assume a successful socket write means the application consumed the
bytes: it may only mean a local transport buffer accepted them. Observability
should distinguish engine generation, queue publication, writer acceptance
and client receipt when the last boundary is actually available.

\section{Test traces, then diagnose the timeline}
The terminal invariant is a \Term{safety property}: something forbidden,
such as a second terminal or text after termination, never occurs.
Eventual release is a \Term{liveness property}: something required
eventually occurs. A request that never produces any event satisfies
\emph{no text after terminal} vacuously but serves nobody. Test both kinds.
The deterministic engine uses finite budgets so admitted scenarios finish.
The threaded replay separately observes close-to-release delay.

For a useful trace, record the server execution key, event sequence number,
event type and local monotonic timestamp. Do not merge independently timed
records into one apparent total order without a correlation method.
The minimum cancellation timeline is: consumer gone, frontend notified,
abort enqueued, engine observed, outcome selected, work retired, resources
released. A long gap between the first two suggests detection or transport
trouble. A long gap after enqueue suggests a blocked command path. A long
retirement gap can be legitimate outstanding work rather than lost cancellation.

The property checker now rejects mixed request identities and status replies
in a generation trace. It also rejects a natural completion after a
cancellation recorded for a still-running request. Its earlier checker could
accept that completion if it matched the natural oracle, overlooking the
stronger cancellation obligation. The new negative test constructs precisely
that plausible wrong trace.

Tests need not guess sleep durations to force an order. The protocol tests
submit a ticket, cancel, inspect reuse, retire the ticket, then inspect output.
Another test fills both output slots before cancelling. Another changes the
slot generation before submitting a delayed old reply. These controlled
orders establish the relevant boundaries more clearly than an assertion
that a wall-clock timeout happened to be short.

Finally, count the numerical and output populations separately. The
four-token fixture performs two forward calls for one text token. A token
budget may stop without an EOS prediction. A stop-string implementation may
buffer text that is generated but never exposed. Cancelled work may have
completed on the device without any token being published. A benchmark that
uses one counter for all four populations can call wasted work useful
throughput. \Appref{reproducing} gives the cohort accounting needed to
keep that distinction visible.

\HappenedSection{cancellation that did not reach the model}

The orphaned request of this chapter's opening was not an accident of the
measurement. \textbf{DEFAULT, pinned case:} llama.cpp's server, at the commit
of the measured build, handles a
non-streamed request on an HTTP thread that waits for the request's result. It
waits in slices of one second, and only when a slice expires with no result
does it ask the socket whether the client is still there; if the client has
gone, it posts a cancellation that releases the request's slot
(\texttt{HTTP\_POLLING\_SECONDS} in \texttt{tools/server/server-context.cpp}
and \texttt{recv\_with\_timeout} in \texttt{tools/server/server-queue.cpp} at
commit \texttt{d006858}; \cite{llamacpp2026cancelqueue,llamacpp2026cancelcontext}).
The waiting threads of all requests share one
condition variable, and every result delivered for \emph{any} request wakes
them all; a woken thread that finds nothing for itself starts a fresh
one-second wait. While another client is streaming --- a result every 40~ms ---
no thread's wait ever expires, so no thread ever checks its socket. The
measurement showed exactly that: cancelled within a second and a half on a
quiet server, never cancelled while a neighbor streamed.

The first attempt to measure this found it by accident. The measuring script
polled the server's slot-status endpoint every 20~milliseconds to see when the
request would be released; each poll produced a result, each result reset the
waiting thread's timer, and the observer kept alive the request it was
observing. The measurement was rerun with a poll every 1.5 seconds, longer
than the server's slice, and with a separate streaming client as the
neighbor --- which is when the mechanism became clear. Both runs are in the
record.

For disconnect detection, vLLM makes the opposite design choice.
\textbf{DEFAULT, pinned handler path:} its decorated API handlers are
wrapped so that each request's work races a listener for the HTTP server's
disconnect message; whichever finishes first cancels the other, and the
engine aborts the request when its generator is cancelled
(\texttt{vllm/entrypoints/serve/utils/api\_utils.py} and
\texttt{vllm/v1/engine/async\_llm.py} at commit \texttt{bcdacfc};
\cite{vllm2026cancelhandler,vllm2026cancelengine}).
The decorator hands disconnect listening to the streaming response once the
handler returns that response. Its scope assumes the request body has
already been read. Disconnects here are events rather than idle-result polls.
This establishes an observation path, not cancellation correctness at
every admission boundary.

\FrontierSection{2026-10-03}

The ASGI HTTP specification makes two signals relevant: a disconnect receive
event and an exception when sending on a closed connection. Concurrent sends
can fail before the disconnect event is received, and older implementations
need not provide the newer send-exception behavior
\cite{asgi2026disconnect}. An owner should converge both supported
signals on one stopping decision. Receiving either does not establish that
a downstream engine process has reclaimed its resources.

Event-driven detection does not remove partially completed admission.
An upstream report, issue 57061 opened on 15 September 2026, describes local
request-state retention when cancellation interrupts engine submission
\cite{vllm2026admissioncancel}. This is a reported failure, not a
reproduction by this book or a claim about every current deployment.
The pinned \texttt{bcdacfc} code independently exposes the relevant
boundary: \texttt{\_add\_request} registers locally before awaiting
engine submission, while \texttt{generate} guards abort with
\texttt{q is not None}; that collector is assigned only after
\texttt{add\_request} returns. The multi-sample branch has a separate
exception cleanup path. The inference is narrow: read and test each
admission branch rather than treating an event listener as a complete
cleanup proof. The lab's protocol extension illustrates ownership rules;
it does not reproduce this vLLM issue.

The preceding API check, dated 24 September 2026, also illustrates a
different lifecycle policy. OpenAI's Responses API
streams typed events --- a response created, text deltas, a completion or an
error --- rather than bare tokens \cite{openai2026streaming}, and its
background mode decouples a request from the connection that started it:
a long response keeps running when the client disconnects, is cancelled only
by an explicit, idempotent cancel call, and can be resumed from a sequence
number if the stream drops \cite{openai2026background}. This historical
source check is retained, not silently redated by the present pass.
Connection-independent work is useful when explicitly requested. It is
not equivalent to an accidental orphan in a connection-bound service.
