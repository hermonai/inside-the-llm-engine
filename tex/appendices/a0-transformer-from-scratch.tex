\section*{One prediction, five different objects}
Imagine a vocabulary containing three tokens: \texttt{red}, \texttt{blue}
and an end token. This is an illustrative vocabulary, not a real tokenizer.
For a particular history, suppose the model produces
\[
 \mathbf{z}=[\log 2,\;0,\;0]\in\mathbb{R}^{3}.
\]
These scores are \emph{logits}, not probabilities. At temperature one,
softmax exponentiates and normalizes them:
\[
 p_i=\frac{\exp(z_i)}{\sum_{j=1}^{3}\exp(z_j)},\qquad
 \mathbf{p}=[1/2,\;1/4,\;1/4].
\]
The entries are nonnegative and sum to one. Greedy selection chooses
\texttt{red}. Sampling instead draws from this distribution; a fixed uniform
draw of $0.6$ selects \texttt{blue} when intervals are ordered as written.
This draw is a test input, not a statement about a production generator.
The selected token is appended to the history. The next evaluation can
produce different scores because its input changed, even though every
learned weight is unchanged.

The five objects are history, weights, logits, probabilities and chosen
token. Confusing any pair creates a different bug. Token IDs cannot be
averaged as though they were embeddings. Logits cannot be read as
probabilities. The highest-probability token is not the only legal sample.
Output text need not coincide with one token's bytes: detokenization may
buffer an incomplete character. A model distribution is not a truth
certificate; confidently predicted text can be false.

\section*{What the model learned, and what the engine does}
Training adjusts parameters so that correct continuations receive more
probability under a chosen objective. Inference evaluates those parameters
on a supplied history. A chat interface adds an input template and role
conventions before evaluation. A service adds admission, scheduling,
cancellation and delivery. The chat box is not the mathematical interface.

For tokens $x_1,\ldots,x_T$, an autoregressive model factors sequence
probability into conditional probabilities:
\[
 p(x_1,\ldots,x_T)=\prod_{t=1}^{T}p(x_t\mid x_1,\ldots,x_{t-1}).
\]
The first position follows the model's start convention. This is a
probability factorization, not an implementation schedule. Known prompt
positions can be evaluated together under a causal mask. Unknown sampled
tokens ordinarily cannot: each choice becomes part of the next conditional
input. That is the dependency behind the prefill/decode distinction.

An embedding replaces an ID by a learned vector. Decoder layers transform
it using permitted context. A final projection produces one score per
vocabulary entry. Attention mixes value vectors using query--key scores;
a feed-forward network transforms features at each position. Normalization
controls scale, residual connections add updates to incoming representations,
and position information distinguishes order. None of this means the engine
searches a database of complete sentences.

\section*{Predict, compute, challenge}
Change the first logit from $\log 2$ to $\log 4$. The exponentiated scores
become $[4,1,1]$, so probabilities become $[2/3,1/6,1/6]$ (derived).
The same draw $0.6$ now selects \texttt{red}. A deterministic sampler test
is not a claim that two distributions produce identical samples.

Next ask what a cache may remember. Earlier keys and values can be reused
for an unchanged causal prefix; the newly sampled token has not yet had
its own keys and values evaluated. Mark this boundary before implementing
append. Then change an assumption: use another adapter, reset positions
or change tokenization. Matching visible text no longer proves matching
state. These counterexamples lead to cache identity and differential testing.

\texttt{scripts/check-foundations.py}. It needs no model download.
It checks examples, not language quality or industrial performance.
