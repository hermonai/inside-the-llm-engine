\chapter{Reproducing the Book's Measurements}\label{app:reproducing}
\begin{ChapterIntent}
Reproduction executes the stated experiment and compares observations;
it does not demand identical speed from different hardware. This chapter
routes readers to canonical evidence rather than copying raw logs.
The foundational arithmetic runs without a model download.
\end{ChapterIntent}

\section{Begin with a question that can be wrong}
Suppose you believe caching should make the decoder faster. That
sentence leaves several questions open. Faster for which prompt
length? Does the timer include setup? Are the cached and uncached
paths producing equivalent logits? How many tokens are generated?
An experiment becomes useful when those questions have answers.

For the Part I decoder, first test the semantic claim: at each
prefix, cached and full-prefix execution produce matching logits.
Only then ask the performance question. This ordering prevents an
incorrect shortcut from winning a benchmark by doing less than the
required computation.

A good record states the prediction before the result. For example:
as the prefix grows, reusing earlier layer state should avoid
increasing amounts of recomputation. That prediction can fail to
produce a practical speedup if bookkeeping overhead dominates at
tiny sizes. Keeping the negative result teaches something about
the implementation and workload.

\section{State the hypothesis}
Batching reuses weights is a mechanism claim. A batch improves goodput
at a latency target is a workload claim requiring arrivals, lengths and
an acceptance rule. An experiment should be able to falsify the latter,
not merely print an attractive throughput.

Measured numbers name hardware, software revision, model bytes, precision,
workload, warm-up, repetitions and statistic. Derived numbers name inputs
and assumptions. Illustrative numbers teach without claiming a device
result. A vendor peak stays a specification when inserted into a formula.

\section{An auditable timestamp trace}
Consider an illustrative request with times in milliseconds from intended
arrival: client send at 3, admission at 7, first delivered token at 17,
later tokens at 25 and 40, terminal event at 44.
TTFT from send is $17-3=14$ ms; from intended arrival it is 17 ms.
The first definition excludes 3 ms of client queueing.

Inter-token gaps are 8 and 15 ms. Mean time per output token excluding
the first is $(40-17)/(3-1)=11.5$ ms.
Terminal latency from send is $44-3=41$ ms. Using terminal time in the
token-gap formula would charge terminal handling to decode. Neither clock
is wrong; an unnamed boundary is wrong. A one-token response has no
inter-token sample under this convention.

The percentile of pooled gaps need not equal the percentile of per-request
mean gaps. State the population. Excluding failed or timed-out requests
can improve the reported tail while the service deteriorates.
Report errors and useful completed output alongside latency.

\section{Draw the clock before calculating latency}
The illustrative trace earlier names seven different events. Put them
on one line before reducing them to a statistic.
\EngineFigure{foundation-measurement-clock}{Illustrative client and
request timestamps in milliseconds. TTFT from send is 14 ms, while
the two delivered-token gaps are 8 and 15 ms. The terminal event
occurs after the last token and is not another token arrival.}
{fig:foundation-measurement-clock}

The intended arrival at zero expresses the workload schedule.
The actual send at three reveals a client-side delay. Admission at
seven describes a server boundary. The first token at seventeen
describes an observed delivery. These timestamps should not be
substituted for one another because they happen to be close in a
particular run.

Run the trace arithmetic:
\begin{verbatim}
python3 code/foundations/lesson.py measurement
\end{verbatim}
The program reports TTFT 14 ms, gaps 8 and 15 ms, mean gap 11.5 ms
and terminal latency 41 ms. Now deliberately use the terminal event
as the last token: $(44-17)/2=13.5$ ms. The arithmetic is valid,
but it answers a different question and mislabels the result if
reported as mean delivered-token gap.

Avoid subtracting timestamps from unsynchronized machines as though
they share one clock. End-to-end duration can be measured on the
client's monotonic clock. Internal stage durations can be measured
within their own clock domain. Combining them requires an explicit
clock and synchronization method.

\section{One run is an observation, not a distribution}
Repeated runs reveal variation from scheduling, caches, temperature,
background work and the workload itself. Report a central value and
a measure of spread appropriate to the question. Keep the raw
observations so another reader can recompute the summary.

For the illustrative times $[9,10,10,11,60]$ ms, the median is 10 ms
and the mean is 20 ms. The slow run is part of the data. Removing it
because it makes the chart unattractive changes the claim. If an
external interruption invalidated a run, state the exclusion rule
and retain the excluded observation with its reason.

Do not infer a reliable extreme-tail percentile from a handful of
samples. Percentile conventions also differ in interpolation and
rounding. State the method when exact reproduction matters. For a
service, retain failures and timeouts in the workload accounting;
otherwise the system can appear faster by failing its slowest requests.

\section{Warm means something specific}
A process can be new while the operating system still holds its
checkpoint pages in memory. A model can be loaded while its kernels
are not yet compiled. A kernel can be compiled while a particular
graph shape has not been captured. These are different warm states.

Describe which work has already happened before starting the timer.
For an isolated kernel experiment, preallocated buffers and compiled
kernels may be appropriate. For startup latency, excluding them
would remove the very cost being studied.

Do not flush shared caches, change system protections or download
large checkpoints merely to make an experiment look more controlled.
Use the available environment, document its limits, and separate
the question you can answer from the one that needs another setup.
A reproducible limitation is better evidence than an undocumented
intervention.

\section{A load generator can change the workload}
In a closed-loop test, a client sends new work only after earlier work
finishes. A slow service therefore receives fewer new requests.
In an open-loop test, arrivals follow an external schedule, so a
slowdown can build a queue. Both are useful, but they model different
users and produce different latency distributions.

The load generator can also fall behind. Record intended arrival,
actual send and observed completion so that client delay is visible.
If the client stops creating work during a server stall, measuring
only sent requests can hide the waiting that a real arrival stream
would experience.

For the same reason, report both throughput and useful completed
work under a latency target. A larger batch can raise aggregate
tokens per second while making each user wait longer. The systems
chapters will call useful work meeting the target \emph{goodput}.
The definition includes the acceptance rule; it is not another name
for the largest throughput number on a chart.

\section{Control machine state without changing the question}
Arrival feedback is one control; machine state is another. Record
compilation, graph capture, cache state, thermal conditions and competing
work alongside the earlier warm-up and repetition rules. A fresh process
does not establish a cold OS file cache. Do not improve the reported
distribution by silently removing a slow observation or withholding arrivals.

Preserve a slower optimization or failed oracle as evidence. Reproduction
and layout inspection do not promote a chapter to VERIFIED; that additionally
requires independent technical review.

\section{Leave a record another reader can follow}
A compact record should let someone reconstruct the experiment
without guessing. Include the code revision, model identity,
hardware and software versions, command, input construction,
timer boundaries, warm-up, repetitions, summary method and raw
outputs. Separate facts you measured from specifications and
derived estimates used to interpret them.

When a command has several modes, record the arguments actually
used. A source file containing a GPU variant does not prove the
reported run used it. Similarly, a passing unit test does not prove
a production request reaches the tested code path.

Preserve the result when an optimization loses. Explain the initial
hypothesis, the changed variable and the observed outcome. That
record can be more valuable than a successful benchmark because it
shows where an apparently sensible cost model was incomplete.

\section{Run cheap checks before expensive measurements}
From the repository root:
\begin{verbatim}
python3 scripts/check-foundations.py
make textbook-check
(cd code/mini-engine && cargo test --workspace)
\end{verbatim}
These check the worked examples, book contracts and teaching engine.
They do not establish benchmark performance. For a chapter experiment,
read its README and record, inspect the arguments, run the oracle, then
time the workload. Keep raw stdout and stderr including failures.
Record model content hashes and source revision, not only mutable aliases.

Do not download additional checkpoints, purge shared caches or disable
system protections as an unannounced part of reproduction. State any
unavailable hardware or unperformed experiment explicitly.

\section{Analyze a trace, then build an experiment}
Before leaving Part I, build a complete small experiment. We will
first analyze a request trace with no timing noise, then time an
integer computation whose outputs can be checked exactly.

\subsection{Choose a cohort and keep its failures}
A cohort is a declared collection of requests. For this teaching
example, all four requests have intended arrivals in the interval
from 0 to 40 ms and have reached a terminal event by 40 ms.
Every timestamp is on one illustrative client clock. The observation
includes the cohort's drain; it is not a rolling production window.

\begin{center}
\begin{tabular}{@{}lllll@{}}
\toprule
Request & Planned/send & Delivered tokens & Terminal & Outcome\\\midrule
A & 0/0 ms & 5, 9, 13 ms & 14 ms & correct success\\
B & 2/8 ms & 12, 30 ms & 32 ms & correct success\\
C & 4/4 ms & 15 ms & 40 ms & timeout\\
D & 6/6 ms & 8, 10 ms & 11 ms & incorrect success\\
\bottomrule
\end{tabular}
\end{center}

There are eight token deliveries on the wire. Only five belong to
correct, successfully completed requests: A's three and B's two.
The partial token from C did not turn its timeout into a successful
response. D's terminal status says success, but the correctness check
rejects its result. A service metric must decide how partial output
is valued; this chapter counts useful tokens only from correct,
complete responses.

Choose a teaching acceptance rule: first-token latency from intended
arrival must be at most 10 ms, and each request's mean delivered-token
gap, when defined, must be at most 10 ms. A has TTFT 5 ms and mean
gap 4 ms, so its three tokens qualify. B has TTFT $12-2=10$ ms
but mean gap $30-12=18$ ms, so its two do not. A one-token successful
response would have no mean-gap sample; this rule applies only its
TTFT test rather than inventing a zero gap. That convention belongs
in the rule, not in a silent implementation shortcut.

Over the 0.04 s observation, raw wire throughput is
$8/0.04=200$ tokens/s. Correct-completion throughput is
$5/0.04=125$ tokens/s. Accepted useful throughput is
$3/0.04=75$ tokens/s. All three calculations are valid, but their
numerators answer different questions. Reporting the first under
the third's name hides both failure and poor latency.

\EngineFigure{foundation-cohort-gates}{The executable teaching
cohort's accounting gates. Eight delivered tokens become five
correct-completion tokens, then three accepted tokens under the
stated latency rule. Rejected output remains in the failure record;
the gates do not erase observations.}{fig:foundation-cohort-gates}

Do not average per-request token rates to obtain aggregate throughput.
Sum the accepted output over the common observation duration.
For a long-running service, declare arrival windows, warm-up windows,
unfinished requests and drain policy separately. This small cohort
requires complete drain and rejects an input trace extending past
its observation end. It does not estimate censored completion times
or pretend an unfinished request disappeared.

\subsection{The load generator is part of the experiment}
Request B waited six milliseconds between its intended arrival and
actual send. Its first token arrived four milliseconds after send,
but ten after intended arrival. With a 5 ms first-token target,
a send-based calculation would admit B while the declared
arrival-based rule rejects it. The missing time was not removed
from the user's schedule by choosing a later start event.

Workload feedback can hide more waiting. Consider a deterministic
single-worker model with five service demands of $[4,4,20,4,4]$ ms.
Externally planned arrivals at $[0,4,8,12,16]$ ms produce completions
at $[4,8,28,32,36]$ ms. The fourth request arrives at 12 but cannot
start until 28; its latency is 20 ms, though its service needs only
4 ms. The fifth has the same 20 ms total latency.

A one-client closed loop sends at $[0,4,8,28,32]$ ms instead.
Completions happen at the same times in this constructed example,
but observed request latencies are $[4,4,20,4,4]$ ms rather than
$[4,4,20,20,20]$ ms. The client withheld the fourth and fifth arrivals
while earlier work ran. This is not a wrong test; it is a different
arrival process. It cannot establish a tail-latency guarantee for
the external schedule.

MLPerf's rules similarly distinguish completion-driven single-stream
queries from independently generated Server queries, and make accuracy,
latency and workload definitions part of a result~\cite{mlcommons2026rules}.
Our four-request fixture is not an MLPerf submission. It teaches why
an experiment needs such contracts before its largest rate becomes
interpretable. Production batching, admission and cancellation add
mechanisms that the single-worker model deliberately leaves out.

\subsection{A percentile needs a method and a population}
Sort the earlier sample $[9,10,10,11,60]$ ms. Under the nearest-rank
method, empirical percentile $p$ selects sorted index
$\max(1,\lceil pn\rceil)$ using one-based indexing and sample count $n$.
For $p=0.95$ and $n=5$, the index is five, so the sample p95 is 60 ms.
An inclusive linear method instead uses zero-based coordinate
$p(n-1)=3.8$, giving $11+0.8(60-11)=50.2$ ms.
Neither number is a reliable estimate of a service's extreme tail
from five observations.

Python's statistics documentation distinguishes inclusive and exclusive
quantile conventions~\cite{python2026statistics}. The lesson implements
nearest rank and inclusive interpolation explicitly; a unit test checks
the inclusive result against the standard-library implementation.
A function named percentile is insufficient provenance unless the
reader knows its interpolation rule and sample population.

Population matters even with one convention. Suppose one request supplies
100 gaps of 1 ms and another supplies one gap of 100 ms.
Pooled nearest-rank p95 selects the 96th of 101 gaps: 1 ms.
The two per-request mean gaps are $[1,100]$ ms, whose nearest-rank
p95 is 100 ms. The long response contributes many samples to the
pooled metric; each request contributes one to the second metric.
Choose the population that matches the service promise.

For small experiment runs, report each observation, a median and a
range instead of decorating a few measurements with unsupported
tail precision. Repeating a benchmark nine times provides nine
run observations, not thousands of independent request-tail samples.
Correlation from one process, one input and one machine state still
matters. Independent reruns probe a different layer of variability.

\subsection{Wait for the output, not for submission}
A duration requires a clock and two events. The Python experiment
uses \texttt{perf\_counter\_ns}: integer timestamps avoid the floating-point
representation loss of a large clock value. The clock measures elapsed
time rather than only CPU execution time; its origin has no useful
meaning, so subtract readings from the same clock domain~\cite{python2026time}.
Nanosecond units do not imply nanosecond resolution or accuracy.

The recorded M1 run reports a clock resolution of about 42 ns.
That is the clock's reported granularity, not a bound on OS scheduling,
timer overhead or benchmark variance. Its toy computation takes
hundreds of microseconds to milliseconds, but observed times still
include Python allocation and execution overhead.

The functions in this lesson are synchronous: when a call returns,
the result exists. Accelerator submission is different. Stopping a host
timer after launching a kernel can price launch overhead while the
device has barely begun. NVIDIA's timing guidance explicitly distinguishes
CPU timers with completion synchronization from device-event timing
and warns that synchronization changes execution~\cite{nvidia2026bestpractices}.
No CUDA timing is performed here.

Choose the boundary according to the question. A device-event interval
may isolate work in a stream; a synchronized host interval can include
submission and waiting; a client interval includes delivery. Competing
streams or unrelated work can still affect an interval. An isolated
experiment may drain previous work before starting, but imposing that
drain on every production request changes the system being studied.
There is no universal timer placement that measures all three questions.

\subsection{Build a complete, cheap correctness-first experiment}
The optional measured mode compares two ways to multiply illustrative
$24\times24$ integer matrices. The baseline uses explicit row, column,
reduction loops. The candidate first transposes the right operand into
column tuples, then uses row--column dot products. This changes Python
loop and indexing overhead as well as traversal; it is not a controlled
test of cache behavior alone.

The matrices contain deterministic small signed integers. An independent
reduction-first loop constructs every expected output with exact integer
arithmetic. Both implementations are checked before warm-up and every
timed result is checked afterwards. Comparing only a checksum could miss
reordered or compensating output errors; here all 576 coordinates must
match. These are integer calculations, not a claim of floating-point
equivalence for an LLM.

Read the candidate's data transformation before timing it:
\begin{minipage}{\linewidth}
\CodeLines{../code/foundations/experiment_trace.py}{161}{166}
\end{minipage}
After transposition, each tuple is one column of the original right
operand. The paired values in the inner \texttt{zip} therefore have
the same reduction index. No output axis is transposed. The small
integer oracle tests every coordinate, not only the matrix shape.

Run from the repository root:
\begin{verbatim}
python3 code/foundations/experiment_trace.py
python3 code/foundations/experiment_trace.py \
  --measure --size 24 --repetitions 9 --warmups 2
\end{verbatim}
Default mode prints only derived trace statistics. Measured mode records
nine pairs, reversing variant order on alternate pairs. Each variant has
two warm-up calls after initial correctness checks. Alternating AB/BA
reduces a fixed order imbalance; it does not randomize the experiment
or guarantee removal of thermal drift and interference.

\EngineFigure{foundation-experiment-flow}{The synchronous Python
experiment's control flow. An oracle failure aborts result reporting.
Packing is included in candidate total time; correctness checking is
outside the timer but mandatory. Raw pairs are retained before summaries.}
{fig:foundation-experiment-flow}

Three timestamps divide the candidate into preparation and computation.
Total time starts before transposition and stops after output construction.
The baseline has no separate preparation stage. Both include output
allocation; neither includes input generation, the reference calculation,
warm-up or result comparison. Those boundaries define a repeated-computation
experiment on existing inputs, not a cold-start or file-loading experiment.

\subsection{Read the observed result without inventing a mechanism}
On the recorded Apple M1 with macOS 26.6.2 and Python 3.9.6, the first
nine-pair run had median total times of 1.490500 ms for the baseline
and 0.805834 ms for the candidate. A second invocation gave
1.501083 and 0.809334 ms. Candidate medians include transposition,
not only the inner dot products. Both invocations passed every
output comparison.

The complete raw times, clock metadata, source hash, input hash and command
are in \texttt{research/measurements/2026-10-03-foundation-experiments.md}.
No model file or quantization is involved. The source hash identifies
the executed teaching program even though measurements were collected
before the revision was committed.

The candidate is faster in these two tiny Python runs. That observation
does not establish which fraction came from indexing, interpreter execution,
memory locality or allocation. It predicts neither native GEMM throughput
nor a token rate. The experiment is valuable because its boundaries and
correctness can be inspected, not because its speed ratio ranks engines.
The companion tests deliberately corrupt one output and require the
performance-reporting route to abort.

Try sizes smaller and larger than 24 while retaining the same checks.
Predict which fixed costs become visible. Do not compare a candidate's
compute-only interval with the baseline's total and call that fair
end-to-end acceleration. If preparation can genuinely be reused across
many calls, measure and name that amortized workload separately.
Keep a losing run or an unavailable check with its setup rather than
rewriting the hypothesis after seeing the result.

representation, hardware execution and evidence. You can follow
a token through the decoder, count its state, read its stored
weights and design a test of a claimed improvement.
