\chapter*{How to read this book}
\addcontentsline{toc}{chapter}{How to read this book}

Run a 7-billion-parameter model on a laptop or a gaming GPU and watch two
numbers: tokens per second, and the bytes per second the memory can deliver.
Multiply the first by the size of the model and you get almost exactly the
second. Generating one token reads every weight once, and the chip's
arithmetic units --- the part everyone talks about --- spend most of that time
waiting. Nearly every idea in a modern inference engine is a way of changing
that picture: doing more useful work per byte moved, moving fewer bytes, or
hiding the wait.

This book is organized around that accounting. Every inference engine
negotiates four scarce resources: \textbf{memory bandwidth}, the bytes moved
per token; \textbf{memory capacity}, the bytes that must stay resident;
\textbf{compute}, the floating-point operations; and \textbf{latency}, the time
a person waits for the first token and for each one after it. It does so for
two outcomes: a \textbf{correct} answer, and a low \textbf{cost} --- tokens per
dollar at a latency target. Each technique in the book enters as a response to
a measured constraint and is charged, in a small table we call the
\emph{constraint ledger}, for what it spends of the other resources. Batching
buys throughput with latency and memory. Quantization buys bandwidth and
capacity with accuracy. Speculative decoding buys latency with compute that
would otherwise sit idle --- and loses when it would not. When a new technique
appears next year, it will slot into the same ledger.

\section*{How each chapter works}
Every chapter has the same anatomy. It opens with a \emph{measurement} ---
a real, reproducible number that should surprise you. It then does the
\emph{napkin math}: the back-of-the-envelope cost model, with real model and
hardware numbers, before any code. It derives the \emph{mechanism}, charges it
in the \emph{constraint ledger}, and asks you to \emph{build it small} in a
self-contained lab that runs on a laptop. It tells \emph{what actually
happened} when real engines tried the idea, including the attempts that failed.
It ends with a dated \emph{frontier watch}, because this field changes every
month, and with exercises.

Numbers carry their provenance. A \emph{measured} number comes with a record
of the hardware, software, model file and command that produced it. A
\emph{derived} number shows its arithmetic. An \emph{illustrative} number says
so. Claims about the state of the art are checked against primary sources and
logged, with dates, in the book's frontier ledger.

\section*{How to read it}
Part~\ref{part:physics} is the foundation: read it first. It explains why
decode is bound by memory bandwidth, why prefill is bound by compute, why the
KV cache is the engine's central data structure, and how to predict the cost
of serving any model on any machine in five minutes. After that the parts can
be read in the order your work needs them. Parts~\ref{part:one-request}
and~\ref{part:serving} make one request fast and then serve many;
Parts~\ref{part:beyond-one-token} and~\ref{part:architectures} cover
speculation and the model architectures that reshape engines;
Parts~\ref{part:scaling-out} and~\ref{part:hardware-you-have} cover many GPUs
and too few; the last two parts cover correctness, measurement, production
and a capstone engine.

You need ordinary programming experience and basic linear algebra. The labs
are in Rust, with Python for independent checks. If you want to build the
Transformer computation from scratch before reading about engines, start with
Appendix~\ref{app:transformer}: it constructs tokens, tensors, matrix
multiplication, normalization, projections and rotary position step by step,
with a tested Rust engine and independent oracles.
