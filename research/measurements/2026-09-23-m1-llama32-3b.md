# Decode, prefill and batched decode of Llama 3.2 3B on an Apple M1

**Date:** 2026-09-23, 11:41–11:48 UTC.
**Used by:** Chapters 1, 3, 4 and 5 (opening measurements and napkin math).
**Raw outputs:** [`2026-09-23-m1-llama32-3b/`](2026-09-23-m1-llama32-3b/).

## Questions

1. How fast does a laptop GPU decode a small quantized model, and what
   fraction of its memory bandwidth and arithmetic does decode use?
2. How much faster per token is prefill than decode on the same weights?
3. How does aggregate decode throughput change with the number of sequences
   decoded together?

### Single-sequence prefill and decode (`llama-bench`, 5 repetitions, mean ± s.d.)

| Test | Tokens/s |
| --- | ---: |
| Prefill, 512 prompt tokens (`pp512`) | 247.75 ± 1.84 |
| Decode, 128 generated tokens (`tg128`) | 21.02 ± 0.30 |

### Achievable GPU bandwidth (MPS, median of 20 after 5 warm-ups)

| Read (sum) | 47.9 GB/s (best 53.3) | 46.0 GB/s (best 51.0) |
| Copy (read + write) | 49.9 GB/s (best 54.9) | 49.4 GB/s (best 54.9) |

### Batched decode (`llama-batched-bench`, second run, 128-token prompts, 64 generated tokens per sequence)

| Sequences $B$ | Aggregate decode tok/s | Per sequence | Step time |
| ---: | ---: | ---: | ---: |
| 1 | 20.08 | 20.08 | 49.8 ms |
| 2 | 23.13 | 11.56 | 86.5 ms |
| 3 | 21.90 | 7.30 | 137.0 ms |
| 4 | 46.43 | 11.61 | 86.2 ms |
| 5 | 50.09 | 10.02 | 99.8 ms |
| 6 | 44.40 | 7.40 | 135.1 ms |
| 8 | 48.63 | 6.08 | 164.5 ms |
| 12 | 78.34 | 6.53 | 153.2 ms |
| 16 | 101.14 | 6.32 | 158.2 ms |
| 24 | 140.92 | 5.87 | 170.3 ms |
| 32 | 175.87 | 5.50 | 182.0 ms |

Step time is $1000 \times B / \text{aggregate tok/s}$. The first run
(`-ntg 128`, $B$ = 1, 2, 4, 8, 16) gave 19.46, 21.08, 46.89, 48.92 and 99.47
tok/s: the same pattern.

llama.cpp reported the KV cache it allocated for `-c 8192`: 896 MiB, F16 keys
and values, 448 MiB each.

## Derived numbers

- **Bytes per decode token.** With tied embeddings the output projection reads
  the whole 323 MB table every step, so a decode step reads essentially all
  2,011,539,712 tensor bytes. KV reads during `tg128` average about 64 cached
  tokens × 114,688 bytes ≈ 7.3 MB per step, 0.4% of the weights; ignored.
- **Decode bandwidth.** 2.0115 GB × 21.02 tok/s = **42.3 GB/s**:
  62% of the nominal 68.3 GB/s (LPDDR4X-4266 × 128 bit; Apple states the
  M1 Max's 400 GB/s is "nearly 6x" the M1's), and **85–92%** of the 46–50 GB/s
  that a simple streaming kernel achieved on the same GPU at the same time.
- **Arithmetic.** A forward pass costs about 2 FLOPs per parameter used in a
  matrix product; with the tied table counted once (as the output
  projection), that is 2 × 3.213 × 10⁹ ≈ 6.43 GFLOP per token. Decode:
  21.02 × 6.43 GFLOP ≈ **135 GFLOP/s**, about **5%** of the 2.6 TFLOP/s Apple
  quotes for the M1 GPU. Prefill: 247.75 × 6.43 GFLOP ≈ **1.59 TFLOP/s**,
  about **61%**. Attention-score FLOPs at these lengths add about 1% and are
  ignored.
- **Arithmetic intensity** of batch-one decode: 6.43 GFLOP / 2.01 GB ≈
  **3.2 FLOP/byte**. The M1's ridge point is 2.6 TFLOP/s ÷ 68.3 GB/s ≈ 38
  FLOP/byte nominal, or ≈ 52–57 FLOP/byte against the achieved 46–50 GB/s.
- **Prefill against decode:** 247.75 / 21.02 ≈ **11.8×** more tokens per
  second on the same weights.
- **Batching:** at $B = 32$ the machine produces 175.87 / 20.08 ≈ **8.8×**
  the tokens of $B = 1$, while each step takes 182.0 / 49.8 ≈ **3.7×** as
  long.
- **KV per token:** 896 MiB / 8,192 tokens = 112 KiB = 2 × 28 layers × 8
  heads × 128 × 2 bytes. llama.cpp's allocation confirms the formula.

## Why batched decode is a staircase

The step times are not smooth in $B$. They follow ggml's Metal kernel
selection for K-quant weights, read at llama.cpp commit `389ff61d`
(2026-05-10, as vendored in Hermon), file
`ggml/src/ggml-metal/ggml-metal-ops.cpp`, and
`ggml-metal-device.cpp` for tile sizes:

- $B = 1$–3: the plain matrix–vector kernel, one batch column per pass over
  the weights (`nr1 = 1`). Two or three sequences cost nearly two or three
  weight passes (86.5 and 137.0 ms against 49.8 ms).
- $B = 4$–8: a small-batch matrix–vector kernel (`mul_mv_ext`, enabled for
  K-quants only at 4–8 columns) that handles 3, 4 or 5 columns per pass
  (`r1ptg`): one pass at $B$ = 4 and 5, two at 6 and 8.
- $B > 8$: the tiled matrix–matrix kernel, whose tiles on devices without
  Metal's tensor API (the M1) are 64 weight rows × 32 batch columns. Any
  batch from 9 to 32 costs one column tile, so the step time is nearly flat
  from $B$ = 12 to 32.

The measured binary is build d00685831, not the vendored commit, so this is
an explanation consistent with every measured point rather than a proof
that the two builds select kernels identically.

## Limits

- One machine, one model, one quantization, one run per configuration of the
  batched benchmark; a busy desktop.
- Decode was measured from an empty context (`tg128`) or 128-token prompts;
  long contexts add KV reads (Chapter 5).
- The MPS kernels are a practical ceiling, not the hardware's peak; a
  hand-tuned Metal kernel may reach more.
- Apple does not state the precision of its 2.6 TFLOP/s figure; it is used
  as the compute roof without further assumption.
