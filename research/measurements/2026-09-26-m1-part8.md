## Questions

1. Does a greedy request's output depend on what else llama.cpp decodes beside
   it, for a dense and a mixture-of-experts model, and do the groups of batch
   sizes with identical results match the Metal kernel-selection rules?
   (Chapter 38)
2. How much locality does a real router have, and how do LRU, a learned
   frequency policy and the offline optimum do on its trace? (Chapter 36)
3. How much does the same benchmark vary within an hour and across days, and
   what is the flash-attention flag worth? (Chapter 39)
4. What do a closed and an open load generator report for the same server
   through a stall? (Chapter 39)
5. Where is one llama-server's saturation knee, and what do its own counters
   show on either side? How long does a new replica take to serve? (Chapter 40)
6. How do runtime choices compare on one distribution-level scale: repeat,
   physical batch, flash attention, cache precision, weight precision?
   (Chapter 38)
7. Do llama.cpp's server, Ollama and Hermon produce the same output from the
   same file, and at what speed? (Chapter 41)
8. Where does the capstone engine sit on the roofline of this machine, and why?
   (Chapter 42)
9. What does keeping experts on the CPU cost when there is no link to cross?
   (Chapter 35)

## Commands

```bash
# batch variance and routing (run_part8a.sh)
probe8 batch <llama> target.txt fillers.txt 256 batch-llama32-3b.json 1 2 3 4 8 16 32 64
probe8 batch <granite> target.txt fillers.txt 256 batch-granite.json 1 2 3 4 8 16 31 32 48 64

python3 analyze_routing.py route-granite.json route-analysis.json
# repeat, stall, sweep, KL (run_part8b.sh)
llama-bench -m <llama> -fa 1 -p 0 -n 128 -r 3 -o json            # 12 times, 15 s apart
python3 loadgen.py stall out/loadgen                                # closed vs open, SIGSTOP 5 s
python3 loadgen.py sweep out/loadgen                                # 60 s per rate
llama-perplexity -m <llama> -f text.txt -c 512 --chunks 8 -ngl 99 --kl-divergence-base base.kld [--kl-divergence ...]
llama-quantize --allow-requantize <llama> requant-q2_k.gguf Q2_K
# flash-attention A/B, capstone v1, Hermon build, three engines (run_part8c.sh)
llama-bench -m <llama> -fa {0,1} -p 0 -n 128 -r 3 -o json         # interleaved, 4 rounds
cargo run --release -p capstone --example capstone_roofline
cargo build --release -p hermon-cli --features engine-metal
python3 engines3.py out/engines3 <hermon>
# capstone v2-v4 (run_part8d/e/f.sh): capstone_roofline <out.json> 1 2 4, 2 or 3 runs each
# second sweep, cold start, expert placement
python3 loadgen.py sweep2 out/loadgen                               # 120 s per rate
python3 coldstart.py out/coldstart
llama-batched-bench -m <granite> -c 2048 -b 512 -ub 512 -npp 128 -ntg 64 -npl 1,4 -ngl 99 --no-repack [--n-cpu-moe 16 | --cpu-moe]
```

`probe8.cpp` decodes a target prompt alone, then beside `B − 1` filler
requests in one llama.cpp context, compares the target's logits step by step
while the generated histories agree, and records the top-1 minus top-2 margin
of the batch-of-one run. The target's prompt is always prefilled alone; the
first generated token is the control and matched in every run.

## Derived

- Runs per arm to resolve δ with two standard errors, σ = 2.4%:
  n ≥ 2(2σ/δ)²: 12 for 2%, 46 for 1%, 2 for 5%.
- Poisson arrivals in 120 s: 24 ± 4.9 at 0.2/s, 36 ± 6.0 at 0.3/s.
- Capstone napkin: 1 thread B = 1: 193.5 MFLOP / 20.0 GFLOP/s = 9.7 ms → 103
  tok/s (measured 106); B = 8: 1,548 / 46.3 = 33.4 ms → 239 (216); 4 threads
  B = 8: max(387 MB / 52.1 GB/s = 7.4 ms, 1,548 / 109.8 = 14.1 ms) + 64 calls ×
  33.6 µs = 16.3 ms → 491 (491).
- Decode bound on the M1 GPU for a 2.01 GB file: 46–53 GB/s / 2.01 GB = 23–26
  tok/s.
- Cost: running the server saturated instead of at 70% of capacity: 24.86 /
  17.27 = 1.44× the tokens; p99 TTFT 29.25–42.48 s against 6.32 s.

## Anomalies

- **Capstone v1's memory ceiling measured arithmetic.** `dot(a, a)` is 0.5
  FLOP/byte; at 11.8 GFLOP/s that is 23.6 GB/s, the reported "memory ceiling".
  The v1 run also failed to write its JSON (the output path was given after a
  `cd`); the numbers are in `capstone-roofline.txt`.
- **v2 regressed the probe** to 17.8 GB/s: a 32-element array accumulator
  compiled to scalar code with spilled registers. Kept as `capstone-roofline2*`.
- **Roofline points above their ceiling** in v2–v4 output (up to 135%): in v2
  and v3 the ceilings were measured on 512 × 512 operands while the model's rows
  are 1,024 and 3,072 wide (v4 measures them at width 1,024); in v4's first run
  the ceilings were measured while the machine was busier than during the
  decode steps (4-thread tiled ceiling 75.6 against 109.8–112.6 in runs 2–3).
  The book uses v4's medians.
- **First sweep** ran under load that rose to 19/40/27; kept, not used. The
  first sweep2 attempt failed because the model file had been removed (log
  kept as `loadgen-sweep2-attempt1-model-missing.*`).
- **Hermon's `blocking_send`**: from code reading, not measured
  (`crates/hermon-runtime/src/batched.rs` at `2a3fd52`).

## Limits

- Single-machine results on a desktop in use, under memory pressure; the load
  tests and benchmarks give conditions but cannot remove them.
- Batch variance was measured on Metal with two models and one prompt each; the
  kernel regimes are read from source, and other backends have other rules.
- The routing trace is one small mixture-of-experts model (40 experts per
  layer), greedy, over 2,705 tokens of eight prompts; it says nothing directly
  about Qwen3-30B-A3B's router.
- The load tests use fixed output lengths and one prompt distribution; a
  server's knee moves with both. Cold starts were measured with the model file
  in the page cache, so they exclude storage.
- The capstone runs on the CPU with f32 weights; its ceilings are its own
  kernels', not the machine's peaks.
- vLLM and SGLang were read at pinned commits, not run.
