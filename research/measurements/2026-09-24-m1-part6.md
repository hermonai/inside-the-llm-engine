# Part VI measurements on an Apple M1: a model split across processes, and moving a KV cache

**Date:** 2026-09-24, 16:46–17:33 UTC.
**Used by:** Chapters 31, 33 and 34 (opening measurements, napkin math,
ledgers), Figure `fig:ch34-load-recompute`; Chapter 32's imbalance figures (a seeded simulation, not a
measurement).
**Raw outputs:** [`2026-09-24-m1-part6/`](2026-09-24-m1-part6/). Local paths
are redacted to `<scratch>`, `<ollama-blobs>` and `<home>`, and the loopback
address in server logs to `<loopback>`; the probe scripts connect to
`localhost`.

## Questions

1. What does splitting a model's layers across two llama.cpp processes cost,
   with the second reached through llama.cpp's RPC backend over loopback TCP
   and both on the same GPU? (Chapter 31)
2. How fast does this machine's SSD deliver bytes with caching off, and
   through the page cache? (Chapter 34)
3. For prompts of about 1K, 4K and 16K tokens, how does recomputing a KV
   cache compare with restoring it from host memory, from a file in the page
   cache, and from a file on the SSD? Is the continuation identical?
   (Chapters 33, 34)
4. Can prefill run on one server and decode on another, with the cache moved
   through a file, and does the text match a single server's? (Chapter 33)
5. Under uniform routing, how far above the mean is the busiest device in
   expert parallelism? (Chapter 32; derived by simulation)

### A model split across two processes (`rpc`, `rpc2`, `placement`)

`rpc-server -p 50052 -d MTL0` (Metal device, loopback address by default) and
`llama-bench -fa 1 -p 512 -n 64` in three configurations: *local* (no RPC),
*split* (`--rpc localhost:50052 -ts 1/1`), *remote* (`--rpc localhost:50052
-ts 1/0`). llama.cpp lists RPC devices first, so the split gave the RPC device
the first 15 of Llama 3.2 3B's 29 layer slots (852.89 MiB of weights) and the
local GPU the other 14; *remote* gave the RPC device all 29 (1,918.35 MiB); the
token-embedding table stayed on the CPU in every configuration
(`placement-*.err`, verbose runs).

### Moving a KV cache against recomputing it (`kvmove`)

`llama-server -np 1 -c 20480 -fa on --slot-save-path <dir>` (default
`--cache-ram` 8,192 MiB). For each prompt: a cold prefill (`n_predict` 1);
`POST /slots/0?action=save`; an unrelated prompt, which moves the slot's state
into the host-memory prompt cache, then the original prompt again (restored
from that cache); `erase`, `restore` from the saved file and the prompt again;
a copy of the file written with `F_NOCACHE`, `erase`, `restore` from the copy
and the prompt again. Prompts are the first words of `doc.txt` after a salted
first line, sized with `/tokenize`.

| Model | Prompt tokens | Cold prefill | Save to file | File size | Into host cache | Back from host cache + 1-token prompt | File restore + 1 token | Uncached-copy restore + 1 token | Same next token |
| --- | ---: | ---: | ---: | ---: | ---: | --- | --- | --- | --- |
| Llama 3.2 3B | 1,021 | 3.68 s | 0.19 s | 117,113,484 B | 0.047 s | 0.014 + 0.058 s | 0.017 + 0.048 s | 0.068 + 0.043 s | yes |
| Llama 3.2 3B | 4,096 | 16.55 s | 0.62 s | 469,828,284 B | 0.243 s | 0.020 + 0.055 s | 0.250 + 0.051 s | 0.261 + 0.049 s | yes |
| Llama 3.2 3B | 16,384 | 96.56 s | 3.08 s | 1,879,311,036 B | 1.359 s | 1.386 + 0.174 s | 1.337 + 0.108 s | 0.694 + 0.088 s | yes |
| Qwen3-8B arch. | 1,024 | 9.75 s | 0.28 s | 151,012,220 B | 0.052 s | 0.011 + 0.133 s | 0.147 + 0.124 s | 0.066 + 0.109 s | yes |
| Qwen3-8B arch. | 4,095 | 51.23 s | 1.16 s | 603,898,732 B | 0.608 s | 0.453 + 0.201 s | 0.596 + 0.156 s | 0.345 + 0.163 s | yes |
| Qwen3-8B arch. | 16,382 | 282.90 s | 8.92 s | 2,415,887,196 B | 4.386 s | 67.338 + 0.608 s | 4.045 + 0.406 s | 3.665 + 0.426 s | yes |

Host-cache times are the server's own "prompt cache update took" log lines
(`kvmove-*.server.log`): the first when the unrelated prompt displaced the
slot's state into the cache, the second when the original prompt brought it
back. The file times are the `save_ms` and `restore_ms` the server reports. The file sizes equal the cache bytes the layout implies (112
or 144 KiB per token) plus a small header. Prefill rates: 170–277 tokens per
second for Llama 3.2 3B, 58–105 for the Qwen3-8B architecture.

Two observations bound what these numbers mean. The copy written with caching
disabled was meant to force a read from the SSD, yet for Llama 3.2 3B at 16,384
tokens it restored at 2.71 GB/s, faster than the uncached reads above allow;
at least part of it came from memory, so the two file columns are treated as
one tier. And the host-memory prompt cache, a copy held in the server's own
memory, took 67 seconds to restore the 2.3 GiB cache on a machine then using
about 19 GB of swap (`conditions.log`), slower than restoring the file.

Two `llama-server` processes (P and D) with Llama 3.2 3B, `-np 1 -c 8192 -fa

## Limits

- One laptop, under heavy load from other work during parts of the run (see
  Conditions). The RPC split has no network in it: both processes share one
  GPU and one memory, so it measures the cost of a process boundary and the
  RPC protocol, not of a link; real multi-GPU and multi-node numbers need a
  multi-GPU host.
- The SSD figures are for a nearly full, encrypted internal SSD read by one
  thread in 16 MiB requests; they are this machine's, not an NVMe device's.
- Chapter 32's imbalance figures are a simulation with uniform routing, a best
  case; no MoE model was measured.
