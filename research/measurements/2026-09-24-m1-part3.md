# Part III measurements on an Apple M1: request lifecycle, batching, KV layout, prefix caching, chunked prefill, overload, structured output and adapters

**Date:** 2026-09-24, 01:53–02:22 UTC.
**Used by:** Chapters 14–21 (opening measurements, napkin math, ledgers and
case studies); Figure `fig:ch18-stall-comb`.
**Raw outputs:** [`2026-09-24-m1-part3/`](2026-09-24-m1-part3/). Local paths
are redacted to `<scratch>`, `<ollama-blobs>` and `<home>`.

## Questions

1. What are time to first token and inter-token latency for one streamed
   request, and when does a server stop generating for a client that has
   disconnected? (Chapter 14)
2. What does continuous batching change for a short request that arrives
   during a long one? (Chapter 15)
3. What does a per-slot KV reservation refuse that a unified pool accepts?
   (Chapter 16)
4. What does a prefix-cache hit save, what breaks it, and what does restoring
   an evicted prefix from host memory cost? (Chapter 17)
5. How does a long prompt interfere with a running stream, and how does the
   logical batch size change the interference? (Chapter 18)
6. What happens when concurrent requests exhaust the KV cache? (Chapter 19)
7. What do schema-constrained outputs cost, and how valid are unconstrained
   ones? (Chapter 20)
8. What do LoRA adapters cost per token, can requests with different adapters
   share a step, and what does switching whole models cost? (Chapter 21)

## Commands

The probes are one stdlib Python script, `serve_probe.py`, which starts
`llama-server` with the flags below for each case, drives it over HTTP with
monotonic timestamps on every streamed event, and stops it:

```bash
python3 serve_probe.py <experiment> <outdir>      # one experiment per process
python3 make_lora.py <out.gguf> <rank> <seed> <gguf-py path>
python3 ollama_switch.py <out.json>
python3 sse_bytes.py <outdir>
```

| Experiment | Server flags | Workload |
| --- | --- | --- |
| `lifecycle` | `-np 1 -c 4096` | 200-token prompt, 128 tokens streamed, 6 runs (first discarded as warm-up); a stream closed by the client after 20 events; a non-streamed 2,000-token request whose socket is closed after 3 s (the slot endpoint polled every 20 ms) |
| `cancel2` | `-np 2 -c 8192 --log-timestamps` | Non-streamed 1,500-token request pinned to slot 0, socket closed after 3 s; the slot endpoint polled every 1.5 s; once on an idle server, once while a second client streams 500 tokens on slot 1 |
| `contbatch` | `-np 4 -c 16384`, with and without `-nocb` | A: 100-token prompt, 512 tokens streamed; B: 100-token prompt, 32 tokens, sent 2 s after A; 3 runs each |
| `kvlayout` | `-np 4 -c 8192`, `-no-kvu` and `-kvu` | One 3,001-token prompt, 16 tokens |
| `prefix` | `-np 1 -c 8192` (default prompt caching and 8,192 MiB host prompt cache) | 3,000-token document + questions, 8 tokens each, in the sequence of the results table |
| `chunked` | `-np 2 -c 16384`, `-b/-ub` = 2048/512, 512/512, 256/256 | A: 100-token prompt, 400 tokens streamed; B: 4,000-token prompt, 8 tokens, sent 3 s after A; 2 runs each |
| `overload` | `-np 4 -kvu`, `-c 4096` and `-c 8192` | Four streamed requests at once: 200-token prompts, 1,200 tokens each |
| `structured` | `-np 1 -c 4096` | Chat request for a JSON book record, temperature 0.8, seeds 1–20, `max_tokens` 200; unconstrained, with the JSON schema as `response_format`, and with the genre items as an enum of 2,000 strings |
| `lora` | `-np 2 -c 8192 --lora-init-without-apply --lora a,b,c` | 100-token prompt, 128 tokens, adapter chosen per request by `lora` scales; single streams, then two concurrent streams with no adapter, the same adapter, or two different adapters |
| `sse_bytes` | `-np 1 -c 2048` | 64 tokens streamed from `/completion` and from `/v1/chat/completions` |

## Results

### Lifecycle (Chapter 14)

| Run | TTFT | Server prompt time | Median gap | p90 gap | Max gap | 128 tokens |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 741 ms | 740 ms | 39.9 ms | 51.3 ms | 73.6 ms | 6.22 s |
| 2 | 746 ms | 744 ms | 40.3 ms | 46.0 ms | 53.2 ms | 6.04 s |
| 3 | 741 ms | 738 ms | 39.1 ms | 43.1 ms | 53.1 ms | 5.83 s |
| 4 | 762 ms | 757 ms | 40.5 ms | 48.5 ms | 83.1 ms | 6.16 s |
| 5 | 744 ms | 739 ms | 39.7 ms | 47.3 ms | 57.3 ms | 6.01 s |

Streamed request closed by the client after 20 content events: slot released
71 ms after the close, having decoded 21 tokens.

Non-streamed request, socket closed after 3 s:

| Case | Decoded at close | Observed afterwards | Released |
| --- | ---: | --- | --- |
| `lifecycle` (slot endpoint polled every 20 ms) | 55 | still generating when polling stopped after 20 s | only at server shutdown |
| `cancel2`, idle server (polled every 1.5 s) | 57 | released by the first poll, 1.51 s after the close | 82 tokens decoded |
| `cancel2`, second client streaming on the other slot | 30 | 30 → 498 tokens over 37.2 s | by the poll at 38.7 s, 523 tokens decoded; the other stream had finished 37.0 s after the close |

Explanation, from source at `d006858`: the non-streamed handler waits for
results in 1 s slices (`HTTP_POLLING_SECONDS`) and checks the socket only when
a slice expires with no result (`server_response_reader::next`); every result
for any waiting request calls `notify_all` on the shared condition variable
(`server_response::send`), and `recv_with_timeout` then starts a new 1 s wait.
Each slot-endpoint poll and each streamed token of another request is such a
result. The first observation (`lifecycle`) was therefore produced by the
measurement itself; `cancel2` repeats it with polling slower than the slice.

Bytes per streamed event (`sse_bytes`): `/completion` median 122 B (max 134;
final event with timings 2,035 B); `/v1/chat/completions` median 306 B (max
556).

settings and `can_batch_with` skips slots whose settings differ.

Adapter sizes (derived and matching `make_lora.py`'s count): rank 16,
24,313,856 parameters, 48,627,712 bytes F16; rank 64, 97,255,424 parameters,
194,510,848 bytes.

Ollama (`ollama_switch`): alternating the two models with `keep_alive: 0`,
`load_duration` 1.62–2.34 s and wall time 2.18–2.96 s per 8-token request; with
the model resident, `load_duration` 0.00 s and wall time 0.27–0.28 s. No model
was loaded before or after the probe.

## Limits

- One machine, one model family, a busy desktop session; each configuration
  ran two or three times. The book uses these results for mechanisms and
  ratios, not as capacity figures.
- Every claim about why the server behaved as it did comes from its source at
  `d006858`; the Homebrew binary reports build 8660 with commit prefix
  `d00685831`, which that commit matches.
- The disconnect behaviour was measured on non-streamed requests only. It has
  not been reported upstream as of this record.
- Adapters with B = 0 measure the cost of adapter arithmetic, not the quality
  of any fine-tune. The Ollama loads probably came from the operating system's
  file cache; cold loads from disk would be slower.
