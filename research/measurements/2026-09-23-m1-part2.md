# Part II measurements on an Apple M1: weight formats, cache formats, matrix shapes, attention memory and dispatch cost

**Date:** 2026-09-23, 18:32–19:22 UTC (a first pass under heavy load, then a
confirmation pass and three short cross-checks).
**Used by:** Chapters 7–10, 12 and 13 (opening measurements, napkin math and
ledgers); Figure `fig:ch10-quant-sweep`.
**Raw outputs:** [`2026-09-23-m1-part2/`](2026-09-23-m1-part2/). Local paths
are redacted to `<scratch>`, `<ollama-blobs>` and `<home>`.

## Questions

1. How does decode speed change with the weight format when the model and the
   engine are held fixed? (Chapter 10)
2. What does attention over a long KV cache cost per step, and how do 8- and
   4-bit cache formats change it? (Chapters 9 and 12)
3. How does a matrix product's throughput depend on its shape, from
   matrix–vector to square, on the same GPU and library? (Chapter 7)
4. What happens to naive, fused and blockwise attention as the sequence grows
   under a fixed memory budget? (Chapter 8)
5. What does one extra GPU operation cost when issued from PyTorch, and what
   does compilation recover? (Chapter 13)

**Conditions.** An ordinary desktop session, nothing closed for the
measurement, memory under pressure throughout (swap 17–21 GB used). The
first pass ran immediately after `llama-quantize` finished: one-minute load
average 27.4 at the start of the weight-format runs and 12.8–16.3 during the
cache runs. The confirmation pass waited for the one-minute load average to
fall below 6 (below 4 for the GEMM probe) and started at 3.1–5.5; the load
rose to 9.2 around the attention probe and to 11.8 by the end of the last
cache run. Each segment's start is logged in
`conditions.log` and `conditions2.log`. The book uses the confirmation pass;
the first pass is kept because it shows how much a busy machine moves the
numbers.

## Commands

```bash
# Weight formats (first pass -r 3, confirmation -r 5)
llama-bench -m <model> -p 512 -n 128 -r 5 -o json
# Cache formats at depth, flash attention on (first pass: -d 0,4096,8192,16384 -r 2)
llama-bench -m <Q4_K_M> -fa 1 -ctk <t> -ctv <t> -p 0 -n 64 -d 0,8192 -r 3 -o json
llama-bench -m <Q4_K_M> -fa 1 -ctk <t> -ctv <t> -p 0 -n 64 -d 4096,16384 -r 3 -o json
# First pass only: flash attention off, f16 cache
llama-bench -m <Q4_K_M> -fa 0 -p 0 -n 64 -d 0,4096,8192,16384 -r 2 -o json
# PyTorch and NumPy probes
python3 gemm_shapes.py
python3 attention_memory2.py <naive|sdpa|tiled> <tokens>   # one process per case
python3 launch_overhead2.py
```

The driver scripts (`run_all.sh`, `run_second.sh` … `run_fifth.sh`) and every
probe are in the raw directory. Each probe checks its results before timing:
products against a float64 NumPy oracle on 8 rows; attention against a
float64 CPU computation of query rows 0, S/2 and S−1 (the last row attends to
every key); the dispatch chains against a single operation, with exact
equality.

### 4. Causal attention under a 6 GiB allocator cap (Chapter 8)

Batch 1, 8 heads, head width 128, float16 inputs; one process per case;
`torch.mps.set_per_process_memory_fraction` set to 6 GiB of the 11.84 GiB
recommended maximum. *naive* computes all scores (fp16), masks, softmaxes in
fp32 and casts back; *sdpa* is `torch.nn.functional.scaled_dot_product_attention`
with `is_causal=True`; *tiled* is a blockwise online softmax in eager PyTorch
(blocks of 1,024 queries × 1,024 keys, fp32 running state). Median of 3 timed
calls (2 above 8,192 tokens) after the first call.

| Tokens | naive | sdpa | tiled | Error vs float64 (naive / sdpa / tiled) |
| ---: | --- | --- | --- | --- |
| 1,024 | 7.7 ms | 8.7 ms | 13.0 ms | 1.5e-4 / 6.0e-5 / 6.0e-5 |
| 2,048 | 28.3 ms | 30.6 ms | 32.4 ms | 1.8e-4 / 5.8e-5 / 5.8e-5 |
| 4,096 | 120.1 ms | 122.4 ms | 102.5 ms | 1.3e-4 / 4.8e-5 / 4.8e-5 |
| 8,192 | refused (see below) | first call ran; refused on repeat | 340.1 ms | — / — / 2.9e-5 |
| 16,384 | refused | first call ran; process failed after it | 1.293 s | — / — / 1.5e-5 |
| 32,768 | refused: `Invalid buffer size: 16.00 GiB` | refused: `Invalid buffer size: 16.00 GiB` | 4.653 s | — / — / 1.4e-5 |

The allocator's messages, verbatim in the raw directory:

- naive, 8,192: `MPS allocated: 4.00 GiB, other allocations: 400.00 KiB,
  max allowed: 6.00 GiB. Tried to allocate 2.00 GiB`.
- naive, 16,384: `MPS allocated: 5.00 GiB … Tried to allocate 4.00 GiB`.
- sdpa, 8,192 (second call): `MPS allocated: 1024.00 MiB, other allocations:
  4.13 GiB, max allowed: 6.00 GiB. Tried to allocate 1024.00 MiB`.
- sdpa, 16,384 (a 256-byte allocation after the first call): `MPS allocated:
  1024.00 MiB, other allocations: 16.50 GiB`.

*Other allocations* is memory the Metal device holds outside PyTorch's
caching allocator — for the fused call, its internal buffers. The cap does not
govern them, which is how the 16,384-token call could hold 16.5 GiB on a
16 GB machine. They grow with the square of the length: 4.13 GiB at 8,192 and
16.50 GiB at 16,384 is consistent with two fp32 score matrices (2 GiB each at
8,192; 8 GiB each at 16,384). Derived: the naive fp16 score matrix is
8 × S² × 2 bytes: 1 GiB at 8,192, 4 GiB at 16,384, 16 GiB at 32,768; Metal
refused the 16 GiB buffer outright. The tiled version's largest temporaries
are 8 × 1,024 × 1,024 × 4 bytes = 32 MiB blocks. After its first call only
the inputs and output are allocated (128 MiB at 16,384 tokens =
4 × 8 × 16,384 × 128 × 2 bytes).

Guard added during the run: after the 16,384-token *sdpa* case, the probe was
edited to skip *sdpa* at 32,768 so it would not request another four-fold
allocation. The 32,768-token *sdpa* case had already run and failed on its
own (the `Invalid buffer size` record above), so the guard changed no result.

An earlier version of this probe without a cap (`attention_memory.py`, first
pass, load average 8.7) ran naive attention at 8,192 tokens in 524 ms and
the fused call in 812 ms. It tried to measure memory as the change in
`driver_allocated_memory`, which moves in whole heaps (0, 1, 2 or 6 GiB), too
coarse to separate the cases; that is why the confirmation probe used a cap
and recorded success or refusal instead.

### 5. Dispatch cost (Chapter 13)

A chain of *n* dependent `x = x + 1` operations on 1,024 float32 values,
against one `x + n`; median of 15 after 3 warm-ups (first pass: 7 after 2).
*Per extra op* = (chain − one) / (n − 1).

| n | chain | one op | per extra op | compiled chain | first compiled call |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 10 | 0.238 ms | 0.161 ms | 8.7 µs | 0.162 ms | 0.08 s |
| 100 | 0.734 ms | 0.168 ms | 5.7 µs | 0.170 ms | 0.36 s |
| 1,000 | 6.514 ms | 0.214 ms | 6.3 µs | 0.209 ms | 2.61 s |

First pass (no compilation): 5.7 µs per extra op at n = 100 and 5.9 µs at
n = 1,000; one op 0.14–0.15 ms. At n = 1 the difference is noise (−11 µs).
The compiled chain costs what one operation costs. A follow-up run with
`TORCH_LOGS=output_code` (`compile_kernels.py`; excerpt in
`compile_kernels.txt`) shows why: for both n = 10 and n = 1,000, Inductor
generated one Metal kernel, `generated_kernel`, containing every addition,
and the compiled graph launches it once with 1,024 threads.

## Limits

- One machine, one model, a busy desktop session. Ratios are what the book
  uses; absolute numbers move with load, as the two passes show.
- The re-quantized files measure speed, not accuracy.
- `llama-bench` decode rates at depth come from 64 generated tokens after a
  pre-filled cache; they do not include the prefill of that cache.
- The PyTorch probes measure PyTorch's MPS backend as shipped in 2.10.0, not
  Apple's hardware limits; the attention probe's blockwise version is eager
  PyTorch, so each block's scores still travel through memory.
- No profiler was used. Explanations of the N = 8/16 step and of the
  quantized-cache slowdowns are hypotheses.
